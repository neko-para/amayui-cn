# 物品 / 建筑 / 配方数据结构（ITINIT / PLINIT / ALINIT）

> 级别：**已确认**（`data/*ITINIT.txt`、`data/*PLINIT.txt`、`data/*ALINIT.txt` 全量反汇编文本实证 + Fandom 配方 wiki 交叉验证）。
> 产出脚本：`scripts/extract-recipes.js` → `metadata/items.json` / `buildings.json` / `recipe-items.json` / `recipe-buildings.json`。
> 本文件由早期两处散落文档**合并**而来：`docs/物品建筑配方.md` 与 `docs/AGE脚本语言与物品数据结构.md` §4（物品结构）/§5（配方调查）。后者 §5 曾误判「当前语料无配方表」——**实际上配方表在 `ALINIT.txt`**（即 `0x6ba7/6b9/6baa…` 行的 `mov`），已由 `物品建筑配方.md` 定位并验证。

## 1. 关键编码（解析的两把钥匙）

### 1.1 物品 id = 名字串地址 − `0x18e40`

每个物品在 `ITINIT.txt`（base + `$n$ITINIT`）里有一条 `set-string (global-string <addr>) "名称"`。

- **物品 id = `名称串地址 − 0x18e40`**。
- 例：青銅の導鍵 @`18e41` → id **1**；水色の木の実 @`18f09` → id **0xc9=201**；パール鋼 @`19049` → id **0x209=521**。
- ⚠️ disasm 里的值全为 **hex**（`209` = `0x209` = 521，不是十进制 209）；配方里的产品/材料值就是这个「串地址派生 id」。

### 1.2 建筑/设施 id = 名称串地址 − `0x1f5ba`（来源 PLINIT）

建筑/设施名在 `PLINIT.txt`（base + `$n$PLINIT`），同样用 `set-string (global-string <addr>) "名称"`。

- **建筑 id = `名称串地址 − 0x1f5ba`**。
- 例：アヴァロの工房 @`1f5bb` → id **1**；訓練場 @`1f5db` → id **33**。
- 吸收时排除以 `【` 开头的说明串（`【施設：…】` 是描述，不是名字）。

## 2. 物品记录结构（ITINIT，**早期调研结论 + 修正**）

- 每个物品 = `set-string (global-string 18exx) "名称"` + 连续若干条 `mov (global-int <地址>) <值>`（实测共 732 条「名称+mov」记录）。
- **并行数组、按物品 id 索引**：地址按物品下标 +1（青銅の導鍵=558746、白銀=558747、黄金=558748…），故「同一地址 = 同一字段」不成立；更正确模型是「若干并行数组、按物品 ID 索引，每条记录向相关数组各写一个槽位」。
- 物品种类 ≈「写了哪几个数组」（地址区间组合）：消耗品 7 数组、重要道具 4~5、素材 6、装备类另组数组。
- **已交叉验证的字段**：
  - **第一个数组 = 物品 id × 10**（与 foxofice `Files/EU18/DB/Item_*.txt` 逐一比对 20+ 条全吻合，含共同空缺 ID 4）：青銅の導鍵 0a→÷10=1、ドンパフ楽器 32→5、治癒の水・小 7f8→204、若葉の宝石 bc2→301。
  - 消耗品 `5ba4xx` 效果值：0xa/0x1e/0x64/0x1f4 与「回復 10/30/100/500」吻合（强相关，未游戏内验证）。
  - 消耗品 `5bf2xx`：买价/卖价（约 10:1，未验证）。
- **跨表引用用「裸 id」**：部分表直接引用 ÷10 后的裸 id（如 PLINIT「水実の木」设施产出字段 `70710a = c9` = 201 = 水色の木の実）。搜跨表引用时需**同时尝试两种编码（7da 与 c9）**。

## 3. ALINIT = 配方表（物品 + 建筑，同一张表按「标记值」分行）

`ALINIT.txt`（base + `$n$ALINIT`）用 `mov (global-int <addr>) <value>` 写配方。每行结构：

```
行标记(值=1|2)   →  产品(id)  →  若干元数据(6b*)  →  {材料id, 数量}*
```

| 标记值 | 含义 | 产品 id 用哪张名表 |
|---|---|---|
| `1` | 物品合成配方 | 物品名表（`0x18e40`） |
| `2` | 建筑/设施配方 | 建筑名表（`0x1f5ba`，PLINIT） |

判据（脚本里 `isMarkerAt`）：标记 = 值 `1`/`2`、地址前缀 `6ba7`/`6ba9`/`6baa`、且下一 mov 是产品数组（`6bab`/`6bad`/`6bae`）。

- **材料** = 行内所有 `6c*` mov，按出现顺序两两配对 `{材料id, 数量}`（顺序保留）。
- **元数据** = 产品之后、首个 `6c*` 之前的那批 `6b*` 字段。

> ⚠️ 修正早期文档：`AGE脚本语言与物品数据结构.md` §5 曾基于「只用 `7da/7f8` 同现点搜索」得出「当前语料无配方表」，**结论错误**——配方表确实在 `ALINIT.txt`（以 `6ba7…` 标记行 + 材料 `6c*` 行编码），`物品建筑配方.md` 已定位并验证。

## 6. 已知边界 / 待办

- **物品与建筑 id 空间重叠**：如 id 51 在物品表=城砦拡張図面Ⅰ、在建筑表=小さな家（黄）。`recipe-buildings.json` 的 `product` 统一用建筑名表（PLINIT）。若需区分可加 `productItem`/`productBuilding` 两字段。
- **每行元数据（`metadata`）语义未定**（需对 `AGE.EXE` 读这些数组的函数交叉验证）：
  - `6bafxx`：≈10000–11000，非物品名槽，像“代价/等级”或技能 id。
  - `6bb3xx`/`6bb6xx`：多为 1（布尔）。
  - `6bbaxx`：恒为 `32`(50)，像上限/等级乘数。
  - `6be5xx`：bb9=素手/bba=竜鰐刀/…，解析为**装备物品 id**，像“关联/可进化”物品。
  - `6bf9xx`：235c/235d/235e… 按行递增，像**技能/能力 id**。
- **id≤58 覆盖**：`recipe-items.json` 已覆盖全部可合成物品；`4,26,28,29,30,34,45-50` 经核实为不可制作（4=已知空缺槽；28/29/30=材料；26/34/45–50 在 ALINIT 无产品行）。
- **其余物品字段**（分类/种类/标志等）：**未定义**，需差分验证（改值 → 游戏内观察）。
