> 相关：同款「按 id 直接算地址」的定长数组模型见 `03-掉落数据.md`。

## 1. 三段并列定长数组（已确认）

技能表**不是**逐技能的变长记录，而是**三段并列的定长数组**，段与段之间 stride = `0x3e8`(1000)，即**技能 id 容量 1000**——与掉落表的「1000 单位容量」是同一套引擎惯例。

设 `SKILL_BASE = 0x1d4f4`，`skillId = 技能名串地址 − 0x1d4f4`：

| # | 段 | 地址算式 | 槽/技能 | 内容 |
|---|---|---|---|---|
| ① | **技能名** | `0x1d4f4 + id` | 1 | `防御` |
| ② | **简述**（单行摘要） | `0x1d4f4 + 0x3e8 + id` = **`0x1d8dc + id`** | 1 | `回避+10 物防&魔防+3　攻撃不可` |
| ③ | **题头** | `0x1d4f4 + 2×0x3e8 + 2×id` = **`0x1dcc4 + 2id`** | 2 | `【行動：防御】` |
| ③ | **详述** | `0x1dcc4 + 2id + 1` | （同上） | `　攻撃しない防御態勢 回避+10 物防と魔防+3` |

- **段边界严格成立**：`0x1d8dc = 0x1d4f4 + 0x3e8`、`0x1dcc4 = 0x1d8dc + 0x3e8`。前两段 1 槽/技能，第三段是 **2 槽/技能的配对数组**（题头 + 详述），所以第三段用 `2×id` 索引。
- **文件内的书写顺序**是「名 → 若干 mov → 题头 → 详述 → 简述」，但**地址归属与书写顺序无关**，一律按上表算式反推 id：

```
set-string (global-string 1d4f5) "防御|防御"                                  ← ① id=1
mov (global-int 6c65a3) a                                                     ← 数值字段（见 §4）
…
set-string (global-string 1dcc6) "【行動：防御】|【行动：防御】"                 ← ③ 题头 = 0x1dcc4+2×1
set-string (global-string 1dcc7) "　攻撃しない防御態勢 …|　不攻击的防御姿态 …"   ← ③ 详述 = +1
set-string (global-string 1d8dd) "回避+10 物防&魔防+3　攻撃不可|…"              ← ② 简述 = 0x1d8dc+1
```

**验证口径**（`app/amayui-toolkit/scripts/extract-metadata.mjs` 内置断言 + `src/services/dataset.test.ts`）：
把六个 SKINIT 的每条 `set-string` 地址按上表反解 `(skillId, 字段)`，若模型有误必然出现「同一 (id,字段) 被写两次」或「id 越界」。实测：

| 指标 | 结果 |
|---|---|
| 技能总数 | **450** |
| skillId 分布 | **稀疏**，落在 **1..803**（容量 1000，未写满） |
| 地址冲突（同 id 同字段重复定义） | **0** |
| 越界地址（id ∉ [1,1000)） | **0** |
| 无名技能（只有描述没有名字） | **0** |
| 四行全部落在同一文件内 | 是（base 与 `$1$`..`$5$` 互不交叉） |

## 3. 三行描述文案的文法（已确认）

### 3a. 题头：`【<分类>：<技能名>（假名）】　<属性后缀>`

- **分类共 13 种**（449 个带描述技能的分布）：

  | 分类 | 必殺 | 戦闘 | 魔法 | 特殊 | 範囲魔法 | 範囲必殺 | 合体攻撃 | 支援 | 移動 | 常時 | 行動 | 変身 | 範囲回復 |
  |---|---|---|---|---|---|---|---|---|---|---|---|---|---|
  | 计数 | 111 | 93 | 72 | 42 | 35 | 34 | 18 | 16 | 13 | 7 | 3 | 3 | 2 |

  中文侧同步汉化（必杀 / 战斗 / 魔法 / 范围恢复…），**449 条题头 100% 符合 `【x：y】` 文法**，无例外。
- **技能名部分可带注音**：12 例形如 `【必殺：刃剣舞（じんけんぶ）】`，中文题头会去掉假名（`【必杀：刃剑舞】`）。因此**题头内的名字 ≠ 技能名字段**，不可互相当作真值。
- **`】` 之后可跟属性后缀**（全角空格分隔）：242 条无后缀；其余共 46 种组合，含属性（火炎 / 電撃 / 冷却 / 暗黒 / 神聖 / 地脈 / 無 / 物理）、`再充填N`（冷却回合）、以及少量说明式后缀（`３回攻撃後に使える溜め技`、`味方を強化する精霊魔法`）。

### 3b. 详述 / 简述

- **详述**：技能说明面板正文，多以**全角空格**起首（3 例例外：#44、#352、#665 用半角或无缩进）。含射程 / 命中 / 消耗等文案。最长 38 字。
- **简述**：列表用紧凑单行摘要，最长 24 字。
- **两者均无空串**：449 个带描述技能的三行都是非空文本。

### 3c. 唯一例外：#40「進行不可」

`skillId=40`（`0x1d51c`，`進行不可|无法前进`）**只有名字，无三行描述**——`0x1d904`(简述) / `0x1dd14,0x1dd15`(题头,详述) 三个槽在六个文件里**均无写入**。它只带 2 个数值字段，是**仅供内部状态使用的技能槽**（非玩家可见技能）。

⇒ 导出侧以 `hasDesc` 标记；`false` 时三行取 `null`，前端 `SkillCard` 显式提示「只有名字、无描述文案」。

## 4. 数值字段（`mov` / `sub`）：骨架已探明，语义未定

本轮**未导出**数值字段，但先记录已探明的地址骨架，供后续接手：

设 `FIELD_BASE = 0x6c65a2`。共 4639 条 `mov`/`sub`，其地址呈两类形态：

| 形态 | 算式 | 覆盖 |
|---|---|---|
| **1 槽/技能的字段数组**（**字段主序**，字段之间 stride = 1000） | `0x6c65a2 + k×1000 + skillId` | **3385 条 / 73.0%** |
| **多槽/技能的二维子数组**（已定位两个） | `0x6c84e2 + 5×skillId + j`（j∈0..3）<br>`0x6d2cda + 13×skillId + j`（j∈0..12） | 30 + 743 条 |
| 合计已解释 | | **4158 / 4639 = 89.6%** |

- **1 槽字段共出现 26 个 k**：`k=0`(450 次，每个技能都有)、`k=3`(450)、`k=5`(447)、`k=7`(373)、`k=13/14`(各 285)、`k=20`(189)、`k=70`(251)、`k=79/80`(各 74) 等。「每技能必有」的 `k=0`、`k=3` 最可能是**类型 / 分类**一类的必填属性。
- 余下 ~10%（481 条）是**更多按技能多槽的二维子数组**（如 id=251.. 处 stride 4 的 `0x6d7ee6` 段、id=301.. 处 stride 3 的 `0x6d6712` 段），**槽宽未逐一确认**。
- **`1000` 再次出现**为字段间 stride，与 §1 的技能 id 容量、掉落表的单位 id 容量一致，佐证「引擎按 1000 容量开静态数组」的惯例。
