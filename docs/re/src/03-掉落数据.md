# 掉落数据结构（src / data）

> 级别：**已确认**（data/EBINIT.txt 静态表 + UNITECH/COMMITBTL/REWARD 脚本实证 + 运行态 dump）。
> 跨域桥接：引擎侧运行时数组见 `docs/re/engine/04-引擎侧运行时数组.md`。

## 1. 单位 id 与掉列表索引（已确认）

- 单位名地址即单位 id 的来源：`unitId = 名字串地址 − 0x17ab6`；首个掉落单位 `0x17b42 → unitId=0x8C=140`。
- 掉落表（每单位**最多 5 槽**，用 `unitId×5 + 槽位` 索引）：
  - `item_addr = 0x53cd7c + unitId×5 + 槽`
  - `rate_addr = 0x53e104 + unitId×5 + 槽`
- **不匹配 = 0 / 203**，unitId 范围 140..750（十进制）。这是「按 unitId 直接算出位置、无需索引指针」的**第 1 种**模型（有上限 5，位置可算）。
- 追加包单位 id 更大 → 同一公式自然落到更高地址（基础版在 `0x53e…`，追加 `$n$` 越到 `0x53f…`）。

## 2. `rate` 的字段分布（已确认：不是单个值域，而是 0–100 百分制刻度）

用 `scripts/re/extract_global_data.ps1` 全量导出 global 表，对 rate 区 `[0x53E104..0x53F48C)` 的 **990 个非零 rate** 分布（值：计数）：

| rate | 1 | 2 | 3 | 5 | 10 | 15 | 20 | 25 | 30 | 35 | 40 | 50 | 60 | 75 | 100 | 200 | 300 | 500 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 计数 | 5 | 5 | 25 | 147 | 92 | 30 | 96 | 8 | 136 | 3 | 18 | 134 | 11 | 3 | **272** | 3 | 1 | 1 |

- `100` 最多（272 槽）；**<100 共 713 槽**；`200/300/500` 仅 5 槽。
- item/rate **严格配对**：整个掉落区 `[0x53CD7C..0x53F48C)` 内 item 索引 947 个、rate 索引 990 个；**空闲 / 战斗 / 掉落瞬间三次导出该区零变更** → 是**静态数据**（启动时从 `EBINIT` 载入），不是运行时量。多槽单位带**递增 rate**（如 unit 500: `710/10, 614/15, 667/25, 626/50, 685/100`；unit 750: `522/5, 521/20, 304/30, 511/50, 504/100`）。

## 3. `rate` 的工作原理（**本次澄清**，已确认自 COMMITBTL）

`rate` 有**两条不同语义路径**，之前文档把二者混为一谈，这里拆清：

### 3a. 战斗掉落路径（COMMITBTL）—— rate 是**概率刻度**

掉落触发调用链（脚本级 call-script，全部已确认）：

```
SYSTEM4(L441) → FIELD(5267) → BTL(511f) → COMMITBTL(399e) → REWARD(39a2)
                                                          → ADDITEM(77a) 进入背包
```

即 **FIELD - BTL - COMMITBTL - REWARD**。掉落判定集中在 `COMMITBTL`，分两步：

**(1) 候选槽门控（COMMITBTL L253-259）—— 实际退化为 `item > 0`：**

```
253: item = item_arr[0x53cd7c + b*5 + slot]
254: gr (item > 0)
255: X    = 0x53f48c[b*5 + slot]
256: Y    = 0x928a7[c]
257: lte  (X <= Y)
258: and  (item>0) AND (X<=Y)   → 候选门
259: 不满足则跳过该槽
```

- **关键结论**：`0x53f48c` 区段（`[0x53f48c, ...)`）数据**按 0 处理**，遍布脚本/数据层**未观测到任何赋值逻辑**，怀疑是 AGE 引擎**通用逻辑**，**本项目未使用**。⇒ `X = 0` 恒成立，`X <= Y` 恒真，**门退化为 `item > 0`**。
- `0x928a7` 的 `Y` 因此**不影响掉落判定**；其运行态被填充（详见 `engine/04`）但不左右结果。

**(2) 概率抽取（COMMITBTL L339-346）—— 真实判定：`RNG < rate + 0xa3578`：**

```
339: RNG = rand_pool[0x5697a + 61c73*0x14 + (5b8af % 0x14)]   ; 从 FIELD 初始化的随机池抽一个（stride 0x14=20，计数器 %20）
340: global[0x5104a3] = RNG
341-342: 5b8af = (5b8af + 1) % 0x14                ; 每次 roll 前进计数器（%20）
343: rate  = rate_arr[0x53e104 + b*5 + slot]
344: thr   = rate + global[0xa3578]                ; 阈值 = rate + 掉落加成
345: if (RNG < thr) → 掉落                                    ; 否则该 roll 落空
```

- 随机池 `rand_pool` 基址 `0x5697a`（**1000 项 = 0x32×0x14 = 50 行×20 列**），**值域 0–99**（`random 0x64` = `rand()%0x64` = `%100`，运行态实测一致）。它在 **FIELD** 里用**嵌套循环 + `random` 指令批量填充**（见 §3c），不是靠逐条手工写。
- `0xa3578` 是**掉落率加成**（全局量），加到阈值上 → 掉落率 `P = clamp(rate + 0xa3578, 0, 100)/100`（RNG∈[0,99]）。其来源未确认（推测：幸运/难度/装备等，见 Todo）。

**(3) 数量（COMMITBTL L347-367）—— 不是 `rate/100`：**

```
347-348: item = item_arr[b*5+slot]; e = item
349-350: f    = 1 + global[0xa357d]               ; 掉落数量
351-354: if (0x62d72[9*0x3e8 + 0x63]) f *= 2     ; 翻倍旗（stride 0x3e8）
356-358: 6ff603[item] += f                        ; 物品计数
359-364: if (rate <= 5) 7005a3[item] += f         ; 低概率槽额外记一笔
367:     701543 += f                              ; 累计掉落总额
```

- **掉落路径的数量是 `1 + 0xa357d`，并非 `rate/100`**。`0xa357d` 与 `0xa3578` 紧邻，同属「掉落修正」一组全局量（来源未确认）。

**§3a 行为小结（战斗掉落，COMMITBTL）**：

| rate `N` | 概率 | 掉落数量 |
|---|---|---|
| `N < 100`（`0xa3578`=0） | **`N%`**（`RNG<N`，RNG∈0–99） | `1 + 0xa357d`（通常 1，翻倍旗×2） |
| `N >= 100`（`0xa3578`=0） | **必掉**（`N≥100` 恒真） | **仍是 `1 + 0xa357d`（≈1），不是 `round(N/100)`** |

- 若 `0xa3578`（掉落率加成）> 0，概率整体上浮：`P = clamp(N + 0xa3578, 0, 100)/100`；`N>=100` 段只决定"必掉"，**不决定数量**。
- **结论**：`rate` 在**战斗掉落**里纯粹是**概率刻度**（0–100，≥100 即必掉）；**`round/floor(N/100)` 的数量语义只在 UNITECH（单位加入）路径**，**不**适用于战斗掉落。
- 说明：`N > 100` 的数据槽（如 200/300/500，多为 BOSS 专属）在战斗掉落里就是"**必掉的专属物**"，数量仍走 `1 + 0xa357d`，并非"掉 2/3/5 个"。

### 3b. 单位加入路径（UNITECH）—— rate/100 作为**自动发装备数量**

`UNITECH.txt` L267-270（单位加入/合流时自动发放其掉落表装备）：

```
267: item = item_arr[0x53cd7c + unitId*5 + slot]
268: global[546e03] = item
269: rate  = rate_arr[0x53e104 + unitId*5 + slot]
270: global[546e04] = rate / 100               ← 数量 = rate/100
271: call-script 77a  // ADDITEM
```

- **`rate/100` 只对 `≥100` 成立**（`div` 是**整数除法=floor**：100→1 个、150→1、200→2 个…）；`<100` 那批 `rate/100`=0。
- 因此 `rate` 在**战斗掉落**里是概率刻度（§3a），在**单位加入**里兼作「保底数量」。二者是**并存的两种用法**，前面的文档误把 UNITECH 的数量语义当成了掉落主路径。

### 3c. 随机池的初始化（FIELD，**已确认**：嵌套循环 + `random` 指令填充；保存/载入走 `memcpy`）

> ⚠️ **src 汇编字面量是 16 进制**：`64`=`0x64`=100、`32`=`0x32`=50、`14`=`0x14`=20。下面已换算。

**① 池的填充（FIELD `L10480-10498`，嵌套 50×20 循环）—— 真正的「初始化逻辑」：**

```
L10481: lt (3007) 0x32               ; 行 0..49（0x32=50）
L10483: mov (2fcf) 0                  ; 列 0
L10490: lt (2fcf) 0x14                ; 列 0..19（0x14=20）
L10492: lookup-array-2d (ptr 3) 0x5697a (3007) 0x14 (2fcf)  ; ptr = &pool[行][列]，stride 0x14=20
L10493: random (ptr 3) 0x64            ; *ptr = rand() % 0x64  → 值 0..99
```

- **是 `random` 指令逐条填**（每项 `rand()%100`），**不是** `memcpy` 批量拷入。⇒ 回答「是 random 指令还是有批量初始化指令」：**是 `random` 指令（嵌套循环逐项填充）**。
- 池 = **1000 项 = 50×20**（`0x5697a` 基址，`[row*0x14 + col]`，row∈[0..49], col∈[0..19]）。
- **值域 0–99**：`random` opcode（0x60, `sub_42CA50`）语义 = `param1 = rand() % param2`，`param2=0x64=100` ⇒ `0..99`。与运行态实测 0–99 一致。

**② 保存 / 载入（FIELD `L12188-12189` / `L12383-12384`）—— 状态持久化：**

```
L12188: mul (819f) 0x32 0x14          ; 1000 = 0x32×0x14
L12189: memcpy (0x5697a) (0xeafe5) 1000   ; 读档：从保存区拷 1000 项入池
L12342: mov (0x5b8af) (0xa8b85)           ; 读档：恢复计数器（0xa8b85 为保存区）
L12384: memcpy (0xeafe5) (0x5697a) 1000   ; 撤退：把池写回保存区
```

- **读档/撤退用 `memcpy`**（赋值 opcode 0x1B0，批量内存拷贝），把池状态与计数器在「保存区 `0xeafe5`/`0xa8b85`」与运行时 `0x5697a`/`0x5b8af` 之间搬运 ⇒ **确定性/可复现的随机序列，随存档同步**（sl 重读 rand 序列一致）。

**③ 掉落后的局部重填（COMMITBTL `L393-394`）：**

```
L393: lookup-array-2d (ptr 0) 0x5697a (61c73) 0x14 (i)   ; i = 0..19
L394: random (ptr 0) 0x64                                 ; *ptr = rand()%100  → 0..99
```

- **含义**：它刷新的是**本轮 COMMITBTL 抽取 RNG 所用的那一行**——`0x61c73`（battler 槽索引）这一行的 **20 项**全部重随机为 0–99。掉落判定 L339 读的正是**同一行 `0x61c73`**；且 BTL/CALCDMG/CALCILL 战斗全程也用 `0x61c73` 那行做伤害/暴击 RNG（`pool[0x61c73*0x14 + (5b8af%0x14)]`）。⇒ 即「battler `0x61c73` 那行 20 个值用完即 refresh」，供下一场战斗取新数。
- **它每次 COMMITBTL 都执行**（在 L383 `label_00001ba4` 公共出口，跟是否掉落无关）。
- **⚠️ 措辞修正**：这里**不是**「按被击杀单位定行」，而是固定用全局 battler 槽 `0x61c73` 取行——与掉落取自哪个单位（`b`）的 item/rate 表**无关**。`0x61c73` 是否语义上恒等于"被击败方"待核实（见 §5 Todo）。
- **⚠️ 值域修正**：此前把 `random 64` 误读为 `%64(0..63)`；实际 `0x64=100`，故与主池 0–99 一致，**无值域差异**。

**「整场用哪一行」的模型**：**整场战斗的 RNG 固定取行 `0x61c73`**（BTL/CALCDMG/COMMITBTL 三处实读同一行），**不是随机选行**——`0x61c73` 在**战前/行动解析时被赋值**（FIELD/SELACT/ADDEN 等 `mov (global-int 61c73) …` 多处写，DEBUGBTL 设为 `0xa`）→ 它指向**本次解析对应 battler 的那一行**。行内取值通过**共享、跨场不重置**的计数器 `0x5b8af` **环形取用**（`+1 % 0x14`，一路从 BTL/CALCDMG/COMMITBTL/CALCILL 递减前进）：即「**选定一行 → 环形掏出 20 个值之一 → 战斗结束整行重随机**」。

**计数器的行进**：`0x5b8af` 在每次抽取后 `+1 % 0x14`（COMMITBTL L341-342、BTL、CALCDMG、CALCILL 同款），**全局共享**、跨战斗持续前进、不重置；故不同场次从同一行的**不同列偏移**开始取，同场次内超过 20 次抽取则环形复用这 20 个值。

**④ 回答「每次战斗开始的重置」**：**没有**对整池逐场战斗开始时重填的逻辑。全工程对 `0x5697a` 的写入只有三处：①FIELD 进入时序的种子循环、②FIELD 读档/存盘的 `memcpy`、③COMMITBTL **每次结算**仅重填 `0x61c73` 那一行（非按被击杀单位定行）。整池只在 **FIELD 进入时序**种一次（①），战斗内**只局部重填**（③）；计数器 `0x5b8af` **跨战斗累积不重置**。⇒ 掉落的"随机性"来自「首场前的 0–99 全池 + 每场结算对 `0x61c73` 行重填 + 无重置的旋转计数器」，是**确定性可复现**序列。
> STAGEROUND/ADDEN 等处的 `random ... 0x100`(=`rand()%256`) 走的是**引擎自带 RNG**（敌人/事件抽取），与本池**无关**，不要混为一谈。

## 4. 掉列表是「1000 单位容量」的连续数组（关键联系，已确认）

- `0x3e8 = 1000` = **单位 id 上限（数组容量/维度）**，来自引擎里二维索引的 stride=0x3e8（`COMMITBTL` 的 `... 62d72 ... 9 3e8 63`、`UNITECH` 的 `... 546e02 3e8 ...` 都以「单位 id(0..1000)」为第一维）。
- 掉落表整块连续：`item[0x53cd7c, 0x53e104)` + `rate[0x53e104, 0x53f48c)`，各 1000×5=5000 槽。
- **`0x53f48c = 0x53e104 + 5×1000`**（严格成立）→ 它是 **id=1000（单位上限/边界）** 的 rate 基址；**也是下一段（随机判定/引擎通用区）的起点**。该区段按 0 处理（§3a），项目未用。
- 最大静态 rate 写入是 **`0x53f486`**（≈ id 998）；id 999/1000 的槽在容量内但**无数据**。

## 5. 文件扫描提取法（`extract-unit-drops.js`）与统计（早期工具，与 §1 等价）

> 早期（合并自 `docs/单位掉落物.md`）用「按单位块扫描文件」的方式提取掉落，与 §1 的「`unitId×5+槽` 语义模型」**是同一份数据的两种表述**：
> - **语义模型（§1）**：`item_addr = 0x53cd7c + unitId×5+槽`、`rate_addr = 0x53e104 + unitId×5+槽`（**权威索引**）。
> - **扫描启发式（本节）**：item mov 落在 `0x53d000` 页、rate mov 落在 `0x53e000` 页，页内偏移随单位漂移，两两配对（rate 在前、item 在后），相邻对各 +1（双游程）。
> 两者吻合：首个掉落单位 `0x8c`(140) → `0x53cd7c + 140×5 = 0x53d038`（正好=启发式观察到的 `這竜リムドラギル` … 等页内漂移起点类）。

### 5a. 单位块分界
`EBINIT.txt` 由 **243 个怪物/敌人单位块**组成，每块以**相邻 set-string 对**开头：`set-string (global-string 17b..17e) "名字"`（名字串 `0x17a00..0x17eff`），紧接 `set-string (global-string 17f..181) "副标题/阵营/种族"`（`0x17f00..0x181ff`）。判据 = **名字串地址 < 副标题串地址** 且两条连续。可玩角色名册（名字 `17a` + 副标题 `17e`）无掉落表，自然排除。

### 5b. 掉落表扫描判据
| 判据 | 规则 |
|---|---|
| **item 地址** | 页基 `0x53d000` 固定，页内偏移随单位漂移（`0x53d038`…`0x53d858`…`0x53dc26`）→ `(addr & 0xffff000) === 0x53d000` |
| **rate 地址** | 页基 `0x53e000` 固定，页内漂移（`0x53e3c0`…`0x53ebe0`…`0x53ede8`）→ `(addr & 0xffff000) === 0x53e000` |
| **配对** | 每条 rate 紧跟其 item（rate 前、item 后），相邻两对的 rate/item 地址各 **+1**（双游程） |
| **边界** | 游程后紧跟一条 `51xx/52xx` 数据指针行 |

**❌ 常见误判**：`4xxx` 尾不是必要判据（多数尾 `45xx/4xxx`，但有 `396x/397x`、`16xx/1761`（BOSS 单体掉落））；item 前缀不是 `53d1xx`（页内偏移随单位漂移，只锁页基 `0x53d000`，如 `這竜リムドラギル` item 在 `53d858~53d85b`）。

### 5c. 统计（`data/EBINIT.txt`，`scripts/extract-unit-drops.js` → `metadata/unit-drops.json`）
- 单位块数 = **243**（敌人/怪物），含掉落表 = **203**，不含 = **40**（无掉落剧情/纯敌人）。
- 全文件 `53dXXX` item mov 行 = **648 条**，输出捕捉 **648 条**（0 缺失、0 重复）；去重后掉落物品 ≈ **252 种**。
- 掉落条目数分布：1条:67 单位 / 2条:4 / 3条:15 / 4条:57 / 5条:60。**单体（1 条）多为 BOSS/独特单位**，率恒 `100`（专属/必掉）。
- 单位块内 `53c66x` 等行属块内其它字段，非掉落物。

**抽查**（`狂える男`=金のメダル(5)/勇壮の水・小(10)/壊れた刀(20)/銀のメダル(30)；`這竜リムドラギル`=刃這竜の血液(10)/皮(20)/牙(40)/爪(100)；`重聖堂騎士`=騎士の証(5)/火槍ルナグレイプ(5)/治癒の水・特大(10)/大(20)/小(50)；`地の大魔術師`=地割れの魔法書(5)/勇壮の水・大(10)/破れた研究書(30)/解魅の粉(50)）。

> 注：`unitId` 在 `unit-drops.json` 里为「名字串地址（十进制）」（如 `0x17b6c` = 狂える男 = 97132），与 §1 的「`0x17ab6 + id`」是**同一条单位名的两种 id 表示**（`0x17ab6 + id = 名串地址`）。
