# 引擎侧运行时数组 `0x53f48c` / `0x928a7`（engine）

> 级别：**部分已确认**（运行态 dump 实证）/ **仍未解**（X/Y 确切取值语义）。
> 它们与掉落门控的语义/使用见 `docs/re/src/03-掉落数据.md`（跨域桥接，主归属 src）。
> 运行态 dump 工具：`scripts/re/extract_global_data.ps1`。

---

## 1. 它们是「数组区段基址」，不是单个量（本次澄清，已确认自 COMIMITBTL 脚本）

`COMMITBTL.txt` 第 253-258 行实读：
```
253: item = global_int[0x53CD7C + b*5 + slot]
255: X    = global_int[0x53F48C + b*5 + slot]   ; b、slot 为运行时值
256: Y    = global_int[0x928A7 + c]              ; c = global_int[0x52AC6C][b]
257: 1e   = (X <= Y) ;  258: 1f = (item>0) AND (X<=Y)  → 掉落门控
```
⇒ **`0x53f48c`、`0x928a7` 本身是"数组区段基址 index"，其值 X/Y 在偏移 `+b*5`/`+c` 处**。因此在空闲/战斗 dump 里把这三处当作"单值"读到的都是 0 —— 这是预期，不代表无数据。

---

## 2. 运行态 dump 实测（三次对比，已确认）

用 `scripts/re/extract_global_data.ps1` 分别导出：空闲 → 战斗存档 → 掉落瞬间（COMMITBTL 附近，物品已掉），差异如下：

- **`global_int_base`/`key` 三次完全一致**（对象稳定）：`int=0x41007700`、`key=0x221D01E6`（带壳进程 `AGE.EXE`）。
- **掉落表（`0x53CD7C..0x53F48C`）三次零变更** → item/rate 表是**启动时从 `EBINIT` 载入的静态数据**（`03-掉落数据.md` §1 的判断坐实）。
- **游戏状态标志**大量变动（空闲 vs 战斗 vs 掉落瞬间各差 ~1.2–1.4 万索引），与掉落无关。

### 关键：Y 数组在掉落瞬间被填充
- **Y 数组 `[0x928A7 .. ~0x9345F]`（= `0x928a7 + c`）在掉落瞬间出现 224 个非零 per-unit 值**（如 `0x92D2A:12`、`0x92D6B:38`、`0x92D89:17`、`0x92D8A:27`…）。空闲/战斗时该区全为 0，掉落时才写入 ⇒ **这就是引擎运行时维护、脚本/数据/存档都无法静态定出的那部分**。
- **X 数组 `[0x53F48C + b*5]` 与 `0x546E04` 区仍是 0** → 更可能是**掉落循环内瞬态**（置位/清除很快），快照落在其被清后。

## 3. 仍未解（继续）

- **X/Y 的确切取值语义**：Y 数组看起来是"每单位判定量"（单位属性/随机/计数？）；X（`0x53f48c+b*5`）为何在快照里为 0（是瞬态清掉，还是另有来源）。
- 两条出路：
  1. **掉落瞬间 hook**：在写到 `0x53F48C+b*5` / `0x928A7+c` 的指令（或 `sub_42B4B0`、`lookup-array`(0x61)/`lookup-array-2d`(0x12C) handler）下断，抓当前 `b/c/slot` + X/Y + item，一次定死 `X<=Y` 比的是什么。
  2. **引擎 xref**：在 `.lst`/IDA 对这两个**真实地址**（`global_int_base + 0x53f48c*4`、`+0x928a7*4`）做 xref，找写它们的引擎函数，看以何值填入。
