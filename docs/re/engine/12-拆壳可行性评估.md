# 拆壳可行性评估（AGE.EXE @ ASProtect）

> 级别：**已确认**（PE 实测）＋ **推测**（路径取舍）。
> 评估对象：`raw/AGE.EXE`（1,007,104 B，ASProtect 加壳引擎本体）。
> 结论形成于 2026-xx（本机 mac 环境，无 Windows）。

> ⚠️ 勘误（对 `01-加壳与拆壳.md` 的补充）：`01` §1 称「`天结.exe` 同样仍是 ASProtect 壳」。据实测修正 —— **`天结.exe` 用的是另一种壳（非常好拆）**，不是 ASProtect。但**壳不同只影响拆壳方式，不影响引擎本身**：AGE 与天结的核心进程是同一个，只是对个别场景（如系统编码适配）做了修复。故「拆天结」**不能**作为「拆 ASProtect AGE」的通用先例。

---

## 0. 一句话结论

- **「纯静态 trace ASProtect 壳的启动逻辑来理解加壳、进而拆开」——可行，但不是好路径（高努力、低确定性）。**
- **「得到一份干净的 AGE.EXE 引擎」——可行，且比想象容易得多。** 真正的杠杆不是逆壳代码，而是已有资产：
  **同引擎的无壳姊妹件（`天结_unpacked.exe`）＋ 完整反汇编（`engine/*_utf8.lst`/`.c`）＋ 已知 IAT/节布局（OEP 无需假设、靠运行时观察）＋ 运行时在位读取能力（amayui-inspector 已实证）。**

## 1. AGE.EXE 的 PE/壳实测（本次重新核对，确认 ASProtect）

用 `objdump -x` + Python 复析：

| 项 | 值 | 含义 |
|---|---|---|
| ImageBase | `0x400000` | 与已知引擎一致 |
| EntryPoint(RVA) | `0x1000` | 只是 **ASProtect stub**，非 OEP |
| SizeOfImage | `0x26F000` | 运行时镜像大小 |
| SectionAlignment / FileAlignment | `0x1000` / `0x200` | 标准 |
| 节 | 共 8 节，**全部 `0xE0000040`（读+写+执行）** | 壳特征 |
| `.text`（节0） | `VAddr=0x1000 VSize=0x11C000`，熵 **8.000** | 压缩/加密代码，长度与 `天结.exe` 一致 |
| 节1 | `VSize=0x33000`，熵 **7.997** | 加密 |
| `.rsrc` | `VSize=0x4E000`，熵 6.803 | 加密资源 |
| 节4 / `.adata` | **零文件节**（`RawSize=0`：节4 `VSz=0x11000`，`.adata` `VSz=0x1000`） | BSS/RESERVE，运行期由壳填充 |
| 导入目录 | RVA `0x1C1A60` 落在 `.data`（非 `.idata`），熵 4.157 | **诱饵 IAT** |
| 导出目录 | RVA `0x1C0000`，熵 **5.937**（`NumberOfFunctions` 荒谬） | **垃圾/高熵导出** |
| 入口桩 | `68 01 10 5C 00`(push 0x5C1001) `E8 01 00 00 00`(call over) `C3 C3` 后接高熵 | ASProtect 1.x 风格入口 |
| 无 overlay | 文件尾 = 最后节 raw 终点 `0xF5E00` | 纯引擎本体 |
| 特征字符串 | ASProtect/UPX/Themida/VMProtect/MPRESS **全部 0 命中**（串已清/加密） | 典型 ASProtect |

> 结论：与 `docs/re/engine/01-加壳与拆壳.md` 的判定一致，**确认 ASProtect**。

## 2. 关键洞察：带壳运行时的镜像布局 == 已知无壳引擎

**证据链（叠加确认）：**

1. **打包档预置 VA 空间**：打包档的节 `VSize` ＋ 零文件节预留，使解包后的引擎落在与已知引擎**相同 RVA** 上。
   实测：入口桩 `.text` 区间 `0x1000..0x12C000` 能容纳 OEP `RVA 0xEDBDE`；已知无壳引擎 `.idata VA=0x1B0000` 正好落在打包档**零文件节4** 的 `0x1AF000..0x1C0000` 内。
2. **amayui-inspector 的 `dispatch_signature.json`**：以 `RVA = VA − preferred_base(0x400000)` 为指纹（handler VA 如 `0x418E30`、`0x42C6E0` …，与已知 `sub_*` 一致），**在带壳 AGE 上按 `module_base+RVA` 一次命中** `this`（本机 `0x2FDC020`），并 DEC 解码全局表、读帧栈 —— 全部正确。
3. **结论（已确认）**：带壳 `AGE.EXE` 运行时，其引擎镜像的**各段 VA 布局、dispatch 函数指针表、handler 地址、OEP 与已知无壳引擎一致**。壳只是在运行期把整个引擎**完整解压到内存**。

## 3. 为什么「静态 trace 壳」不是好路径（要诚实说明）

即使目标只是「理解它是怎么加壳的 / 找到 OEP」，纯静态（不执行）对 ASProtect 也不划算：

- **自修改 / 自解密 / 多态**：stub 是分阶段自解密代码，反汇编与执行行为不一致（它写自己）。静态 `objdump` 看不出执行真相。
- **2.x / SKE 可能带虚拟机（mutation）**：部分代码被「虚拟化」，逐行静态 trace 无意义，得先逆 ASProtect VM（极大工程）。
- **反调试 / 反 dump / 自校验**：会检测调试、重保护、卸载等。
- **磁盘 IAT 是诱饵**：真实导入只在运行期构造；**仅凭文件得不到真实导入**。

→ 「纯静态自底向上从零拆壳」：**高努力、低确定性**。不推荐作为主路径。

## 4. 关于 OEP 是否固定（关键方法论问题）

> 你问得很对 —— 这决定路径能不能「顺手」：**OEP 不是壳决定的，是原程序链接期就定死的**。

**OEP 的本质**：它是**原程序 PE 头里的 `AddressOfEntryPoint`**（本例 = MSVC CRT 的 `start` 例程，RVA `0xEDBDE`，仅 10 字节，位于 `.text` 尾部、紧邻 `_printf`/`___tmainCRTStartup` = CRT 区）。打包器只是把这个值**记下来、解包后跳过去**。所以：

| 问题 | 答案 | 说明 |
|---|---|---|
| **同一个带壳二进制，每次运行时 OEP 是否总在同一位置？** | **是（已确认）** | OEP 是原程序头里的常量，ASProtect 解包后**确定性**跳转；不随运行随机化。 |
| **两个「相关但不同」的二进制（AGE vs 天结）OEP 是否保证相同？** | **否（按构造不保证）** | OEP 是各自编译产物的属性，只在「代码布局一致」时相同。 |
| 何时会相同？ | 若改动是**就地补丁**（在既有函数内改字节，不重链）→ 布局不变 → OEP 相同。 | 文档判定 `天结_unpacked.exe` 的改动在文字渲染层（GBK/SJIS），若为就地 patch 则 OEP 保持不变。 |
| 何时会不同？ | 若改动是**重新编译/重链**（插入/删除函数、改函数大小）→ 链接器会重排所有 contrib，CRT 区整体后移/前移 → `start` 的 RVA 变化。 | 这会让 RVA `0xEDBDE` 失效。 |

**结论（已确认＋推测）**：`0xEDBDE` 是**强假设**，不是给定值 —— **必须验证，不能直接写死**。这也是本方案对 OEP 的定位：**观察/交叉校验，而非硬编码**。

## 5. 推荐路径（按可靠性排序）

### 路径 A（推荐）：运行时提取 + 已知布局重建可加载 PE

因为 amayui-inspector 已证明 `ReadProcessMemory` 能**无损读带壳 AGE 的整个引擎镜像**（找到 `this`、解码全局、读帧栈），且我们有 ground truth，所以能把「OEP 未知、IAT 未知」这两个拆壳最难的点**全部消解**：

1. 在 Windows 上正常启动 `AGE.EXE`，停在其引擎已初始化的状态（进主菜单即可）。
2. 读取 `module_base + SizeOfImage(0x26F000)` 全量字节（分块 ReadProcessMemory，INSPECTOR 已有现成 `MemoryScanner` 可复用/扩展）。
3. 用**已知布局**重建可加载 PE：
   - 节表按已知结构（VA/尺寸与无壳引擎一致；raw 数据用 FileAlignment `0x200` 排布，`SizeOfRawData = align(VSize,0x200)`）。
   - **IAT 重建**：运行时 IAT 存的是已解析函数指针 → 按已加载模块导出表把每个地址解析回「DLL + 函数名」，生成真实 `.idata`。因知道无壳引擎导入列表（见 `01` §3：`kernel32/user32/gdi32/d3d9/d3dx9_43/mfplat/winmm/ole32/imagehlp/advapi32/version/shell32/shlwapi/imm32/oleaut32/evr/dxva2`），可做**校验/兜底**。
   - **EntryPoint 用「运行时实际观察到的 OEP」，而非写死**：首选**字节签名扫描**（见「路径 A-1」，扫无壳样本 OEP 区字节，命中处即 OEP；不需要调试器）；次选调试器在**壳→OEP 交接点**拦截（run-to-OEP / 内存执行断点 / 检测壳尾跳入原 `.text`）。已知 RVA `0xEDBDE` 只作**对称交叉校验**：观察值 ≈ `0xEDBDE` ⇒ 证明引擎布局与 `天结_unpacked.exe` 一致；不同 ⇒ 说明 AGE 被重链过、引擎确有差异（这个差异本身是信息）。
   - 可选：把节特性还原为正常（`.text=R+X`、`.data=RW`），去掉 RWX 残留。
4. 验证：产物应能加载，且 VM 核心 / 全局数组布局 / 掉落逻辑与 `天结_unpacked.exe` 一致；可与 `engine/*_utf8.lst` 反汇编交叉核对。

> 要点：**拆壳的「未知」只有 IAT 需要真正构造**；**OEP 永远可以靠运行时观察得到**（不需要假设某固定值）。如果**只为读引擎内部**，OEP 甚至不重要 —— 你有整块镜像即可反汇编（IDA/Ghidra 按 base 载入），不需要先得到一个「能双击运行」的 exe。

### 路径 A-1：OEP 定位 —— 字节签名扫描（首选，优于 run-to-OEP）

**原理**：本引擎**不自修改代码**（只有壳的 stub 做解密；引擎是静态解释器）。⇒ 一旦引擎**完整驻留内存**，镜像即**稳定** —— 「dump」并不需要卡在壳→OEP 交接那一刻；交接点只是「解包完成 + 引擎驻留」的**最早且最确定**的标记，**不是唯一可提取点**。据此，可直接用**无壳样本 OEP 区的字节**在**已驻留**的带壳进程内存里做**滑动模式匹配**，**强行定位真实 OEP**（业界成熟的 OEP pattern/signature scan）。

```
1. 定位 AGE 进程，module_base = 0x400000
2. 读 .text 区（module_base+0x1000 .. +0x11C000，宽 = .text VirtualSize 0x11C000）
3. 载入「无壳样本 OEP 处字节」作为签名（见「签名来源/健壮性」）
4. 滑动扫描 → 命中偏移 offset ⇒ OEP_RVA = 0x1000 + offset
5. 交叉核对：命中在 0xEDBDE 吗？
     └ 是 ⇒ AGE 与天结引擎【同版】（最硬证据），OEP 取 0xEDBDE
     └ 否 ⇒ AGE 被重链过，那个命中 RVA 就是 AGE 的真实 OEP（差异本身是信息）
6. 之后照常 dump → 重建节表 → 重建 IAT → EntryPoint 设为命中的 OEP
```

**为什么优于 run-to-OEP**：不需要调试器、不踩反调试、不卡交接点；可在进程**深跑进解释器**（正是 amayui-inspector 已在读的状态）时纯 `ReadProcessMemory` + 比对，与被证明可用的读取管线完全一致，**风险最低**。

**三个必须注意：**

- **时序**：必须等引擎**驻留后**再扫（否则 OEP 区还是壳的密文）。用 inspector 已有的「引擎驻留」信号（命中 dispatch 指纹 / 读到 `this` + 全局）作为「可扫」前提。
- **签名健壮性**：`start` 例程仅 ~10 字节太薄，应**加宽**为一段**稳定 CRT 邻区**（`___tmainCRTStartup`(0x4EDA71) 调用 + `_printf`(0x4EDBE8) 附近，约 `0x20–0x50` 字节）——这些是**编译器/CRT 生成代码**，比游戏代码稳定得多，几乎零误报（32 字节 blob 随机碰撞 ≈ 10⁻⁷⁷）。
- **签名来源**：`天结_unpacked.exe` 本体不在这台 mac，且 `.lst`/`.c` 里该函数是 collapsed（无原始字节）。签名字节需**从无壳样本提取**（取 OEP `0x4EDBDE` 起 `0x20–0x40` 字节；或展开 IDA 里 collapsed 的 `start`）。

**再加一层保险（双证据）**：inspector 的 **dispatch 指纹**命中本身即证明引擎布局与已知一致（`this` + handler VA 对得上）。把「dispatch 指纹命中」+「OEP blob 命中在 `0xEDBDE`」**双证据**都用上，即可**确定** AGE 与天结同版、OEP 已知。

> 边界提醒：**签名扫描只解决「OEP 在哪 / 确认解包完成 + 同版」**。要得到可加载/可运行的干净 exe，仍需 `dump(已驻留镜像) → 重建节表 → 重建 IAT → 设 OEP`（IAT 重建是必须做的，跑 Scylla 或自建工具皆可）。

### 路径 B：真正解码文件内载荷（无运行时，纯静态）

需逆 ASProtect 解压缩/加密算法并用模拟器执行 stub 解密循环 —— 就是 §3 的硬骨头。**只在极特殊需求**（在意打包档与内存镜像的字节级差异、想脱离 Windows 得到文件）才值得。

## 6. 最该先做的一步：判定 AGE 与 天结 引擎是否同版

这是前置却最有价值的一步。注意：**`天结.exe` 用的是另一种壳（好拆），不代表其引擎与 AGE 不同** —— 壳不同只影响「拆壳方式」，不影响「引擎本身」。

- 用 amayui-inspector 在**各自运行时**分别采 dispatch 签名 / 全局数组基址 / key / 字符串，与已知值比对（A/B 校验）。**顺便在 AGE 上抓一条真实 OEP**（见 §5「路径 A-1」字节签名扫描），与 `0xEDBDE` 比对 —— 这是**判定是否同版最硬的静态证据**（dispatch 指纹 + OEP blob 双命中即定版）。
- **若同版**（`0xEDBDE` 交叉校验命中，且 dispatch/全局一致）：
  - 对**改数据文件**、**读引擎内部**（`0x53f48c`/`0x928a7`/`0x53e104`/`0x53cd7c`/`0x52a0b5`…）这些下游目的，**`天结_unpacked.exe` 反汇编已够用，无需重新拆 AGE**（见 `01` §2）。
  - 新拆 AGE 的唯一新增价值：拿到**原版未改**的引擎镜像（`天结_unpacked.exe` 被改过文字渲染层，如 GBK 非 SJIS，且 `天结.exe` 壳不同、可能引入 overlay 差异），用于干净的引擎层工作。
- **若不同版（观察到的 OEP 明显 ≠ `0xEDBDE`，或全局布局/签名对不上）**：路径 A 立即变成刚需，务必执行。

## 7. 平台注意

- **本机（macOS）**：可做全部静态部分 —— PE 解析、节/IAT 分析、IAT 重建工具脚本、与 `*.lst` 反汇编比对、同版判定脚本。
- **运行时提取**：需在能跑 `AGE.EXE` 的 Windows 环境（即跑 amayui-inspector 的那台机）。本机无法直接 run+dump。

## 8. 结论（分事实度）

| 判断 | 事实度 | 说明 |
|---|---|---|
| AGE.EXE 是 ASProtect 加壳 | **已确认** | PE 实测（本节 + `01`） |
| 壳在运行期把整个引擎解压进内存 | **已确认** | amayui-inspector 在带壳进程上按 RVA 指纹命中 `this` 并正确解码 |
| 带壳 runtime 引擎布局 == 已知无壳引擎布局（VA/dispatch） | **已确认** | RVA 指纹匹配 + 打包档预留 VA 空间 |
| **同一个带壳二进制每次运行 OEP 位置固定** | **已确认** | OEP 是原程序头常量，ASProtect 确定性跳转 |
| **AGE 与 天结 的 OEP 是否必相等** | **否（按构造不保证）** | 取决于改动是就地 patch（布局不变）还是重链（可能移位）；`0xEDBDE` 只是强假设 |
| 「纯静态 trace 壳」是好路径 | **推测：否** | 见 §3 |
| 「运行时提取 + 已知布局重建 PE」能得干净 AGE 引擎 | **推测：可行** | 复用 INSPECTOR 读内存 + 已知 IAT/节布局；OEP 靠运行时观察；需 Windows 跑 |
| AGE 与 天结 是同版引擎 | **推测：很可能** | 同游戏同引擎；待 OEP/签名 A/B 校验 |
| **OEP 定位靠字节签名扫描**（无壳样本 OEP 区字节在已驻留进程内存中匹配） | **已确认：可行** | 引擎不自修改 ⇒ 驻留即稳定；签名用加宽 CRT 邻区保零误报；无需调试器 |
| 仅读引擎内部 / 改数据文件需不需要拆 AGE | **已确认：不需要**（`01` §2） | `天结_unpacked.exe` 反汇编已够用 |
