## 1. 「每脚本帧」是 40 个固定槽，不是 1 个

引擎给**每个脚本上下文**准备了 40 个**固定帧**（`0..39`），每帧 120 字节（`0x78`），存放在：

```
frame[cur] 位于  this + 0x5D894 + 0x78*cur        (cur = 0..39)
```

- 由 `sub_405640`（`sub_415640` 构造器里 `for (i=0;i<40;++i) sub_405640(this,i)`）逐帧清零初始化。
- 帧内字段（页相对偏移）见下；`cur_script`（`this[95776]`，偏移 `0x5D880`）选中「当前帧」。

| 帧内偏移 | 字段 | 说明 |
|---|---|---|
| `+0x00` | `str_table` | 当前脚本**字符串表**基址（`this[95781]`；`sub_40ED40` 里 `GlobalAlloc` 分配） |
| `+0x04` | `ip` | 当前指令指针（`this[95782]`；主循环用它读 opcode / 推进） |
| `+0x20` | `local_int` | 局部 int 数组基址（`this[95789]`） |
| `+0x24` | `local_float` | 局部 float 数组基址（`this[95790]`） |
| `+0x28` | `local_string` | 局部 string 数组基址（`this[95791]`） |
| `+0x2C` | `local_ptr` | 局部 ptr 数组基址（`this[95792]`） |
| `+0x30` | `local_float_ptr` | 局部 float-ptr 数组基址（`this[95793]`） |
| `+0x38` | `caller` | 返回链接（`this[95795]`=383180；入帧时写入 `*(this+383108)` 的调用层） |
| `+0x3C` | `frame_arg` | 本帧传入参数（`this[95796]`=383184；入帧时写入 `a4`） |
| `+0x60` | `arity` | 指令长度（dword，含 opcode；`this[95805]`=383220） |
| `+0x70` | `array_container` | 每脚本数组容器（`this[95809]`=383236） |

> 印证：`sub_405640`（`_DWORD *this, int a2`）里 `result = &this[30*a2]; result[9578x]=…`，
> 即页基址按 `30*dword = 120 byte` 步进、字段为页内相对偏移 —— 与上表一致。

## 2. `local_xxx` 的含义 + 与脚本头 `local_vars = { }` 的关系

### 2.1 `local_xxx` 是「运行时的局部变量池基址指针」

`ScriptContext.local_int / local_float / local_string / local_ptr / local_float_ptr` 不是帧内普通标量，而是**指向**该脚本各类局部变量池的**基址指针**（运行时由引擎分配/填写）。`sub_41BF50`（读）与 `sub_42B4B0`（写）按 `base + 4*raw` 直接寻址。它们正好对应 VM 的局部变量**操作数类型**：

| 字段 | 局部分类 | 操作数 arg type |
|---|---|---|
| `local_int` | local-int | `0x9` |
| `local_float` | local-float | `0xA` |
| `local_string` | local-string | `0xB` |
| `local_ptr` | local-ptr | `0xC` |
| `local_float_ptr` | local-float-ptr | `0xD` |

### 2.2 脚本头 `local_vars = { ... }` 是「静态的局部变量声明」

脚本 BIN 头部（`==Binary Information - do not edit==`）里有一行声明，例如：

```
signature = SYS4450
local_vars = { f 1 1 6 1 2 }
```

反汇编器 `disassembler.cpp`（`disassemble_header`）/`reassembler.cpp`（`parse_header`）把这 6 个数逐个命名：

```
local_integer_1  local_floats  local_strings_1  local_integer_2  unknown_data  local_strings_2
=      f              1               1                 6              1               2
```

这是该脚本**声明的局部变量按类别的数量/容量**（随脚本 BIN 存储的静态属性）。

### 2.3 结论：同一件事的「静态声明 ↔ 运行时指针」

- 头部 `local_vars` 声明「这个脚本的局部作用域里，每类变量各有多少个」；
- 帧内 `local_xxx` 指向引擎为这些局部量**实际分配**出来的池，供局部操作数直接寻址。

**留意点（推测）**：头有 **6** 个计数，而引擎访问器目前只见 **5** 个局部基址（int/float/string/ptr/float-ptr）。反汇编器源码里留有 `// In Sankai no Yubiwa onwards, why? // Another type of int and string?`（针对 `0xE` / `0x8000` 序列），头里多出的 `local_integer_2 / local_strings_2 / unknown_data` 很可能对应页中**另一组局部区**（未标定 dword 承载）。此部分尚未逐一坐实。

## 3. call-script 的「叠加」如何实现

因为每帧都有自己的 `ip / local_xxx / str_table`（即**完整的 VM 帧上下文**），嵌套调用只要切换「当前帧指针」即可，**不需要动态再分配**：

### 3.1 压栈（call-script，`sub_41C6A0`）

```c
*(this + 120*cur + 383220) = 3;            // 记本指令长度
if ( cur >= 39 ) throw "...深すぎます...最大40";   // 深度上限：40 帧
script_id = sub_41BF50(this, 1);           // 读参数1 = 目标脚本 id
*(this + 383108) = cur;                    // 保存调用层（返回链接）
cur = cur + 1;                             // 深度+1 → 用下一帧
sub_40ED40(this, ..., script_id);          // 初始化新帧：读脚本文件、分配字符串表、填 local_xxx 等
```

- 深度上限来自报错文案「ファイルの階層が深すぎます．最大は%dです．」（C 行 26779，arg=40）。故最多 **40 帧（0..39）**。
- `sub_40ED40`（C 行 18577）对「当前（已自增的）cur」所指向的帧做装载：`sub_40EA00` 压调用栈、`GlobalAlloc` 分配该帧字符串表（`frame.str_table = GlobalAlloc(...)`）、读脚本文件头、解 SYS4/SYS3 校验等。

### 3.2 弹栈（return，`sub_41C770` 等）

```c
*(this + 383108) = cur - 1;                // 或直接 cur = *(this+383108)
... sub_40ED40 / 帧切换 ...
```

- 被挂起的调用层帧的 `ip/local_xxx/str_table` **一直留在原帧里**，回来时 `cur` 退回该层即可续跑，故嵌套脚本**互不覆盖**。

### 3.3 调用/恢复的「控制流寄存器」（在 `cur_script` 旁，不在帧内）

这三个紧邻 dword **不是帧内字段**，而是引擎的“控制流目标深度”寄存器：存的是**帧下标 `0..39`**（或哨兵 `-1` 空 / `-10` 续跑 / `-11` 特殊退出），**不是内存地址**。它们与 `cur_script` 的用法关系：

| 偏移 | 字段 | dword | 语义与用途 |
|---|---|---|---|
| `0x5D880` | `cur_script` | `95776` (383104) | **当前帧深度** ≈ active 帧指针（像 esp/帧顶，指向“现在跑的那层”） |
| `0x5D884` | `call_ret` | `95777` (383108) | **返回/恢复目标深度** ≈ active 帧的“返回地址/保存的 bp”。call 时=cur；return 时 `cur = call_ret`；`-10` 续跑 / `-11` 特殊退出 |
| `0x5D888` | `call_link` | `95778` (383112) | **次级续跑目标深度**（`-10` 路径 `sub_40FB60` 用它保存要回跳的深度） |
| `0x5D88C` | `call_flag` | `95779` (383116) | 控制流/状态标志（`-10` 路径做 OR/状态用） |

- **关起门来的“栈”其实在帧里**：持久的回链是 `frames[cur].caller`（页 `+0x38`），每个帧自己记录“回到哪层”。所以上面三个寄存器是**瞬时工作寄存器**，随便被覆盖也不丢调用链。
- **`-10` 续跑路径（`sub_40FB60`）**：`call_link = cur; call_ret = -10;` 然后要么 `cur=37` 并由 `sub_40ED40` 装载脚本，要么（`v2<0` 时）`cur = -v2` 直接回某帧。`-11` 则是“save-version / 特殊退出”约定。
- 印证帧下标即深度：代码用 `15 * call_ret`（`= 8*15*cur = 120*cur`）再 `+383124` 去索引 `frames[cur].str_table`（`sub_41A820`），即 `cur` 是 120 字节帧数组的下标。

#### `call_link` 详解（关键）

- **它有唯一写点**：`sub_40FB60`（C 行 18978）`call_link = cur`。
- **只有两个读点**：都在 `sub_41A820`（C 行 25663/25664）的 `call_ret == -10` 分支里 `cur = call_link`。
- **它是「`-10` 续跑的返回目标深度」**：相当于“返回地址槽”。引擎用 `sub_40FC90`（C 行 19019，脚本队列 `this+124343` 的 API `sub_409E10` 入队 + 触发 `sub_40FB60`）派发一个“延后执行”的脚本时：
  1. `call_link = cur`（记下“我现在在第几层”，将来要回到这里）；
  2. `call_ret = -10`（哨兵：本帧返回时应“续跑”）；
  3. 派发的目标帧 `caller = -10`（标记它返回时走 `-10` 路径）；
  4. 要么装载新脚本到 `cur=37`（`sub_40ED40`），要么 `cur = -v2` 直接回到某帧。
  当被派发的脚本返回时，`sub_41A820` 看到 `caller == -10` → `cur = call_link`，就回到当初保存的那一层。
- **与 `call_ret` 的分工**：普通 `call/return` 只用一个返回目标槽 `call_ret`（=调用层）；「续跑/派发」这个特殊控制流则用 `call_ret = -10` 当**哨兵**、把真正的返回目标放进 `call_link`，所以 `call_link` 是 `-10` 流的“第二返回地址”。
- **触发入口（`sub_40FC90` 本身不是指令）**：`sub_40FC90`（C 行 19019）是「把脚本入队并派发」的**辅助函数**，不是分发表里的 opcode handler。它被 3 处调用：
  1. **opcode `0x143`**（arity 0，外部名 `u00415FB0`）= `sub_41A000`（分发表槽 `this+677288`，C 行 23016）—— 这才是**字节码里真正的那条指令**，handler 里 `sub_40FC90(this, 目标)`；
  2. **`sub_411560`**（C 行 19938，一个“按脚本名”请求的 API）：`sub_455000(this+170023, 脚本名)` 查 id 再 `sub_40FC90`；被大量引擎内部点以脚本名常量（`aCallback*`）调用，非字节码指令；
  3. **解释器主循环 `sub_412290`**（C 行 20976 `sub_40FC90(this, -v29)`）—— 内部事件/消息处理里也用它派发脚本（负 id 对应 `sub_40FB60` 的“跳回已有帧”分支）。

> **类比（mental model，非事实）**：这整段 `call_link + call_ret=-10 + frame[37]` 很像一次「协作式中断/系统调用」：
> - `frame[37]`（行 18987 写死）= 系统派发帧 / “中断入口”（位于帧数组顶部，总帧上限 40 = 0..39）；
> - `call_link = cur` = 保存“被中断”的深度（像保存中断现场 / 返回地址）；
> - `call_ret = -10` + 目标帧 `caller=-10` = “中断模式”标记（像 IF 置位/中断向量）；
> - `sub_40ED40` 装载脚本 → 执行“ISR”；
> - `sub_41A820` 见 `caller==-10` → `cur = call_link` = **iret** 回到被中断的深度。
> **但有三点差别**：① 它是**协作式、队列驱动**的（`sub_40FC90` 入队 `this+124343` → `sub_40FB60` 派发），不是硬件/OS 那种**异步抢占**；② 它不是把现场 push 到一条中断栈，而是**切回一个本就挂起的 VM 帧**（被中断帧的 IP/local 一直留在原帧里）——即“上下文切换”而非“压栈/弹栈还原”；③ 37 是**单一派发槽**（`v2<0` 也能跳任意既有帧），并非严格保留一整段 `37+` 区。

> 类比：`cur_script` 像「栈顶/帧指针」（现在在哪层），`call_ret`/`call_link` 像「返回地址/保存的帧指针」（return/续跑要回到哪层）——但引擎里存的是**帧下标**而非内存地址。

### 3.4 opcode `0x143` = `sub_41A000` 行为详析（批量派发脚本请求）

C 行 25168，分发表槽 `this+677288`（= 0x143，arity 0）。

```c
void __thiscall sub_41A000(_DWORD *this) {
  v2 = 1;
  this[30*this[95776] + 95805] = 1;   // (1) 当前帧 arity(383220) 暂时置 1
  this[124350] = 1;                   // (2) 队列“派发中”锁(497400) 置 1
  v3 = this + 173106;                 // (3) 255 槽“待处理请求”表(字节 692424)
  do {
    if ( *v3 )                        //    该槽有请求（非 0）
      sub_40FC90(this, v2 << 24);     //    入队 (槽位+1)<<24
    ++v2; ++v3;
  } while ( v2 < 256 );               //    扫 v2=1..255
  this[124350] = 0;                   // (4) 解锁；恢复 arity=0
  this[30*this[95776] + 95782] += 4;  // (5) 本帧 IP += 4（跳过 opcode）
  sub_40FB60(this);                   // (6) 一次性派发整个队列
}
```

- **(1) arity 暂置 1**：`383220`(页+0x60) 是“当前指令长度”。派发期间把它设为 1 dword，防主循环误推进 IP；扫完恢复 0（此时主循环再 `IP += 4*0`，总计前进 4 = 该 opcode 本体）。
- **(2) 锁 `this[124350]`**：`sub_40FC90` 里 `if (!this[124350]) sub_40FB60(this)`。锁置 1 期间 `sub_40FC90` **只入队不派发**，避免边扫边派发的重入；扫完由本函数解锁并统一派发。
- **(3) 扫 255 槽请求表 `this[173106]`**：槽是布尔“有请求”标志；入队编码 `(槽+1)<<24` 把“哪个槽”压在最高字节。
- **(5) `IP += 4`**：arity 0 无参数，handler 手动前进 opcode 的 4 字节。
- **(6) `sub_40FB60`**：弹出整批请求，逐个走 `call_link + call_ret=-10 + frame[37]`（§3.3）继续派发。

> **结论**：opcode `0x143` = “批量刷新并派发待处理脚本请求” —— 把 255 个命中/待运行槽打包入队，再统一派发（装载到帧 37，或按符号跳回某帧）。

> ⚠️ 待确认（推测）：`(槽+1)<<24` 的编码用**最高字节的符号**区分“装载新脚本(正, 0x01..0x7F)” vs “跳回已有帧(负, 0x80..0xFF)”（对应 `sub_40FB60` 的 `if(v2>=0)…else…`）。但每个槽最终映射到哪个**具体脚本/事件**，需查谁写 `this[173106]` 请求表，以及 `sub_409E10`（入队，`this+124343`=497372）→ `sub_40FB60` 的队列结构 `497376/497380/497384/497396`。

## 4. 与既有结论的衔接

- `this[95776]=cur_script` 即 `03` 文档主循环 `sub_412290` 里选取指令指针的键：
  `this + 120*cur_script + 383128` = 当前帧的 `ip`。
- `this + 0x5D894` 是「帧数组」基址（frame 0），不是「页大小 0x5D894」——`0x5D894` 是 frame 0 的 *str_table 字段* 的字节偏移。
- 对象模型 `engine/engine.hpp` 已把帧数组建成 `ScriptContext frames[40];`（+ `call_ret/call_link` 链接字段），`script(cur)` 返回 `&frames[cur]`。
