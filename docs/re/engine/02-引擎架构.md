# 引擎架构（engine）

> 级别：**已确认**（反汇编器 opcode 表 + 反编译实证）。
> 分析对象：`tools/eushully-decompiler`、`engine/天结_unpacked.exe_utf8.c`。

---

## 1. 引擎是通用解释器，业务逻辑在字节码（核心判断）

- 反汇编器 `tools/eushully-decompiler` 的 opcode 表（`age-shared.cpp` 的 `definitions`，~300/548 条 `{opcode,"uXXXX",参数个数}`）就是**引擎对外暴露的全部语义面**：
  - 通用 VM 指令：`add/sub/mul/div/mov/and/or/eq/lt/jcc/lookup-array/set-string/…`；
  - 引擎子系统调用：`play-sound-effect`/`play-voice`/`draw-texture`/`draw-string`/`play-bgm`/`set-font`/`create-texture`/`toString`/`strlen`…；
  - 注释里的 `// Amayui 2`、`// Fuukan no Gransesta`、`// Tenmei no Conquista` 表明**同一套引擎跨多作**。
- **没有任何一条 opcode 包含「单位字段语义」/「掉落字段语义」** → 引擎对游戏数据字段一无所知，字段语义在**字节码**里。这印证「1MB 二进制、逻辑几乎全在 src、无 JIT」。

> **推论**：字段语义靠 src 字节码分析（见 `docs/re/src/`）；引擎反汇编只给「VM 核心 + 子系统 + 全局数组布局」，不直接给字段语义。

---

## 2. `uXXXX` 与 `sub_XXXXXX` 地址不匹配（重要前提）

- 反汇编器（age-asm）给出的 opcode handler 名是 **`u0042xxxx`**（如 `u00420950` = 引擎函数 VA 0x420950）。
- 但这份引擎（`天结_unpacked.exe`）的 Hex-Rays 反编译函数名是 **`sub_XXXXXX`（= 地址）**（如 `sub_42C6E0` = 0x42C6E0）。
- **两者是不同构建/版本，地址对不上** ⇒ **不能用 `uXXXX` 去对这份引擎的函数地址**；只能靠**结构**分析这份 C 文件。

---

## 3. 字节码 / 指令布局（来自反汇编器 `parse_instruction`、`disassemble.cpp`）

- 每条指令 = **opcode (u32)** + `arg_count` 个参数；**每个参数 = type (u32) + raw_data (u32)，共 8 字节**。
  - 指令长度 = `4 + 8 * arg_count`（见 `reassembler.cpp: compute_length`）。
- 操作数**类型**（`get_type_label` / `reassembler.cpp: get_type`）：
  - `0`=整形立即/值、`1`=float、`2`=字符串、`3`=global-int、`4`=global-float、`5`=global-string、`6`=global-ptr、`8`=global-string-ptr、`9`=local-int、`0xA`=local-float、`0xB`=local-string、`0xC`=local-ptr、`0xD`=local-float-ptr、`0xE`=local-string-ptr、`0x8003/0x8005/0x8009/0x800B`=特殊（后作/未知）。
- 头部 `signature` 为 `SYS4450`（v4，BinaryHeader 0x3C）或 `SYS5501`（v5，0x44）。
- **字符串**编码在 `.data` 尾部，`raw_data` 指向 `header_len + raw_data*4` 处，逐字节 XOR `0xFF`，`0xFF` 终止。**v4=单字节(Shift-JIS)、v5=UTF-16**。

---

## 4. `call-script` 与 `jcc` 等控制流（引擎视角）

- 控制流相关 opcode：`0x8C/0x8F/0xA0/0xCC/0xFB/0xD4/0x90/0x7B`（见 `age-shared.h is_control_flow`）。
- 这些 opcode 的操作数在 `raw_data != 0xFFFFFFFF` 时才是**目标地址/label**（`is_label_argument`）。
  - 具体语义按 opcode 分段（`0x8C/0x8F` 用 idx、`0xA0` 用 idx>0、`0xCC/0xFB` 用 idx>0、`0xD4` 用 idx>=2、`0x90` 用 idx>=4、`0x7B` 全 idx）。
- `jcc` 的完整语义与统计见 `docs/re/src/02-jcc语义.md`。

> 这些 opcode 的「语义如何落到引擎」已在 `03-opcode分发与解释器.md` 里解开（dispatch 表 + 主循环）。控制流 = 把 IP 改成 label 目标，不改变通用分发机制。
