# 「过桩型」导入桩：实现、反解与解壳健康评估（含工作记录）

> 级别：**已确认**（运行态实测 + 双二进制对齐 + 解壳健康评估）；**含一段重要的自我修正**（见 §修正）。
> 主题：回答 `13-导入调用机制与过桩型特征.md` 的核心问题 —— 过桩型的桩如何实现；以及后续追问 —— 在不提权、不附加调试器、假定「桩不修改自身代码」的前提下，能否把过桩调用点反解成真实 API；并评估 `AGE.EXE__dumped.EXE` 是否已脱壳。
> 运行环境：Windows 运行中的带壳 `AGE.EXE`（PID **30624**，非管理员），引擎基址 `0x400000`，无 ASLR。全程只用 `OpenProcess(0x0400|0x0010)+ReadProcessMemory`（同用户读），**不**用 `SeDebugPrivilege`、不 `DebugActiveProcess`、不写目标进程。

## ⚠️ 先看修正（最重要）

**关于基准的最终正确认知**：`raw\AGE.EXE__dumped.EXE` 与 `raw\天结_unpacked.exe` **都是 AGE 的拆壳产物，不存在所谓"原版/权威无壳基准"**。二者由不同工具对同一个带壳 AGE 拆壳得到，trampoline 策略不同：

| 产物 | 来源 | 性质 |
|---|---|---|
| 原始带壳 AGE | 安装包 | 唯一起点；**不存在"未加壳原版"** |
| `raw\AGE.EXE__dumped.EXE` | **工具 A** 拆 AGE | 拆壳产物，**含** 289 条 `poly` thunk（RVA `0x1C3000`） |
| `raw\天结_unpacked.exe` | **工具 B** 拆 AGE **并再次修改** | 拆壳产物 + 汉化修改，**无** `poly` thunk，过桩调用点是 `call [IAT槽]`（`FF 15`）直连 |
| 运行态（PID 30624） | 带壳 AGE 运行 | `call rel32 → 共享桩 0x029E0000`（257 处）；`poly 区`加密垃圾；IAT 槽加密 |

> ❗ **本文件初期曾误判**：先默认 `__dumped` 为"无壳基准"，后把 `天结_unpacked.exe` 当"权威原始引擎"。**两判皆错**。二者都是拆壳产物，无优劣、无"更原版"之分。

**工具无关性（已验证，`tool_independence.py`）**：两种拆壳产物在**"每个调用点调用哪个 API"上完全一致**，差异只在**路由形态与命名别名**：

- D 的 `poly` thunk 表到达的 **69 个 IAT 槽**，**全部**也在 U 里以 `call [IAT槽]` 直连出现（"不在 U 中的 poly 槽" = **0**）→ trampoline **不引入任何新导入语义**，只是路由。
- 两个产物可达的**函数名集合相同（260 = 260）**。差异仅为表示：`lstrlenA`/`GetGlyphOutlineA`（D 带 `A` 后缀）vs `lstrlen`/`GetGlyphOutline`（U 不带）；`ord#7/8/9`（D 以序号表示）vs `VariantClear`/`VariantInit`/`SysStringLen`（U 解析成具名，同为 oleaut32 序号导出）；个别 user32 条目归属/名字解析不同（`RegisterWindowMessageA` vs `RegisterClipboardFormatA`）。

> **因此**：
> 1. **过桩型桩 = ASProtect 的共享 trampoline**（恒收敛 `call 0x65E5B4`，与工具无关）。
> 2. **每个过桩调用点调用哪个 API** 由引擎里对应 IAT 槽决定，**与用什么工具拆壳无关**；两种拆壳产物给出同一批导入。
> 3. **`__dumped` 是否已脱壳** = 已脱壳（EP=真 OEP `0xEDBDE`、`.text` 熵 8.0→6.57、310 真实导入）。这是**事实**，不依赖"哪个是原版"。

（下文 §3 的反解结果——257 站点、60 唯一导入、5 DLL——是**在 `__dumped` 基准下得到**的，与文档 `13`§3 的 missing 清单逐项吻合。它依赖「无漂移 + poly thunk」链路；该链路在"运行态 ↔ `__dumped`"（同为被打过、站点 RVA 重合、都是 5 字节 `call`）下成立。若改用 `天结_unpacked.exe` 作基准，两者之间是 `FF 15`(6B)→`call`(5B) 的**逐点漂移**关系，需漂移对齐——本轮未做，记录为待办。但两种基准最终给出**同一批导入**，见上文工具无关性验证。）

## 1. 桩本体：单一共享 trampoline（已确认）

- 本进程桩地址 **`0x029E0000`**（MAPPED 私有 R-X 页；`0x029E0000..0x02B90000` 一整片 R-X 桩页族）。地址随启动动态分配（文档旧值为 `0x1340000`/`0x340001`），**地址变、结构不变**。
- **桩不修改自身代码**（多时点重读字节恒定：`EB 01 F3 53 9C ...`）→ 假设成立，可安全 dump+静态/模拟分析。
- 桩被大量 `EB xx` 跳垃圾、`CD 20`(int3)、`F2/F3` 前缀、`8D` 算术干扰；控制流跟随反汇编（capstone 实走）显示其内部寄存器算术**互相抵消**，最终**无例外**收敛到：
  ```
  029E0186  jmp   029E018A
  029E018A  call  ebx        ; ebx 恒 = 0x65E5B4
  ```
- **对任意调用点收敛同一目标**：用 Unicorn 对 7 个不同 RA 模拟到 `call ebx`，目标**全部 `0x65E5B4`**，且桩正确读到本站点（`site = RA - 5`）。→ **桩不是「按调用点分派」的混淆 thunk，而是共享 trampoline。**

## 2. 引擎高位区 dispatch 机器（静态描述，已确认形态）

文档 `13`§4 提到的两个分派区在引擎高位区，本进程运行态验证：

- **`0x65D8E8`（RVA `0x25D8E8`）**：真实起始（前有 `push 0xeb04eb05; jmp` 垃圾）。做 `rep movsb` 拷贝 + `push 0x65D910`(返回地址) + `push [ebp+14]/[ebp+0C]` + `mov eax,[ebp+8]`，然后 **`jmp dword ptr [eax+0x38]`** —— 即「手工构造调用 + vtable 式函数指针间转」（`FF 60 38`）。
- **`0x65E5B4`（RVA `0x25E5B4`）**：桩 `call ebx` 的目标；带 SEH 的引擎函数，内部经 `[0x66285c]→[eax]`、`[0x662918]+0x34`、`[0x51Dxxx]` 等**运行时函数指针槽**间接调用。
- ⚠️ 诚实边界：`0x65E5B4` 内部走的 `call[slot]` 依赖**真实全局数据/线程环境**（含 `fs:[0x34]`=TEB 读取）。我的 Unicorn 用固定寄存器基线 + 假 TEB，**只能走到进入 `0x65E5B4`**，无法在纯模拟里复现其真实分派目标。**但这不阻碍每站点导入反解**（见 §3）。

## 3. 反解结果（在 `__dumped` 基准下，已确认有效）

工具 `scripts/re/map_all_stubs.py` 输出 `.tmp/stub_import_map_full.json`，`emit_mapping.py` 汇总为 `.tmp/stub_site_import_map.csv/.json`。

- 站点总数 257；**257/257 解析**；唯一导入函数 60；唯一 IAT 槽 60；DLL：`KERNEL32`(215) / `USER32`(28) / `SHELL32`(5) / `ADVAPI32`(6) / `SHLWAPI`(3)。
- 代表函数：`USER32!MessageBoxA(28)`、`KERNEL32!FreeLibrary(27)`、`KERNEL32!WaitForSingleObject(25)`、`KERNEL32!OutputDebugStringA(25)`、`KERNEL32!GetCurrentThreadId(20)`、`KERNEL32!WriteFile(15)` 等。
- **与 `13`§3 missing 清单逐项吻合**（WriteFile/HeapAlloc/WaitForSingleObject/WaitForMultipleObjects/CreateProcessA/CreateEventA/FreeLibrary/TerminateProcess/GetCurrentThreadId/GetFileSize/SetFileTime/…/MessageBoxA/SHGetSpecialFolderPathA/PathRemoveFileSpecA/Reg* 等）。反解与文档定性一致。

**反解链路（`__dumped` 基准，无漂移）**：运行态 `call→桩` ↔ (同 RVA) `__dumped` 的 `call→poly_thunk` → `poly_thunk = jmp [IAT槽]` → `.idata` 导入目录 → `DLL!函数名`。

## 4. 解壳健康评估（`AGE.EXE__dumped.EXE` 是否已脱壳）——已确认脱壳成功

`scripts/re/unpack_health.py` 对比 **原始带壳 P** / **脱壳产物 D（`__dumped`）** / **另一拆壳+修改产物 U（`天结_unpacked`）**。这里 U 不是"权威原版"，只是作**第二个拆壳样本**交叉对照（两工具拆同一壳，若特征一致则佐证结论工具无关）：

| 维度 | P（带壳） | D（`__dumped`） | U（`天结_unpacked`） | 判定 |
|---|---|---|---|---|
| 入口点 EP | `0x1000`（壳 stub） | **`0xEDBDE`（真 OEP）** | `0xEDBDE` | ✅ 已指向真 OEP（两工具给出同一 OEP） |
| 导入表位置 | `0x1C1A60`(诱饵, `.data`) | `0x1C1000`(真 `.idata`) | `0x1B1B9C` `.idata` | ✅ 已恢复真导入表 |
| 导入函数数 | 22 | **310** | 303 | ✅ ≈ 另一拆壳产物（+7 为转发/序号/粒度差） |
| `.text` 熵 | **8.0/7.997/7.986**（加密） | **6.568** | 6.567 | ✅ 已解压到明文熵 |
| 末期节熵 | 7.625 | 0.831 | 0.901 | ✅ 高熵残留已清除 |
| overlay | 0 | 0 | 0 | ✅ 无 |

**判定：D 已脱壳成功**。功能层面的壳全没了（`.text` 明文、EP=真 OEP `0xEDBDE`、IAT 重建为 310 真实导入）。残余仅为**形态/卫生层面**：节名仍是匿名（unnamed）、节特性仍 `0xE0000040`(RWX) 未归一化、多出 `.idata/.poly` 两节。**这些不是加壳保护功能，只是没做节归一化。** 那 289 个 trampoline 是**工具 A 恢复导入时物化的路由表**（工具 B 则用直连 `call[IAT]` 恢复、无此表），两者让**同一批导入**可达。

> 结论与拆壳工具无关，可用两种拆壳产物交叉佐证：**`__dumped` 确实是脱壳成功 + 保留一堆 trampoline**，并非失败。

**走过的弯路（记录以免重蹈）**
1. **反复误判基准**：第一次默认 `__dumped` 为"无壳基准"；被纠正后又把 `天结_unpacked.exe` 当"权威原始引擎"。**两判皆错**——二者都是 AGE 的**拆壳产物**（工具不同、策略不同），**不存在"原版/权威基准"**。真相靠 `poly_provenance.py` + `tool_independence.py` 确立：两工具让同一批导入可达，差异只在路由形态与命名别名。
2. **"无漂移"假设**：在"运行态 ↔ `__dumped`"间的确成立（两者 5 字节 `call`、站点 RVA 重合）；但"运行态/`__dumped` ↔ `天结_unpacked`"间是 `FF 15`(6B)→`call`(5B) 的**逐点漂移**关系（`12`§10.2 早已指出）。两种基准最终给出**同一批导入**（见工具无关性验证），故反解结论稳健。
3. **Unicorn FS/TEB base 是 no-op**：`stub_debug.py`/`chain_trace.py` 里写 `UC_X86_REG_FS_BASE` 无效（deprecated, id 250），桩尾部 `push fs:[ecx]`（SEH/`fs:[0]`）直接卡死。把假 TEB 放**线性地址 0**（Unicorn x86-32 FS base=0）才绕过 —— 但 `0x65E5B4` 内部仍依赖真实全局/线程环境，纯模拟无法还原其分派。
4. **入口 OEP 判断**：`unpack_health.py` 显示 `__dumped` EP=`0xEDBDE`，且 `天结_unpacked`（另一拆壳工具产物）EP 相同 → 两独立工具给出同一 OEP，佐证已脱壳 + 同版，结论工具无关。
