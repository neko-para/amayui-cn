# 加壳判定与拆壳（engine）

> 级别：**已确认**（PE 结构实测）。
> 分析对象：`raw/AGE.EXE`、`raw/天结.exe`、`raw/天结_unpacked.exe`。

---

## 1. AGE.EXE = ASProtect 加壳（已确认）

`raw/AGE.EXE`（1,007,104 B）是 **ASProtect** 加壳的引擎本体（非 PlayDRM 层；PlayDRM 是 `start.exe` 启动器，已另移除）。

PE 结构实测证据：
- 8 个节，多数**节名为空**（仅 `.rsrc/.data/.adata` 有名字）；
- **所有节 RWX**（特性 `0xE0000040` = 读+写+执行）；
- 代码节熵 **8.000 / 7.997**（≈最大熵 = 压缩/加密），整文件熵 7.58；
- **零文件节**（节 4 VSize 0x11000、`.adata` VSize 0x1000 的 RawSize=0）；
- 导入表落在 `.data`（非 `.idata`），导出表为**垃圾/高熵**（`NumberOfFunctions` 荒谬值）；
- 入口桩 `68 01 10 5C 00`(push 0x5C1001) `E8 01 00 00 00`(call over) `C3 C3` 后接高熵；
- 无 overlay（文件末尾 = 最后节 raw 终点 0xF5E00）；
- 解释了 UIF 失败：`Unable to enumerate import address table`（磁盘 IAT 是诱饵）。

> `raw/天结.exe`（心愿屋汉化壳）**同样仍是 ASProtect 壳**：`.text`(VAddr 0x1000, VSize 0x11C000) 与 AGE.EXE 一致、`.text` 熵 8.000、带 18.9MB 高熵 overlay（`天结.exe = 加壳引擎 + overlay`）。两文件**节 VA 空间一致**。

---

## 2. OEP 与「能否 run + 全量 dump」（已确认结论，不推荐 run+dump）

- **OEP = Original Entry Point**：被壳包住的原程序真正入口；`AGE.EXE` PE `EntryPoint=0x1000` 只是 **ASProtect stub**，OEP 在运行时解密后才现形。
- 拆壳核心流程：**跟到 OEP → 在 OEP 处 dump → Scylla 重建 IAT → 修 EntryPoint 为 OEP**。
- 「直接 run + 全量 dump」**不可靠**：① 反 dump/自校验（可能二次加密、检测重保护、自毁）；② dump 是**内存镜像**（节/重定位/IAT 是运行时值，不是可加载 PE，需 Scylla 重建）；③ **OEP 仍需跟 stub 定位**；④ 2.x/SKE 可能带虚拟化/分区加密。

> 对做汉化（改数据文件）：**不需要拆壳**。只有要**读引擎内部**（映射 / `0x53f48c`、`0x928a7` 判定）才需要，而那份 `天结_unpacked.exe` 让这条变得简单（§3）。

---

## 3. `raw/天结_unpacked.exe` = 已脱壳的干净引擎（关键资源，已确认）

1.7MB，**无壳**判定（PE 结构实测）：
- 节**全有名字**：`.text/.data/.rsrc/.edata/.idata`；
- `.text` 熵 **6.567**（正常编译代码），其余 `.rsrc` 5.808 / `.data` 5.893 / `.idata` 4.744（无加密段）；
- **入口点 RVA 0xEDBDE**（在 `.text` 内，反汇编为 `call/jmp/push/cmp/setne/jne` = 真实 OEP/main）；
- **真实导入表**：`kernel32/user32/gdi32/d3d9/d3dx9_43/mfplat/winmm/ole32/imagehlp/advapi32/version/shell32/shlwapi/imm32/oleaut32/evr/dxva2`；
- 导出表正常（0x1AF000, 0x4C）；**无 ASProtect/Themida/VMProtect/UPX** 特征串（0x11C1BE 的 "MPRESS" 为随机文本巧合）；
- **无 overlay**（最后节 raw end == 文件大小），**未内嵌 BIN**（`SYS4450` 命中 0 次）。

**注意**：
- 它**被改过**（如支持渲染 GBK 而非 SJIS）—— 但改动在**文字渲染层**，**VM 核心 / 全局数组布局 / 掉落处理逻辑没动**，仍是原引擎逻辑。
- `.text` 特性为 `0xE0000060`（RWX+CODE）：像是 dump/拆壳时**没还原节保护属性**的残留，**不代表残留加密**（内容可读、熵正常）。

## 4. 静态分析 1.7MB 引擎的可行性与路线（已确认可行）

- **可行**：`.text`=0x11C000 ≈1.1MB，是 IDA/Ghidra 常规目标；全量反汇编+自动分析可行（秒级到分钟级）。但**不需要**把全部读懂——**定点**即可。
- 引擎是通用解释器 ⇒ 引擎只给「VM 核心 + 子系统 + 全局数组布局」，不直接给字段语义（见 `02-引擎架构.md`）。
- **路线（按优先级）**：
  1. **找全局整型数组基址/步长**：在解释器处理 `global-int` 的分发代码里找 `mov eax,[base+index*4]` / 指向大整型区的指针常量 → 解出 `global_int_base`，从而定「索引→地址」映射。
  2. 用基址算 `0x53f48c/0x928a7/0x53e104/0x53cd7c/0x52a0b5` 的**真实地址**，在 IDA/Ghidra 里做**交叉引用（xref）**，找它们被哪些引擎函数**读写**（即掉落门控的真正来源）。
  3. 顺带确认 `u0042xxxx` 子系统函数，读懂掉落时调用的引擎能力。
