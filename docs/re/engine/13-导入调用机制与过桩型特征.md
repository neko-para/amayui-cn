# 导入调用机制与「过桩型」特征

> 级别：**已确认**（运行态实测）+ **推测**（路径）。
> 主题：引擎导入调用的两种形态——**直接型** vs **过桩型（混淆型）**，以及后者在二进制里的**可识别特征**。为后续强行分析桩函数留存。
> 运行环境：Windows，运行中的带壳 `AGE.EXE`（engine base `0x400000`，无 ASLR 重定位）；读取/附加需管理员 `SeDebugPrivilege`。

---

## 0. 一句话

引擎的**导入调用分两类**：一类是干净的 `call [IAT槽]`（可直接读取映射到 API）；另一类**经过 ASProtect 混淆 thunk**（形如 `push 返回地址 + jmp dword ptr [eax+0x38]` 的间接/函数指针调用），**静态扫 `.text` 的 `call [IAT槽]` 覆盖不到**，这正是「用户态 call 固定地址 → 真 API 需穿过混淆代码」的根源。

---

## 1. 两类导入调用（运行态实测）

| 类型 | 形态 | 是否可独立静态映射 |
|---|---|---|
| **① 直接型** | `call dword ptr [IAT槽]`（如 `004B669E  call [0x51D130] ; kernel32.ReadFile`） | ✅ 可（纯读取：扫 `.text` 找 `call [槽]` + 读槽值 + 用运行态系统 DLL 导出解析） |
| **② 过桩型/混淆型** | **入口**：`call rel32 → <固定桩地址>`（如 `0x1340000`，业务代码发的）；**内部**（桩跑完分发逻辑后）：`push 返回地址 + jmp [eax+0x38]` 之类间接分派 | ❌ 需反混淆桩 / 运行时抓真实上下文 |

> 两类**不是按 DLL 划分，而是按调用点混合**（同一段业务代码里混着两种调用）。ASProtect 只把其中一部分调用点重定向到桩，其余保持直接。

## 2. 直接型：已独立拿到的映射

**工具：`scripts/re/scan_imports.py`（管理员 32 位 Python 执行）**

- 扫描运行态 `.text`（`0x400000+0x1000` 起，`0x11C000`）里所有 `FF 15 / FF 25 [槽]`，槽在 `0x51C000..0x51E000`。
- 读槽值（= API 地址），用**运行态加载的系统 DLL 导出表**解析成 `模块!函数`。
- 结果：**233 个槽，230 个解析成功**；仅 3 个未解析（见下）。

**未解析的 3 个**：
- `0x51d2c8 = 0x653B04 (AGE.EXE)` → 引擎自身函数指针（非导入，正常）；
- `0x51d490 = 0x6CF7AFB0 (d3d9.dll)`、`0x51d50c = 0x6FE6D140 (apphelp.dll)` → 系统 DLL 里导出表未直接列出的（可能按序号/转发）。

**引擎「直接导入」模块分布（230 个）**：
```
KERNEL32(64) user32(57) GDI32(23) winmm(19) d3dx9_43(19) ntdll(15)
combase(7) MFCORE(5) mfplat(4) oleaut32(3) version(3) mf(2) RTWorkQ(2)
ADVAPI32(1) evr(1) imm32(1) d3d9(1) dxva2(1) imagehlp(1) ole32(1)
```

**与 `天结_unpacked`（无壳）对比**：运行时直接导入是无壳 303 导入的**有序子集**（`kernel32` 64/145、`user32` 57/62 等），顺序一致、无错位。运行时还额外解析出 `ntdll/combase/MFCORE/mf/RTWorkQ`（导入目录外、运行期动态依赖）。

> ⚠️ **一个 bug 已修复**：导出表解析里 `AddressOfNameOrdinals[j]` 是**0 基索引**，我起初误用 `funcs[oi-1]` 导致**名字整体错位一位**（出现 ReadFileEx、GetSystemAppDataKey 等不匹配地址的冷门名）。改为 `funcs[oi]` 后与无壳版对齐。

## 4. 过桩型的精确二进制特征（关键，为后续分析）

**要分两层：入口 和 内部分发。**

- **入口（业务代码发起的混淆调用）**：`call rel32 → <固定桩地址>`。这是业务代码 `call` 的**固定地址**——正是「用户态 call 固定地址」所指。它把控制流拉进桩（如 `0x1340000`，每次启动动态分配；也可在 `0x340001` 一带），这里用 `call rel32`，操作数是**相对偏移+固定目标**。
- **内部（桩执行完分发逻辑之后）**：才会走到我们看到的 `push 返回地址 + jmp [reg+offset]` 这种**间接函数指针分发**。也就是说，`0x65D910` 处的是桩/thunk **内部、分发逻辑跑完之后**的机制，**不是**业务代码的调用入口。

**实例地址**：`0x65D910`（WriteFile 的返回地址，位于引擎高位区 `RVA 0x25D910`）。

**反汇编（内部分发，手动解码；capstone 线性对齐被混淆干扰）：**
```
65D8E0  push 0xeb04eb05            ; 混淆垃圾
65D8E5  jmp  0x65d8e8              ; 跳垃圾(EB 01)
...
65D8F0  8B 75 10            mov  esi,[ebp+10]
65D8FE  89 E7               mov  edi,esp
65D900  F3 A4               rep movsb
65D902  68 10 D9 65 00      push 0x65D910        ; 显式压入返回地址
65D907  FF 75 14            push [ebp+14]
65D90A  FF 75 0C            push [ebp+0C]
65D90D  8B 45 08            mov  eax,[ebp+08]
65D910  FF 60 38            jmp  dword ptr [eax+38]   ; 间接函数指针分派
```

**要点：**
- 这是桩/thunk **内部分发**的「手工构造调用」：`push 返回地址 + push 参数 + jmp [eax+0x38]`，走**运行时函数指针**（`[eax+0x38]`），等价于**类虚表/函数指针间接调用**。
- `[eax+0x38]` 取决于运行时 `eax`（进入时对象的指针/上下文），**静态推不出目标 API**。
- 所在区以 `EB 01`、`push <垃圾>` 等**跳垃圾混淆**包裹，**线性反汇编易错位**（OllyDbg 反向滚动即因此错位）。

> 所以「过桩型」的完整链路是：**业务代码 `call rel32 → <固定桩>`（入口）→ 桩执行分发逻辑 → `push 返回地址 + jmp [reg+offset]`（内部分发，间接命中真 API）**。后续强行分析桩时，入口从 `call rel32 → 固定目标` 追入，内部找「站点→函数指针」的分发/查表。
