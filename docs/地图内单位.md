# 地图内单位构成解析（天結いキャッスルマイスター）

> 结论基于：对 `src/STINIT.txt`（$n$ 追加包同）逆向，并用 `src/STINIT2.txt`（关卡名）、`src/EBINIT.txt`（单位名）交叉验证。
> 产出脚本：`scripts/annotate-stinit-maps.js`（关卡名）、`scripts/annotate-stinit-units.js`（单位名）；均在 `src/*STINIT.txt` 行尾追加 `//` 注释。

## 1. 两块关键编码（本次解析的两把钥匙）

### 1.1 关卡 id / 关卡名（STINIT → STINIT2）
每个关卡（地图）在 `STINIT.txt` 以如下块开头：

```text
eq (local-int 0) (global-int b222) <mapNo>
jcc (local-int 0) ffffffff label_...
jmp label_...
```

`eq` 的**第三个参数 `mapNo` 就是地图编号**。
- **关卡名 = STINIT2 中 `set-string (global-string <addr>) ` 的字符串，其中 `addr = 0x121e2 + mapNo`。**
- 例：`mapNo=1` → `0x121e3` = `遺跡地下の調査区域`；`mapNo=b` → `0x121ed` = `堆積した砦路樹`；`mapNo=51` → `0x12233` = `廃妖の谷底`。
- ⚠️ 注意基址是 **`0x121e2`**（非 `0x121e3`）：名表以 `mapNo=1 → 0x121e3`（第 1 关 `遺跡地下の調査区域`）为起点，全表 655/655 命中。
- 名表来源为**全部 `src/*STINIT2.txt`**（base + `$n$`，地址空间一致，按 `set-string` 合并）。名值形如 `日文|中文`。
- 关卡名地址表稀疏（`STINIT2` 中按 `0x121e2+mapNo` 稀疏分布），但基址正确时**所有**关卡均能命中。

### 1.2 单位 id / 单位名（STINIT → EBINIT）
每个关卡块内是若干个“单位槽”，每个槽以如下锚点结束：

```text
mov (global-int 14dc<低字节>) <v>  ×N     ← 计数器列（前部，数量随遭遇而异）
mov (global-int 14dd<0x40+i>) <unitId>    ← 单位 id（寄存器随 i 递增）【注释行】
mov (global-int 14dd<0x40+i+0x1E>) <level>← 单位等级
mov (global-int 14dd<0x40+i+0x3C>) <v>     ← 未知（观测量）
mov (global-int 14dd<0x40+i+0x5A>) 1       ← 未知（多为 1）
copy-local-array (global-int 14dXXX) [...] ← 锚点
```

- **单位名 = EBINIT 中 `set-string (global-string <addr>)`，其中 `addr = 0x17ab6 + unitId`。**
- 例：`unitId=fa` → `0x17bb0` = `迷い入った小鬼`；`unitId=38f` → 歪侍女；`unitId=2d1` → 掘削の彫像。
- 名表来源为**全部 `src/*EBINIT.txt`**（`set-string` 按地址合并，`日文|中文`）。

## 2. 单位槽的定位（采用的简洁方法）

- **每个关卡的单位都是从 `mov (global-int 14dd41)` 开始放置**；单位 id 寄存器落在**闭区间 `0x41..0x5d`**（部分遭遇可能跳号、不连续）。
- **判定**：**所有 `mov (global-int 14ddXX)`（`XX ∈ [0x41,0x5d]`）且 `0x17ab6+unitId` 能反查到单位名，即为单位**，逐一标注。实测全工程 **1791** 个。
- 上界 `0x5d` **恰好排除伴随/率/等级字段**（单位 0x41 的 `+0x1E` 伴随在 0x5f，落入 `0x5e..0x7b`；其小值也可能命中名字，是误标源）。故区间外（`<0x41` 计数器、`>0x5d` 伴随）一律不标。
- ⚠️ **弃用“后 3 行 +0x1E/+0x3C/+0x5A”结构判据**：间距过宽，会把计数器也错标为单位（如 `14dd27=1` 恰命中 `アヴァロ` 名地址被误标为 `アヴァロ`）。该判据只会产生误标，已放弃。
- （可作交叉校验但非判定）`copy-local-array (global-int 14dXXX)` 的“向前第 4 行”锚点：只覆盖部分槽，不完整。

## 3. 单位槽字段（部分已知 / 待定）

### 3.1 单位 id 行**前部**计数器列的偏移规律（本次修订）

> 注：旧稿用“前 4 行固定窗口”统计偏移，会因地址交错而混入非计数器列行（见 §3.3 的失败原因）。
> 本修订改为 **§3.3 的“单调递减向后扫码”**，只顺着真正属于该单位槽的计数器列走。

对全量 **1791 条**已标注单位 id 行做“向后单调递减扫码”的间距统计：偏移**完全有序、数量有限、步长恒为 `0x1E` 的倍数**。

- **`14dc` 计数器列（主体）**：相对标记行 K 的**相邻间距**只有五种——`0x1E / 0x3C / 0x5A / 0x78 / 0x96`（分别 = 1×/2×/3×/4×/5× 0x1E），全是 0x1E 的倍数。即各计数器列相对 K 的偏移为 `+{0x1E, 0x3C, 0x5A, 0x78, 0x96, 0xB4, 0xD2, 0xF0}`（0x1E 等差，列越多采得越远，上限 `0xF0`）。
- **`14dd` 伴随字段**：`+0x1E / +0x3C / +0x5A / +0x78`（等差 0x1E），同为 0x1E 倍数。这些是**单位 id 行之后**的伴生字段，故该单位槽自成一列 0x1E 等差结构。
- **异页寄存器（非规律，扫码时已剔除）**：如 `14df4X`、`14e04X`、`14d8XX` 等属其它表；按 §3.3 的“单调递减 + 窗口 [K-0xF0, K] + 遇大/过小即停”会把它们挡在窗口外，不进入计数器列。

> 结论：**单位槽前的“计数器列”是规则的 0x1E 步进等差**，列数随遭遇而异（扫码扫到的是单位 id 行之前的那些列 + 本槽 `+0x1E` 起的前几列）。它可进一步作为“单位 id 行结构”的更强约束。

### 3.3 验证：从单位标记行向后“单调递减扫码”，间距是否均为 0x1E 倍数（**本次重测，已修正**）

**正确判据（用户的“单调递减向前扫码”规则）**：
从每条单位标记行 K（`mov (global-int 14ddXX)`，`XX∈[0x41,0x5d]`），向**代码前部**（行号递减方向）依序读取寄存器地址，**只保留单调递减（`addr < 上一保留`）且落在 `[K-0xF0, K]` 窗口内**的行；一旦遇到 **变大（`addr ≥ 上一保留`）** 或 **过小（`addr < K-0xF0`）** 即停止。

- **两条停止条件**（都需判断）：
  - **变大**：下一寄存器地址 ≥ 上一个保留的地址（表明已跨到相邻/前一块数据），停止；
  - **过小**：地址 < `K - 0xF0`（`0xF0` = 向后允许的最远窗口，即 `14ddXX` 与倒数计数器列的最大间距），停止。
- 扫码过程中相邻两行的**间距（差值）**即“计数器列”的步进。

**实测（所有 `src/*STINIT.txt`，base + `$1$–$5$`）**：
- 单位标记行 **1791 条**；**全部 1791 条的相邻间距都是 0x1E 倍数**，**0 条违规**。
- 间距桶：`0x1E`×5273、`0x3C`×1286、`0x5A`×854、`0x78`×892、`0x96`×25 —— **全部为 0x1E 倍数**。
- 向后扫码到达的最远深度范围 `0x96 .. 0xF0`，窗口上界 `0xF0` 正是从单位标记行到最远计数器列的最大间距。

**抽查两例（与你给的例子一致）**：
| 标记 K | 向后收集的递减行 | 停止原因 |
|---|---|---|
| `0x14dd41`（牙コウモリ，L146） | `14dcc9 → 14dc6f → 14dc51`（间距 `0x78/0x5A/0x1E`） | 遇 `14d8d5` **过小**（`< K-0xF0=0x14dc51`）停止 |
| `0x14dd42`（雷蝶，L153） | `14dcca → 14dc70 → 14dc52`（间距 `0x78/0x5A/0x1E`） | 遇 `14dd9b` **变大**（`≥ K`）停止 |

> ✅ **结论（已修正，取代原先“待复核”的 127/1791 说法）**：**0x1E 间距规则成立**，前提是采用本节的“单调递减扫码 + 双停止条件”，而非原先的“固定窗口 `[K-0xF0,K]` 全行皆 0x1E 倍数”。

**❌ 原 §3.3 方法为何失败（逻辑错误）**：
原写法用固定窗口 `[K-0xF0, K]` 并把**窗口内所有行**都要求成 0x1E 倍数。但 STINIT 的地址是**交错（interleaved）**的，窗口会框进**本不属于该单位槽“计数器列”的行**：
- **相邻单位寄存器（±1）**：下一条单位的 `14dd4X`（彼此 +1），非 0x1E 间距；
- **`+0x3D/0x5B/0x79/…`（列+1 字段）**：计数器列 +1 的旁路字段；
- **异页寄存器**（如 `14df4X`、`14e04X`，属其它表）；
- 这些行与 K 的差**不是** 0x1E 倍数，导致窗口法必然出现大量“非倍数”。

正确做法是**逐行向前、只顺着“单调递减且在窗口内”的计数器列走**，遇到第一条变大/过小即**当场停止**，从而把上述异页、相邻、列+1 行都排除在外。这也解释了原稿“127 条满足 / 1664 条不满足”的假象：不是规则错了，是**扫描口径错了**。

### 3.4 导出 CSV 的 前部 / 后部 列数量（本次确定）

每个单位 id 行整理成 CSV 时，**前部、后部各占多少列按实际结构定**（用户先前估“前部 6 列”不成立）：

- **后部（后面的数据）恒为 3 列**：`+0x1E / +0x3C / +0x5A`（3 个 0x1E 倍数），**全部 1791 条都写**。`+0x1E`=等级下限、`+0x3C`=等级上限（构成范围，见 §3.9），`+0x5A` 待定。
- **前部（前面的数据）最多 8 列**，offset 均为 0x1E 倍数：`-0x1E / -0x3C / -0x5A / -0x78 / -0x96 / -0xB4 / -0xD2 / -0xF0`；**该单位没写的那一列留空**。全量统计 `填充数/1791` 分两类：
  - **核心列（几乎每条都有）**：`-0x78`(1716, 值域 1)、`-0x96`(1708, 值域 3 = **阵营**，见 §3.7)、`-0xD2`(1715, 值域 25 = **坐标行**，见 §3.8)、`-0xF0`(1715, 值域 27 = **坐标列**，见 §3.8)；
  - **附加列（特定遭遇才有）**：`-0x1E`(508；可刷怪标记，取值仅 `1`/`2`，见 §3.5/§3.6)、`-0x3C`(44, 值域 1)、`-0x5A`(417, 值域 3)、`-0xB4`(507, 值域 38)。
  - 值域极小（`-0x78` 恒 `7`、`-0x3C` 恒 `1` 等）的多为**结构标记**；值域大（`-0xB4`（38 种，未知）/`-0xD2`（行）/`-0xF0`（列））的才是各单位差异量。
- 故 CSV 用 **前部 8 列（第3–10列）+ 后部 3 列（第11–13列）**；产出于 `scripts/export-stinit-unit-records.js` → `output/stinit-unit-records.csv`（1791 行，0 缺失地点名）。

### 3.5 发现点：**`-0x1E` 列=该单位**能否从刷怪点刷新

**`-0x1E` 前置列标记的是「该单位槽是否可以从刷怪点刷新」**（用户发现，经全量核对成立）。

- **语义**：`-0x1E` 位**有值** 表示该单位**可被刷怪点刷出**（可重复遭遇）；**无值（留空）** 表示该单位是**固定/摆位放置**、不从刷怪点刷新。
- **取值**：出现时绝大多数为 `1`（**502** 条，=可刷怪）；罕见 `2`（**6** 条，疑似“出击旗”，见 §3.6 待验证猜想）。全量统计：`508/1791` 条带 `-0x1E`（值域 `0x1/0x2`）。
- **关键是“按槽位”而非“按单位种类”**：同一兵种在不同遭遇里可能一次带 `-0x1E`（可刷）、一次不带（固定摆位）。例：`牙コウモリ`/`雷蝶`/`ドリュアス` 等**既出现在“有 -0x1E”集合、也出现在“无 -0x1E”集合**。故此标记是**该掉落槽/遭遇槽的属性**，不是单位种类的固有属性。
- **校验口径（如何判断某一行的 `-0x1E`）**：对该单位 id 行做 §3.3 的“单调递减向后扫码”，看链中是否含 offset `0x1E` 即可（`-0x1E` 寄存器 = `单位id行地址 - 0x1E`）。
- **应用**：在 `output/stinit-unit-records.csv` 中，`前部-0x1E` 列**非空 = 可刷怪**、**空 = 固定摆位**。区分“可重复刷新的杂兵”与“一次性/固定敌人”用这一列即可。

### 3.6 发现点（**带验证的猜想**）：`-0x1E` 值 `2` = **“出击旗”** 而非刷怪旋涡

### 3.7 发现点（**推测**）：`-0x96` 列 = **单位阵营划分**

- **取值分布**（`-0x96` 有值的行，按“填值 → 不同单位种数”，全量 `src/*STINIT.txt`）：

- **佐证（为何像阵营而非其它）**：
  - 值 `3`/`4` 几乎全是**人类 / 有立场的角色**（友方/中立方），与 `2` 的普怪形成语义对比，很符合“阵营/颜色”直觉；
  - 同一单位**可跨值出现**（如 `ドラゴニュート`、`砂鉄の悪漢者`、`水精ティエネー` 同时出现在 `2` 与 `3`，`嫌らしい顔の男` 出现在 `3` 与 `4`）——说明它是**按遭遇槽的子属性**，随该图把该单位当哪一方而变，**与 `-0x1E` 同理，是槽级而非单位种类固有**。
- **⚠️ 未填写的情况（不确定）**：部分单位槽 **`-0x96` 无值（留空）**。全量去重后约 **28 种单位**出现在无 `-0x96` 的槽中（如 牙コウモリ、雷蝶、迷い入った小鬼、ハルピュア、木精ドリュアス、ヘタボウ、ヘタレン 等）。其含义**尚不确定**——可能是这些单位本就极少作为“有阵营的对象”出现（多为固定/特殊），也可能是该字段非必填。**需进一步验证，不应据此判定阵营**。
- **如何验证**：需对照 `AGE.EXE` 读该字段（`单位id行地址-0x96`）的分支逻辑，或结合地图侧阵营/颜色配置（单位卡、图鉴里的阵营标志）交叉核对 `2/3/4` 是否对应红/黄绿/黄三色。
- **对 CSV 的影响**：`前部-0x96` 列 `2/3/4` 可直接按上表解释为阵营；**留空则阵营未知**。

### 3.8 发现点（**采样已验证**）：`-0xD2` / `-0xF0` = **怪物放置坐标（行, 列）**

**`-0xD2`、`-0xF0` 是怪物被放置的坐标**（用户发现，经采样验证成立）：

> 以**地图左上角为原点**，**`-0xD2` = 行（row）**、**`-0xF0` = 列（col）**，**均为 1-based**。

- **取值验证**（全量 `src/*STINIT.txt`，同时有坐标的行 **1715** 条）：
  - `-0xD2`（行）取值集合 `1..25`（25 种）→ 行号；
  - `-0xF0`（列）取值集合 `1..27`（27 种）→ 列号；
  - 二者都是**小正整数、1-based**，正是网格坐标的特征。
- **单图内唯一性**：以 mapNo=2（`調査区域の奥`）为例，该关 10 个单位各占**不同** `(行,列)`：
  `(1,9)牙コウモリ、(5,9)雷蝶、(10,6)迷い入った小鬼、(2,3)キスニル、(8,6)牙コウモリ、(5,1)雷蝶、(8,3)雷蝶、(5,3)迷い入った小鬼、(10,4)牙コウモリ、(6,2)牙コウモリ` —— 同关无重复格，符合“一个位置放一个单位”。
- **⚠️ 缺坐标的情况**：**76 条**行（去重后约 46 种单位）**没有 `-0xD2/-0xF0`**（如 流燐結騎、小鬼族、ガーゴイル、死魂霊、憑魅霊、操霊師ロズリーヌ、地蟲竜アルカトホグ 等）。多为**非网格固定放置**的单位（会途中加入、动态/刷怪点刷出、或无固定落点），与“缺 `-0x1E`（非刷怪点刷新）”的情形相关。**这些单位无固定坐标，不应假定其位置**。
- **对 CSV 的影响**：`前部-0xD2`（行）与 `前部-0xF0`（列）可直接当该单位的**地图格坐标**用；**留空=无固定位置**。

> 注：**同一 `(行,列)` 组合可在不同地图重复出现**（坐标是“关卡内”相对的，各 mapNo 自用一套），故跨图比较时需先限定在同一地图内再判断是否重叠。

### 3.9 发现点（**已验证**）：`+0x3C` 也是 **等级**，与 `+0x1E` 构成**等级范围**

**`+0x3C`（后部第 2 列）很可能也是单位等级，与 `+0x1E` 共同构成一个等级范围**（用户发现，经采样验证成立）：

> **`+0x1E` = 等级下限（min），`+0x3C` = 等级上限（max）**，二者差恒定 ≈ `10` —— 单位等级在该范围内浮动。

- **验证（全量 `src/*STINIT.txt`，1791 条全都有二者）**：
  - `+0x3C > +0x1E`：**1790 条**（`+0x1E < +0x3C`，0 条反向）；仅 **1 条相等**。
  - 差值 `d = +0x3C − +0x1E` 几乎全是**正的小定值**：`d=10` 占 **1635** 条，另有 `d=5`(112)、`d=7`(24)、`d=9`(14)、`d=4`(3) 等少量。
  - `+0x1E` 值域 `1..82`，`+0x3C` 值域 `1..88`（上限整体高于下限）。
- **同单位差值恒定（决定性证据）**：对同一 unitId，其不同遭遇里的 `(min,max)` 对**差值恒为 10**。例：
  | 单位 | 下限`+0x1E` 集合 | 上限`+0x3C` 集合 | 差值 |
  |---|---|---|---|
  | 牙コウモリ | {3,7,a,b,5,8,16} | {d,11,14,15,f,12,20} | 恒 **10** |
  | 雷蝶 | {3,a,9,11,12,5,16} | {d,14,13,1b,1c,f,20} | 恒 **10** |
  | 迷い入った小鬼 | {3,9,10} | {d,13,1a} | 恒 **10** |
  | キスニル | {3} | {d} | 恒 **10** |
  → 下限随遭遇浮动，但 `上限=下限+10` 不变，正是“等级范围”的形态。全量 **324 个单位**中约 **161 个**在不同遭遇里出现多个 `min`（等级随图浮动），而差值始终固定。
- **与 `-0x1E`（可刷怪）的关联**：等级范围恒宽 `10`，配合 `-0x1E`/`-0x96`/坐标列，可判定每个遭遇槽里该单位的等级带。
- **验证方法**：需对照 `AGE.EXE` 读该字段（`+0x1E`/`+0x3C`）的分支逻辑；或看这些 `(min,max)` 是否严格满足 `max−min=10`（当前满足，极强印证“范围”而非“另一样东西”）。
- **对 CSV 的影响**：`后部+0x1E` 与 `后部+0x3C` 一起读为**等级范围**，而非两个独立等级字段。

### 3.10 地图特殊点位（采集/挖掘/出击门/陷阱）坐标与跟随数字（**实测，修正“至多三个”**）

在 STINIT 每个地图块里，`14d740` 起有一段**特殊点位数据**（采集点/挖掘点/出击门/陷阱等），与单位数据**紧贴**（其后即单位计数器 `14dc51` 起的单位槽）。

- **每个点位是一条记录**，寄存器按**点位索引 k**（从 0 起）逐条 +1。核心三字段（相邻三个家族）：
  | 字段 | 寄存器 | 相对 `14d740` 偏移 | 说明 |
  |---|---|---|---|
  | 列 | `14d740 + k` | `+0x00 + k` | 列坐标 |
  | 行 | `14d772 + k` | `+0x32 + k` | 行坐标 |
  | 类型 | `14d7a4 + k` | `+0x64 + k` | 点位类型（采集/挖掘/出击门/陷阱…）|
- **跟随数字个数不固定**：类型之后，不同点位还写了若干**附加字段**寄存器（构成若干组“成对”槽，如 `+0xC9/+0xFB`、`+0x131/+0x163`、`+0x0C8` 等，随类型而定；另有一条 `+0x190` 恒为 `7` 的常量尾）。
- **实测个数分布（本次统计，全量 `src/*STINIT.txt`，不计 col/row/type 与恒 7 尾）**：
  | 跟随数字个数 | 点数 |
  |---|---|
  | 0 | 509 |
  | **1** | **1077** |
  | **2** | **1284** |
  | 3 | 40 |
  → **个数字不定，最常见为 2、其次 1，也有 0 与少量 3**。所以“至多三个”只是上界，**不要再按固定 3 列**。
- **CSV**：产出于 `scripts/export-stinit-special-points.js` → `output/stinit-special-points.csv`（655 关，**2910 个点位**，列 = 地图号/地图名/点序号/列/行/类型/跟随1..N；`跟随` 列数取全量最大=3，个别点位不足则留空）。
- **⚠️ 与单位数据紧贴 / 跨图边界**：特殊点位块之后紧跟单位**计数器区**（`14dc00`..`14dcff`，其 `14dc51`…`14dcc9`）。统计时**边界须在此截断**：**只有 `14dc00..14dcff` 才代表位块结束**，切勿用“任一 `addr ≥ 0x14dc00`”当边界（否则会被 `14e0xx` 配置寄存器早早截断，导致整张图点位丢失——修复前漏掉 `54` 饥狼的黑曜湖等大量点位）。同时按 `eq ... b222` 到下一 `map` 头截断，避免并入下一图数据（如 `14d712`、`14db89` 等前置数组）。
- **点位类型**：`+0x64` 位置值不同对应不同点，`type` 值对附加字段个数有直接关系（如 `2a`(42) 类的点位多为 2 个跟随数字、`1f`(31) 类多为 3 个、`f`(15) 类多为 0 个等，细节待与 `AGE.EXE` 交叉验证）。
- **type → 语义（用户确认）**：`CSV` 的「类型」列对已识别类型补括号注释：
  | type | 语义 | 点数 |

- **验证方法**：需对照 `AGE.EXE` 读特殊点位数组的函数，确认 `col/row` 的确切语义与 `type`→附加字段个数的映射。
