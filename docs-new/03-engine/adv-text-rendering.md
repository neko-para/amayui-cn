## 0. 一句话结论

AGE 的文本是**「GDI 把整串（或逐字）画进"每窗一张的离屏表面"，再按行一块块贴到画面」**：

```
脚本 show-text/display-furigana
   → sub_46BE30 逐字量宽排版（逐字 push 24B 字记录 + 按换行 push 120B 文本记录；注音配对）
   → 生成时就把「该窗全部文本」画进 该窗私有离屏表面 surfaces[20+win]
   → 每帧由主循环泵 `sub_45BE20` 贴出**下一个 24B 记录 = 一个字**（见 §3.3.1；字格页走 `sub_45A940` 一格/拍）
   → 合成：DrawMode=1 走 Scene 的 DrawItem；DrawMode=0 走 dd surface blit
```

⇒ **引擎里"逐字显示"的观感来自"逐行/逐字块被一块块贴出"，而不是"每帧重画整行前 N 字"**；
也**不存在**"每字一个 quad / 字形纹理 atlas"。文字被合成进**每窗一张的表面/纹理**。

### 字重（加粗）落在哪：**面名 × `lfWeight` 的分工**（2026-09，为 T-0035 核对）

**一句话**：引擎的「加粗」= 把 `lfWeight = 700` **请求**交给 GDI 的**族内选面**；引擎自己**不做任何合成加粗**（不双画、不改 `lfWidth`、不换面），配置里也**没有「粗体面名」键** —— 所以「粗不粗」最终由**系统里那个族有没有粗体面**决定。台账条目 `bold-is-lfweight-face-mapping`。

| 跳 | 事实 | 证据（raw） |
|---|---|---|
| 面名 | **只有一个来源键**：`message:Font`（注册时缺省值 `"ＭＳ ゴシック"`）→ `sub_465390` 写 `Font+1260`（注音面硬编码同一串到 `Font+1320`）。运行时另有 `0x1A5`（`sub_4328F0`，不校验）与 `0x2FE`（`sub_432DD0`，校验白名单）能改面名。★全库带 `Font` 的配置键只有 7 个（`set:AntiFontVersion`/`set:UseProportionalFont`/`message:Font`/`message:AntiFontLevel`/`message:UseAntiFont`/`set:EnableAntiFont`/`set:Menu_UseAntiFont`），**没有**任何一个是粗体面 | 111454-111458；23666；78868；41802/41812 |
| 字重 | **只有一个表达**：`0x2BD` ⇒ `Font+1248`（主模板 `lfWeight`）与 `Font+218516`（当前字重）都写 **700**，否则都写 **0**；`0x2BE` 同理写注音 `Font+1308`/`+218588`。初值 **0 = `FW_DONTCARE`**（不是 400） | 33385-33402 / 33405-33422；78854 |
| 重建 | `sub_459F40`（主）/`sub_45A6E0`（注音）把模板 `qmemcpy` 成 8 + 4 个即席 `LOGFONT`（含竖排 `'@'` 面、escapement 2700/1800 变体、面 `"AGE Extend"` 的变体），逐个 `CreateFontIndirectA`；`lfWeight` 一路照抄 | 70941-71191 / 71192+ |
| 落笔 | 排版时把**当前字重**烘进窗样式记录（读 `Font+218516` → 写窗对象 `+188`）；绘制取 `Font+1084`（主）/`Font+1096`（注音）后 `TextOutA`。★描边档 3 会连画 **5 次** `TextOutA`，那是**描边**、不是加粗 | 75335 / 74094 / 68090/68485；68095-68120 |

**推论（对 T-0035 直接有用）**：

1. 「引擎内部不会尝试直接加粗、只有用户选了粗体字体才会粗」**只有一半成立**：引擎确实**不合成**，但它**确实请求 700**；请求落到哪一面由 GDI 决定 —— 这与补丁说明第 6 步「两份额名同为 `Amayui CN`、系统按 Regular/Bold 两面配对；只装一份时『加粗』那部分文本不会变粗」是同一件事。
2. **「真机偏细」的探针已被实测修正（2026-09-15）**：候选表 `Font+201664`（`0x2DC`/`0x2DD`/`0x2DE`）确实是 `EnumFontFamiliesExA` 的族列表（`Proc` 滤 `lfCharSet == 0x86` 且非光栅；`sub_45F6C0` 用探针字 `Font+218524` 删掉缺字形的族），**一个族一条** —— 但这条只能**单向**读：本机两面都装好、且 `lfWeight = 700` 经 `GetFontData` 确证取到 `id6 = Amayui-CN-Bold` 的同一台机器上，候选表里 `Amayui CN` 仍然**只有一条**（另有 `@Amayui CN` 竖排变体，被 `Proc` 的「首字符」判断滤掉）；全库 2925 条枚举记录里，同一个 face 名**从不**以两种字重出现（GDI 每族每字符集只报一条代表面，字重不同的族是**族名本身就带字重**，如 `Yu Gothic UI` / `Yu Gothic UI Semibold`）。⇒「出现两条」确实是「没配成一族」的证据，但「出现一条」**不能**反推「配成了一族」——Bold 缺失、被字符集/缓存挡住时同样是**一条**。 | 74146-74171；74724；75028-75100 |
3. ★**判定「700 有没有落到 Bold 面」必须直接问 GDI**：`tools/font-face-probe.ps1` —— 建 `HFONT` 后 `GetFontData` 把实际选中的那份字体取回来，比 400/700 的 sha256 与 `name` 表 `id6`。实测：`Amayui CN` 700 → `id6 = Amayui-CN-Bold`（且 sha256 `6f336fad…` 与随包 `res/fonts/Amayui-CN_cnjp-Bold.ttf` 的 oid 一致）；对照组 `MS Gothic`（Windows 自带、**无** Bold 面）400/700 取回**同一份**⇒ 静默退回常体这件事，这条探针看得见。
4. 本工程随包的两份 TTF：`name ID 1` 都是 `Amayui CN`，`OS/2.usWeightClass` = 400 / 700，`ulCodePageRange1` 一致（含 cp932）⇒ 在 Windows 上按定义就配成一族；`test/font-bold-face.test.ts` 把这个前提钉成了棘轮。

### 文字成片的白电平 ≈ 0.89×（实测；机制未定位，`tickets/T-0042`）

**一句话**：引擎**自己画的文字**（ADV 正文、设置界行标签、字体样例预览、直绘串）在成片上的核心亮度恒在 **226-232**；
而**同一屏的美术图**（按钮面 `(254,243,229)`、纯白高光、ON/OFF 图、局部化 UI 图）**逐像素一致**（引擎 vs 模拟器：
米白面 9542 vs 9553 px、纯白高光 374/374）⇒ 差异只发生在"引擎画的文字"这一路，**不是整帧色调曲线**。

| 判据 | 数据 |
|---|---|
| 常数性（不是与场景混合、也不是重采样） | 字体样例预览横跨「亮天空→暗照片」，背景 7→49 时核心只动 **0.3**（若是 α 混合/重采样应按 `(1−峰值覆盖率)` 随背景走）；整段 **0 个 255** 像素 |
| 取色链（这一档发生在绘制**之后**） | 行路径 raw 79666、ADV 路径 raw 79259-79273 都是把 `Font+1360`（= 脚本全局 `f807b`，序章 `0xFFFFFF`）原样交给 GDI ⇒ 颜色链上没有问题 |
| 已排除 | `message:MesWinAlpha`（用户实测 0/32 都无变化）、配置色 `adcd`（真机 SAVE.DAT 全表无 0xE4/0xE6）、AA 门 `Font+1352`、`set:DrawMode`（引擎缺省 0，两边一致）、缩放/滤波（任何内部尺寸×放大都留 255）、调色板（引擎无调色板 API）、窗对象颜色对 op（`0x25E/0x25F/0x131/0x141` 全库脚本零使用） |

台账条目：`text-white-level-on-composite`（E4，guard = `test/draw-string.test.ts` 等三处填色断言）。

#### 3.3.1 为什么是"一个字"而不是"一行"

早先把 24B 记录当成**行记录**（于是"一步 = 一行"），据此把重写侧的显现预算算成
`行数 × MessageSpeed` —— 结果**整段快了"每行字数"倍（~14×）**，设置里的「显示速度」滑条在
emulator 里几乎看不出效果（用户实测"文字出现的速度几乎没有变"）。实证（`sub_46BE30`，raw 83363-83997）：
**推送 24B 记录的那一行就在"逐字循环"里面**：

```c
if ( **(BYTE **)ArgList )                       // 83571：还有字符
  do {
    v24 = *v111;                                // 83576：当前字节
    if ((unsigned __int8)v24 >= 0x20u && ...)   // 83578-83592：解**一个**字符
        String[0] = v24;                        //   单字节
    else { *(_WORD *)String = *(_WORD *)v111; v112 = 2; }   //   或双字节
    String[1] = 0;                              // 83593
    GetTextExtentPoint32A(hdc, String, strlen(String), &psizl);   // 83596：量**这一个字**的宽
    v25 = psizl.cx + *v23;                      // 83597：本字右边界
    v27 = sub_475CF0(win, v25, v93);            // 83601：越界判据（bit0 右 / bit1 下）
    if (v27 & 1) { …换行：push 120B 文本记录(sub_45E870, 83655)… }   // 83607
    …
    sub_455ED0(_this, v5 + 20, x, y, String, Font+1360, Font+1364, Font+1372, 0, 1);  // 83832：画这一个字
    v122[0] = 0; v122[1] = v75; v122[2] = …; v122[5] = win[284];
    sub_45D120((_DWORD *)(v77 + 44), v122);     // 83918：push 一条 24B 记录（★就在这个逐字循环里）
  } while ( *v111 );                            // 83920：下一个字符
```

- `String` 是**单个字**（`String[1] = 0`；双字节时 `*(_WORD *)String = *(_WORD *)v111`），
  `strlen(String)` / `GetTextExtentPoint32A` 都按它量宽；
- `120B 文本记录`（`sub_45E870`，83655）才是**按换行**压的；24B 记录与它**不是**一回事；
- 注音标记 `[+0] = 1`（`*(win+48 - 24) = 1`）是给**某个字**打标，`sub_45BE20` 的 `while (rec[0])`
  只是把跟在这个字后面的注音记录一起贴掉；
- ⇒ **一步 = 一个字**、节拍 = `MessageSpeed` ⇒ 整段耗时 = **字数 × MessageSpeed**。
- ★**注音不占独立一步**：排版收尾（raw 83988-83997）把本文词**最后一个字**的 24B 记录标 `[+0] = 1`，
  紧接着 push 注音自己的记录（`sub_465A20`，raw 79020+）⇒ 上面那个 `do { 贴 } while (上一记录[+0])`
  让「本文末字 + 它的注音」在**同一步**贴出。所以逐字期间注音**既不提前、也不延后**：它跟着本文词的
  **末字**出现（`display-furigana` 的 op2 本文词就是"那个词"）。重写侧对应物 = `RubyGlyph.from`
  + `visibleRubyInLine`（`tickets/T-0037`）；旧实现「该行有 ≥1 字就把整行注音画出来」是错的。
  `INITREGMES.txt:6 i1b5 19` = 25ms/字（脚本自己写的默认），随包 INI 的 `MessageSpeed=5` = 5ms/字，
  滑条 `100 - 值` ⇒ 1..99ms/字（一页 40 字 = 40ms..4s，旋钮手感正常）。

**"逐字/逐行"的真正驱动**（第二层能力，指令枚举不出来）：

### 3.3.2 ★逐字期间的输入出口：点击 ⇒ **立刻整页贴完**（不推进页面）

- 主循环分支顺序（raw 21109 → 21154 → 21158 → **21176** → 21182 → 21224）：`0x400` → `0x40` → `0x8000000`(ADV) →

  每帧 `sub_409400`，**不派发脚本**，等待泵这一帧根本不会被调到。
- `sub_409400`（raw 13780-13970）分两半：前半扫 1..9 号 `0x300` **闸门槽**（有槽活跃 ⇒ `Engine[489860] = 1`，

- **输入出口**（raw 13931-13946）逐字等价：

### 3.4 合成到画面
| 路径 | 方式 | 证据 |
|---|---|---|
| `DrawMode=1` | 文本窗的每行/每注音字都是 **Scene 的 DrawItem**（`Scene+1032` map，key = id = 层序）；帧末 `sub_4B4040(Scene)` 按 id 四路归并刷出 → EndScene → Present | 136821-136942；136838 |
| `DrawMode=0` | 文本画进**私有 dd 表面**后由 `sub_45BE20` **逐字 blit 到 dd 表面 0**（24B 记录 = 一个字；见 §3.3.1）（`win+4`，构造置 0 且从不改写）；`sub_43D870` 即 `ddCpySpriteSurfaceFast` | 72427-72437；90446；48907 |

- GDI 的 DC 必须 `ReleaseDC` 解锁后表面才能被后端使用 ⇒ **文字一定在 Present 之前进入表面**，不可能"Present 后补画"（配对证据：68088→68129、86374→86379、89124→89129）。
- **背景/边框不是纹理**：dd 路径用 `ddFillSurface` 填底色；D3D 路径用 DrawItem 的颜色/alpha 字段。窗体的"边框图"由脚本用普通 `draw-texture` 画（`0x82` = `sub_466000` 重绘该窗全部图元）。
- **淡入**：不存在"把文字颜色朝背景插值"的代码。dd 路径靠"整窗画在离屏表面 → 逐行贴出"；D3D 路径靠每行 DrawItem 的**颜色动画窗**，时长 = `MessageSpeed * MessageFade / 100` ms（5×250/100 = 12）。

## 7. 与 emulator 现状的差距（本节是产物状态，不是分析依据）

**本次分析顺带查实的既有错误**：

1. **`message:MesWinAlpha` 误绑**：`engineConfig.ts` 把 `message:meswinalpha` 绑到字段 `21668`，
   而 `21668×4 = 86672 = Font+1376 = message:MessageSpeed` —— **两个键绑到同一字段**，后写者胜（= 8）。
   实际 `MesWinAlpha` **不进任何持久字段**，只由 `0x131`/`0x141` 按名读写。
2. **`0x7F` 的注释错**：它读的是 `_this[21668]` = **`message:MessageSpeed`**（不是"消息窗 α"）。
   实现（读字段）是对的，注释与 `0x131` 的说明把它写成了 α。
3. **`0x74` 的语义错**：它是 **`SetMessageSpeed`**（写 `Engine[21668]`），不是"放大百分比"；

## 9. ★「白字永不纯白」：字形覆盖率 α 合成（`tickets/T-0042`，2026-09-16 定位）

引擎**自己**光栅化字形（不是 GDI 的色彩问题，也不是调色/缩放）：

| 环节 | 位置 | 事实 |
|---|---|---|
| 覆盖率位图 | `sub_46F2D0` raw 86146（`sub_471180` 同族） | `GetGlyphOutline(hdc, ch, v62, …)`；`v62` 在 raw 86028-86038 定：`Font+1352 != 0` ⇒ `5`(`GGO_GRAY4_BITMAP`)，且 `Font+218500 == 1` 时 `6`(`GGO_GRAY8_BITMAP`)；`Font+1352 == 0` ⇒ `1`(`GGO_BITMAP`，1bpp) |
| 行步长 | raw 86163-86166 | AA 开 ⇒ 每像素 1 字节；AA 关 ⇒ `4*((w-1)>>5)+4`（1bpp 位平面） |
| **逐像素合成** | `sub_46D9F0`：16bpp 分支 raw 84891-84904 / **32bpp 分支 raw 84956-85011** | `v29 = 255*cov`；`v30 = v29/17`（GRAY8 用 `/65`，魔法常数 `0x78787879`/`0x7E07E07F`）；`dst = (C*v30 + dst*(255-v30))/255`；`v30 == 255` 才写不透明 |
| 表面位深分流 | raw 84873 `if (dword_5518C0 == 16)` | 16bpp 走 RGB444 nibble（`v18 = v17>>4`，`v18 == 15` 才满），32bpp 走真 α |

**要点：`α = 255*cov/17` 的上限是 240（cov=16），实测平台对应 cov=15 ⇒ α = 225/255 = 0.882**
⇒ **填充（含"白字"）永不不透明**，"白字"必然落在

```text
dst = α·255 + (1−α)·(填充之下已经画好的东西：描边)
```

真机核对（序章旁白，`x=586` 剖面：描边像素 ≈ `(63,32,16)`）：

```text
(225 + 30/255·63, 225 + 30/255·32, 225 + 30/255·16) = (232.4, 228.8, 226.9) ≈ 实测 (233,230,228)
```

这条**同时**解释了 `tickets/T-0035` 与 `T-0042` 两个现象：

1. **偏灰**：α < 1（满覆盖也只有 0.88-0.94）；
2. **偏粗/偏硬**：覆盖率在边缘有斜坡（多像素渐变），而 emulator 之前按"1bpp 阈值化"把斜坡切掉
   ⇒ 边缘变成硬台阶、笔画在固定阈值下反而更粗；
3. **逐元素差异**（226/230/244）：`cov` 与描边色不同；
4. **"与背景无关"**：填充的 backdrop 是**同一表面里已经画好的描边**，不是场景背景
   （早期把它当"与背景的 α 混合"解出来 0.855-0.866，方向对、对象错）。

**配置门冲突（记录在案）**：`set:EnableAntiFont` 的内建默认是 **0**（raw 111707 `v13 = 0` 后
`sub_434D00(v2, aSetEnableantif, &v13)`），真机 `SYS4REG.INI` 又**没有 `[set]` 段** ⇒ 按配置推导
`Font+1352 == 0` ⇒ 1bpp。但 **1bpp 分支的 `v18/v31` 恒满 ⇒ 输出纯白 255**，与实测 α<1 不可能同时成立
⇒ 引擎运行期走的是**覆盖率路径**。产品侧以**像素判据**为准（emulator 的 `antiAlias = true`）。

### 9.1 写入语义的第二半：`A = max(A_dst, α)`（目标透明时字按 α 落到**场景**上）

α 不只是"混合权重"，它还会被**写进目标表面的 alpha 通道**（`sub_46D9F0` 的 32bpp 分支，
机器码 0x46DDC0-0x46DE7E 逐条核对；`0x80808081` 魔数 `>>7` = 除 255）：

```text
if (α == 255)        pixel = C | 0xFF000000          // 满覆盖 ⇒ 纯色不透明
else if (A_dst == 0) pixel = C | (α<<24)             // RGB = C 原样、A = α
else                 RGB = (C·α + D·(255−α))/255     // D = 表面已有像素
                     A   = max(A_dst, α)             // ★取 max，不是 source-over 的累加
```

⇒ 目标表面**不透明**时（消息窗表面有底色 ⇒ `A_dst = 255`）这条退化成"RGB 按 α 混合、A 恒 255"
（上面 §9 的公式就是它）；目标表面**透明**时（`0x204` draw-string 的槽表面是
`create-texture` 出来的空白 **A8R8G8B8**，`sub_48AC40` raw 107006-107070）表面 alpha 就等于覆盖率 α，
随后 `draw-texture` 按它合成 ⇒ 字落在 `α·RGB + (1−α)·场景`。两条独立旁证：

- 槽里**没被字涂到的像素 A=0**（RGB 也 0）⇒ 若贴出时不认 alpha，设置界每行都会出现**黑块**；
  真机看不到黑块 ⇒ 贴出确实在用表面 alpha；
- 设置界**行标签**（`CONFIG1.txt:2743-2760` 的 bbd 样式：`i076 ffffff` + `i077 ffffff` + `i078 1`，
  **填充与描边都是白**）贴在深色行底板（≈`(65,47,40)`）上 ⇒ `α·255+(1−α)·底板` = **(233,231,230) 暖**
  —— 与真机实测区间 **226-234（暖）**一致；若按不透明合成则应是纯白 255。
  `set-font`(0x1A5) 只换**面名**、**不动颜色**（`sub_4328F0`），所以"描边是暗色"这条假设不成立，
  该元素也没有别的绘制路径（`grep draw-string src/CONFIG1.txt` 只有这几处）——**元素归属已确证**。

emulator 实现（`src/renderer/text/raster.ts`，常量 `TEXT_FILL_ALPHA` 在 `src/text/layout.ts`）：

| 路径 | 目标表面 | 做法 |
|---|---|---|
| 消息窗 `rasterFrame` | 不透明（有底色） | 描边副本不透明先画 + **填充那一遍** `ctx.globalAlpha = TEXT_FILL_ALPHA` ⇒ canvas 的 `dst = α·C + (1−α)·dst`（与引擎等价） |
| 纹理槽 `0x204` | 透明 | `drawGlyphPassesOnSurface` **逐像素复现引擎的写入**（`engineGlyphPixel`：`A = max(A_dst, α)`、`A_dst==0 ⇒ RGB=C`、否则 `(C·α+D·(255−α))/255`）—— canvas 的 `source-over` 会把描边遍 + 填充遍的 alpha 累加成 1，正是"行标签纯白"的来源 |

同屏 OPTION 对照（本机 Electron 截图实测）：字体样例文字 255 → **225**（真机 226-228）；
设置界**行标签** 255 → **(233,231,230) 暖**（真机区间 226-234 暖）；ADV 正文 255 → 225
（真机 229-232 暖 —— 这一档的差是**颜色来源**问题：真机填充的 backdrop 是暖暗色 ≈`(63,32,16)`，
emulator 用黑描边/黑窗底，沿 `T-0035` 的配置色面）。

台账：`text-glyph-coverage-alpha-composite`（写入语义 + 两条路径的现状）、
`glyph-raster-direct-to-slot`（`0x204` 不是 GDI：`sub_456710` 体内没有 `TextOutA`，它走
`sub_471180`/`sub_46F2D0` 的同一套覆盖率路径）。

### 10.2b ★配色表的默认值是**引擎内建**的

用户问："就算没有 SAVE.DAT，默认值应该也是有的？这部分设置也没法改。" —— **是，且已核实**：

| 环节 | 锚点 | 事实 |

所以 emulator 用 mode 3 也没错。

### 10.2c 填充之下垫的到底是什么：脚本画的"底板"

`src/SN0000.txt:3090-3098` 在旁白前建/画一块**底板**：`create-mesh 19640` +
`draw-texture 19640 11 0 0 43e 95 5d 22c`（纹理槽 0x11 的 1086×149 图 @(93,556)）+
`set-draw-color-alpha 19640 0 (global-int f807d) (global-int a9db)`（`f807d` = 消息窗透明度档
192/160/128、`a9db` = 0 = **纯黑**）⇒ 底板 = **黑 @75%**，压在场景上 ⇒ 文字背后的底色 ≈
`0.247 × 场景`（暖色天空下正是 ≈`(63,32,16)` 这种暖暗值 ✓，也解释了"文字核心与背景无关"：
底板固定占 3/4，场景只剩 1/4，再被 `(1−α)=0.118` 压到 ≈3%）。

⇒ 机制上 `α·255 + (1−α)·(底板色)` = `(232.4,228.8,226.9)` ≈ 真机实测 `(233,230,228)` ✓；
而 emulator 的画布是**不透明描边先画、填充按 α 叠上去** ⇒ 填充之下是**纯黑描边** ⇒ 225（中性）。
**两边差的就是"填充之下垫的是描边还是底板"**：引擎 mode 3 的四向描边只覆盖字形外扩 1px 的一圈、
其**内部**仍是底板（`sub_46D9F0` 的 `A_dst == 0 ⇒ RGB = C` 只在**没被前一遍写过**的像素上发生），
而 emulator 的 canvas 描边是"把整个字形轮廓填成描边色"⇒ 内部被描边色占满。
★**`192/160/128` 的语义（用户 2026-09-16 确认）**：它们不是文字层的 alpha，而是**背景整体遮罩**
的三档——`set:設定` 里的「メッセージウィンドウ透明度」三档，经 `f807d` 作为
`set-draw-color-alpha 19640 0 (f807d) (a9db)` 的 **alpha 实参**（= 该遮罩项的**不透明度**；
遮罩色 = `a9db` = 0 = 纯黑）⇒ **只改文字背后那块遮罩的深浅**：
`192 ⇒ 遮罩不透明度 0.75`（场景只剩 25%，与实测 backdrop ≈`(63,32,16)` 相符）；`128 ⇒ 0.50`（场景剩 50%）。
⇒ 判据可以量化（同一句旁白，只切档）：

| 模型 | 文字核心 | 切档（192→128：遮罩 0.75→0.50，露出的场景 25%→50%）时的位移 |
|---|---|---|
| **A. 填充之下 = 遮罩后的场景**（本文档主张） | `α·255 + (1−α)·(1−f807d/255)·场景` ⇒ `225 + 0.118·(63,32,16) = (232.4,228.8,226.9)` ✓=实测 | 场景项**翻倍** ⇒ 核心**上升**约 `0.118·0.25·场景 ≈ 3-8` 级 |
| B. 填充之下 = 不透明黑描边（emulator 现状） | `α·255 + (1−α)·描边(0) + …` ≈ **225**（中性） | 描边把遮罩整个挡住 ⇒ 位移 ≈ `0.118²·0.25·场景 < 1` 级（基本看不出） |

⇒ 真机切档：**核心亮度明显跟着变（3 级以上）⇒ A 成立**（emulator 的"描边整块垫在填充下"是错的，
要改成"填充落在遮罩后的场景上"）；**几乎不变 ⇒ B 成立**（那也是本票"更亮"只在暖调上差 7-8 级的来源）。
在那之前**不改**渲染代码（机制优先；T-0042 第 1 次变更的教训）。

### 10.3 两条绘制路径的合成口径不同（这是 (α, 填充色) 无法唯一反解的原因）

| 路径 | 表面 | 贴出 | 可见值 |
|---|---|---|---|
| `0x204` draw-string（设置界行标签/行值） | `create-texture` 的 **A8R8G8B8**（透明，`sub_48AC40` raw 107006-107070） | 当**纹理**画 ⇒ 逐像素 α | `α·(表面 RGB) + (1−α)·场景`（**两次 α**：填充那次 + 贴出那次） |
