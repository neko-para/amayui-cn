### 1.1 武装 bit30 的**真值表**（本轮新增，修正上一轮）

0x72（`sub_41EEF0`）重跑到 `LABEL_17`（raw 28539）时：

```
28540:  if ( (effectFlags & 0x8000000) == 0 ){        // ★外门：bit27（ADV 显示位）
28545:      Engine[122371] = win;
28546:      sub_45A940(Font, win, -1, Engine+107705);   // 查格数（写 107705）
28547:      effectFlags |= 0x80000000;                  // 置 bit31（等待推进门）
28549:      if ( (effectFlags & 0x40000000) == 0 ){     // ★内门：bit30 原本为 0
28551-3:        effectFlags |= 0x40000000; Engine[107704] = 0; sub_453A90(Engine+430600); } }
```

| 状态 | 结果 |
|---|---|
| bit27 == 0 且 bit30 == 0 | **武装**：置 bit30 + `Engine[107704]=0` + 重启节拍（▼ 从第一帧重来） |
| bit27 == 0 且 bit30 == 1 | 只置 bit31；**不碰**游标/节拍（▼ 平滑继续） |
| **bit27 != 0** | **整块不执行**：bit30 保持 0、格号不归零、节拍不重启 |

`bit27` 在 `LABEL_17` 处是否为 0，由 raw 28489-28520 决定；**另有两条让它保持 1 的路**：

- **`Engine[489984]`（= `_this[122496]`）非 0** ⇒ raw 28518 的 `!_this[122496]` 失败 ⇒ 不清 bit27 ⇒ 外门关闭。
  它的**唯一置 1 点**是 raw 20274（`message:AdvanceMesOnWheel & 2` 且本帧无 `0x50` 输入位 —— 即**滚轮/自动推进**
  那一支），清 0 只在 opcode `0x71`（raw 28444/28449/28457）与复位（17966/22598）⇒ **粘滞**。
- **`Engine[5660]`（= `_this[1415]`，"取消/跳读中"）非 0** ⇒ raw 28487-28488 把 `v17 |= 0x40` ⇒ 同样不清 bit27。

★**真机 SYS4REG.INI 实测**（用户机器，57 行）：`AdvanceMesOnWheel=3`（**bit1 已置**）、`ReadTextSkip=0`。
⇒ 「滚轮推进 ⇒ `Engine[489984]=1` ⇒ 之后门不再武装」在真机上是**可达**路径（这是上一轮完全没建模的一格）。

  票面 notes 早期写的「`a9dd & 2` ⇒ 正文填充随角色」才是对的）。
- 既然 `f807b` 最终 = `0xFFE100`（阿瓦罗黄），而 `adcd[0] = 0xFFFFFF` ⇒ **CHECKCONFIG 执行那一刻 `14acda ≠ 0`**
  （= 上一场景的说话人），之后（SN0000 重放里 `mov (global-int 14acda) …` 共 60 处）它才变成 0。
- `3f36 = 14` 不是 CHECKCONFIG `:42` 写的那个 0 ⇒ 它被**后面**的帧覆盖（`src/NOVEL.txt:26 mov (global-int 3f36) e`）✓。

### 5.2 ② 的真正成因（替换 §2 的 `sub_45F1B0` 主假设）

```
读档 → 引擎先跑 CALLBACK_LOAD.BIN（raw 19916；emulator 日志「帧 0 ← CALLBACK_LOAD.BIN … exit 后再装 SYSTEM4.BIN」）
       ★ src/CALLBACK_LOAD.txt:197-227 会在读档时**重算** global 14acda（当前说话人）：
              :197-200  4fd6 < 0  ⇒ 14acdb = 0; 14acda = 0
              :208-211  查表 14acdc[4fd6] → 14b0c4[…] ⇒ 14acda = 查到的说话人
              :215-227  否则按 14acdb 取 1/2/3

       ⇒ CHECKCONFIG:63-64  f807b = adcd[14acda]（a9dd=2 时）⇒ i076 应用到 Font+1360
⇒ 引擎：14acda 取到「旁白」那一路 ⇒ adcd[?] = 0xFFFFFF ⇒ **白** ✓
⇒ emulator：14acda 停在上一场景（阿瓦罗）⇒ adcd[阿瓦罗] = 0xFFE100 ⇒ **黄** ✗
```

**⇒ 要修的是 `CALLBACK_LOAD.BIN:197-227` 这条「读档重算当前说话人」的链（及其输入 `4fd6`/`14acdc`/`14b0c4`），
不是 `sub_45F1B0` 的文本记录。** §2 的 `sub_45F1B0`/记录回写仍是**真实的机制**（raw 76940-76962 确实存在），
但它**不是**本次黄/白差异的来源——本轮实测把它降为「待核的第二机制」。

★**注意**：`14acda`(0x14ACDA)、`14acdc`(0x14ACDC)、`14b0c4`(0x14B0C4) 都 **大于** SAVE78.DAT 实测的 int count
（1,015,792）⇒ 它们**不在读档的 memcpy 范围内**；而 `4fd6`(0x4FD6=20,438) 在范围内（被还原）。
`Engine[382952]`（池容量，raw 22263 从 `Engine[699180]` 取）与「文件里的 count」到底是不是同一个数，
**正是上一轮出错的地方**（它把两者当成同一个，于是推出「池外 ⇒ 不还原」）；本轮把这条登记为
**必须先实测的量**（活体 `Engine[382952]` vs 文件 count），在此之前不要再据此下结论。

### 5.4 `global 0x1399`（= 5017）的语义与「路由表 19/7/6」算术（2026-09-26，用户提问后补算）

`0x1399` 是**「本次登记哪一套热点」的选择子**，只在 `src/SN0000.txt:48-119`（`label_00000320`）里被判两次；
极性已由**代码**定案（`handlers/control.ts:109-134` 的 `op_jcc`：`cond != 0` 走**操作数 2**；
而反汇编的 `jcc <cond> ffffffff <label>` 里 `ffffffff` 就是"操作数 2 = 落下一句"，`label` 是**操作数 3**）
⇒ **`jcc <cond> ffffffff <label>` = `cond == 0` 才跳** ✓（与项目既定 gotcha 一致，**不是** emulator 的极性 bug）：

| `1399` | 登记的内容（i090 条数） |
|---|---|
| **2** | 走 `:50-51` 不跳 → `:52-66` 共 **13** 条（12 条侧栏/页面热点 + `:66` 满屏） |
| **1** | `:51` 跳到 `:71` → `:72-73` 不跳 → 只登记 **`:74` 1 条**（矩形 x=0x4ce..+0x32 = **1230..1280**，y=0xe9..+0x104 = **233..493** = 侧栏条；ENTER = `label_00000c74`，LEAVE/CLICK = `label_00000e74`＝裸 `ret`） |
| 其它 | `:73` 跳到 `:76` → 屏幕上 **0 条**，只剩 `:79-111` 的 **6** 条屏幕外按键绑定（ENTER/LEAVE = `ffffffff`） |

（三种情况下**都会**继续执行 `:76-116` 的 6 条屏幕外绑定，然后 `:117 i094`、`:119 ret`。）
⇒ 路由表总数只能是 **19**（13+6，`1399==2`）/ **7**（1+6，`1399==1`）/ **6**（其余）。

**⇒ 实测 `cursor=12/19` 说明 emulator 的表是「`1399 == 2` 时建的」**；而现在读到的 `1399 = 1`
（用户独立实测也是 1，见其 2026-09-26 提问）**只表示下一次 `call label_00000320` 会只登记 `:74` 那一条**，
**不代表当前表里只有 7 条**。⇒ §5.3 的实测（悬停派发 + ▼ 重启）成立，① 仍未收口。

### 5.6 「普通移动不会重置」——边沿触发实测 + 两类读档路径的表差异（2026-09-26，回答用户「从逻辑上没有理由 hover 会重置动画」）

**(a) 引擎的派发是边沿触发的**（不是"每帧看鼠标"）：`sub_403E70`（raw 9917-9955）只在**悬停下标变化**时
返回 label（`[7468]` 与 `[959]` 比较；变化时先给旧项的 LEAVE、再给新项的 ENTER），否则恒 -1。
实测（19 条表的状态下）：

| 动作 | 日志 |
|---|---|
| `move` 从窄侧栏条 `(1240,300)` → 正文 `(640,360)` | `hover-leave 0x4a3 cursor=12/19` + `hover-enter 0x38f cursor=12/19` + `[cell] k=0`（区域**变了** ⇒ 派发） |
| `move` 在**同一热点内** `(640,360)` → `(700,400)` | **一行 `[hover-label]` 都没有** ⇒ 不派发、不重启 ✓ |

⇒ **用户的判断成立**：同一区域内移动光标，引擎**什么都不做**（没有"理由"重置任何动画）。
只有**跨区域**（悬停下标变化）才派发；而在刚读档的初始态（表 = 7 条，见 §5.5），普通移动连"跨区域"都产生不了 ⇒ 完全稳定。

**(b) 引擎为什么会在"跨区域"时动 reveal 状态**（这不是随手清动画，是设计）：
`:74`（窄侧栏条）的 ENTER = `label_00000c74`，它做的是 **`:125 i093`（关掉消息面显示态）+ 画侧栏按钮 + `:147 wait`**
= **「打开侧栏面板」**；为避免正文卡在半显现，`sub_4051A0` 先 `sub_45A940(..., -2)` 把这一页正文**收尾**，
顺带清掉 ▼ 的武装位（随后门重跑再武装 ⇒ 帧号归零）。`set:ControlDisibleCursor` 这个配置键
（真机 INI 里没有 ⇒ 取默认 0）存在的意义正是"**关掉这套『光标控制』**"——即引擎作者知道这条会动光标/显现状态。

**(c) ★emulator 侧的真 bug（两类读档路径不一致）**：

|---|---|---|---|
| `op load-from-title --slot 78`（**冷启动**） | **2**（表 19，派发的是满屏 `label_00000e78`=0x38f） | 19 | **会**派发（含满屏热点）✗ |
| `op load-from-adv --slot 78`（**游戏内读档**） | **1** | 7 | 只有那条窄条可命中 ✓ |

（`1399` 还是旧值 2）⇒ **顺序 bug**，与引擎行为不符、也正是用户先前在模拟器里看到"hover 就重启"的来源。
**⇒ ① 的修法不是动 ▼ 逻辑，而是把「读档池还原 vs 帧续跑」的先后在冷启动路径上也对齐。**

### 5.7 ★「从 TITLE 读档」与「从侧边栏读档」的具体区别（2026-09-26，回答用户提问）+ §5.6 归属订正

**(1) 读档动作本身**：两条入口**完全同一条** —— `src/SAVE.txt:935` 的 `i1a1 (local-int 12) (local-int 214)`
（= `0x1A1` 全量，`sub_410160(…, a6=1, a7=1)`）；**`i19f`（短读档）全语料 0 处**（`rg -n "i19f" src` 空）
⇒ 引擎里不存在"另一种读档"；两条入口都要走 `SAVE.BIN`（`load-from-title` 的 op 日志也是进同一个 SAVE 画面）。

**(2) 所以差别只能来自「读档**没有**覆盖的东西」**。读档覆盖的：3 条帧记录、三张 ip 表、
三个池的 `0..文件 count`、图像/记录清单、两张面板（`sub_403EF0`）、`CALLBACK_LOAD.BIN` 收尾。
**不覆盖的只有两类**：

- (a) **脚本全局里下标 ≥ 文件 int count 的槽**：SAVE78.DAT 的 count = **1,015,792**，而
  `f807b`(1,015,931)、`14acda`(1,356,506)、`14acdc`(1,356,508)、`14b0c4`(1,358,532)、`708ada`(7,375,578)
  **都不在文件里** ⇒ 装载只 `memset 0..Engine[382952]` + `memcpy 0..文件 count` ⇒ **这些槽沿用读档前那一场戏的值**；
- (b) 引擎侧字段（面板 `shown`、`Engine[489984]`…）：面板被装载点复位、由页入口 `i094` 重开 ⇒ 无影响。

**(3) 直接从 SAVE78.DAT 解出的关键事实**（用 emulator 自己的 `decodeEngineSlot`，只读）：

| 槽 | 文件里的值 |
|---|---|
| `0x1399` | **2** |
| `0x139a` | 0 |
| `0xa9dd` / `0xa9de` | 2 / 1 |
| `0x4fd6` | 0 |
| `0xadcd` | `0xFFFFFF` |
| `0xf807b` / `0x14acda` | **超出文件 count ⇒ 文件里根本没有** |

**(4) `1399` 的两个取值来自哪**（`SYSTEM4:231-236` 与 `NOVEL:80-85` 是**同一段**，都在各自 `i0ae` 之后）：

```
label_…:  i20e
          call label_…
:234/83   mov (global-int 1399) 1          ← 无条件先置 1
:235/84   jcc (global-int 139a) ffffffff label_…
:236/85   mov (global-int 1399) 2          ← 只有 139a != 0 才置 2
```

⇒ **`139a == 0` ⇒ 重算成 `1399 = 1`**（只登记窄侧栏条 ⇒ 7 条表）；`139a != 0` ⇒ 2（满屏热点也在 ⇒ 19 条表）。
而**存档里存的是 `1399 = 2`、`139a = 0`** —— 二者本来就**不一致**（存档那一刻的 2 是玩家碰过侧栏条后
被 `SN0000:148` 置的，之后 `139a` 又回 0）⇒ **装载后若那段场景入口重跑，`1399` 被归一成 1；不重跑就留着 2。**

**(5) ⇒ 这就是「入口不同、结果不同」的唯一来源，与实测吻合**：

| 入口 | 装载后 `1399` | 路由表 | 普通悬停 |
|---|---|---|---|
| 从 TITLE（冷启动） | 留着存档的 **2**（那段入口没跑） | **19**（含满屏热点） | **会**派发 ⇒ ▼ 重启 |
| 从侧边栏（游戏内） | 被重算成 **1** | **7**（只有窄侧栏条） | 不派发 ⇒ ▼ 稳定 |

★**归属订正（撤回 §5.6(c) 的结论）**：按存档 `1399 = 2` + `139a = 0`，**"归一成 1"才是与场景入口口径一致的那个**，
所以**异常的是冷启动那一次**（它没跑到 `SYSTEM4:234-236`/`NOVEL:83-85`），不是游戏内那一次。
用户的真机口径（两个入口都稳定）⇒ **引擎在两条入口上都会归一**（那段场景入口在两条路上都跑了）
⇒ emulator 要修的是「冷启动装载后的续跑没有经过场景入口那段」。

**(6) 同样地，② 的黄/白也落在 (a) 类**：`f807b`/`14acda` 都在文件 count 之外 ⇒ 从侧边栏读档时沿用
上一场戏（SC0000/阿瓦罗）的值 ⇒ 黄；从 TITLE 读档时沿用 TITLE 那套（碰巧良性）⇒ 白。
**⇒ 「同一存档、不同入口给两种结果」是同一个根因（"读档不覆盖的槽沿用旧值"），修法一处：**
让 `(文件 count, 引擎实际会用的上界]` 这段在装载时**被归一**（引擎的 `memset 0..Engine[382952]` 是这条；
若实测 `Engine[382952] == 文件 count`，则必须靠场景入口的确定性重算，而不是沿用旧值）。

## 6. 实例起不来的原因（回答用户 2026-09-26 的提问）

**症状**：`amayui_emulator action=start` 之后跑 `action=op load-from-title --slot 78` 立刻失败：

```
Error: waitTicking(t0187b) 超时：实例 t0187b 的页面在（viewers=1）但**帧循环停摆**
       （snapshot 报"没等到帧边界"）…
```

**根因**：`action=start` 起的是**全新实例**，它的 `.tmp/instances/<id>/{base,overlay}` 里**没有玩家数据** ⇒
`SYS4REG.INI` 与 `SAVE/SAVE.DAT` 都不在 ⇒ `SYSTEM4.txt:71` 的 `load-int (global 5)` 读到 **0** ⇒
`:72 jcc (global-int 5) → label_0000068c` = **jcc「v == 0 才跳」** ⇒ 跳进 `INITCONFIG/INITCHARM` 分支
⇒ 实例停在 **首跑配置向导**（`INITCONFIG0..4.BIN`），而那个向导**等输入**、不会产生帧边界 ⇒ `waitTicking` 超时。
（当时的 `action=query frame` 正是 `[2] INITCONFIG4.BIN ←cur`，`capture` 是一片白。）

**修法（已按此跑通）**：在**第一次 `action=start` 之前**把玩家数据放进实例可见目录：

```powershell
New-Item -ItemType Directory -Force -Path .tmp/instances/<id>/base/SAVE | Out-Null
Copy-Item <带真存档的实例>/base/SAVE/SAVE7* .tmp/instances/<id>/base/SAVE/ -Force      # 槽文件（SAVE78.DAT/.STH 等）
Copy-Item <带真存档的实例>/overlay/SYS4REG.INI .tmp/instances/<id>/overlay/ -Force      # 真机配置（含 message:Font 等）
Copy-Item <带真存档的实例>/overlay/SAVE/SAVE.DAT .tmp/instances/<id>/overlay/SAVE/ -Force # save-int/save-string 表（global 5 在此）
```

然后 `action=start`（`--idle-sec 0`）⇒ 约 20–25 s 后 `action=query frame` 会看到 `TITLE.BIN`；
此后 `action=op load-from-title --slot 78` **成功**。★`overlay/SYS4REG.INI` 可以换成**真机那一份**
（`%LOCALAPPDATA%\Eushully\天結いキャッスルマイスター\SYS4REG.INI`，57 行）——本轮就是这么做的，
顺带确认了真机配置：`message:ReadTextSkip=0`、`AdvanceMesOnWheel=3`、**没有** `set:ControlDisibleCursor` 键。
