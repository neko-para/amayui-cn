### 2) `0x1A1` 为什么不写操作数（本票最有价值的一条保真度结论）

- `sub_42DDE0` 函数体里**没有** `sub_42B4B0`（= 引擎唯一的"写操作数"出口）；对照 `0x1A0`/`0x19E`/`0x19F` 都显式调它。
- 调度器在 raw 21217：`(*(void (__thiscall **)(int))(_this + 4 * v18 + 675996))(_this);` —— **丢弃 C 返回值**
  （表基址 675996 由注册点反推：`0x190 → 677596`，斜率 4 ⇒ `offset = 675996 + 4*opcode`）。
  所以"失败时 return 1"只是函数返回值，**不是** `op1`。
- 真脚本的用法与此吻合：`src/$1$SC0330.txt:579` 给的是 `(global-int f7ffd)`（占位槽），
  而同一脚本里 `0x19E`/`0x1AE`（17533/17595 行）给的是 `(global-int 1396)`（真输出槽，17535 行 `eq … 1396 0` 判成功）。
  ⇒ 判定"读档成没成"必须先用 `0x1A0` 验头（`src/$1$SC0330.txt:539-540` 正是这么写的）。

### 3) 292 字节头（`0x1A0` 的字段来源）

- `sub_438120`（raw 45106-45149）：`ReadFile` 292 字节 → 魔数（`S4SD` 或 `S3SD`，由 `Engine+698904` 决定）→ 版本串 `strcmp` → **整份头 `qmemcpy` 给调用方**。
- `0x1A0` 取 6 个 u16 + 1 个 i32，本地结构里第 3 个 u16 位于 `+0x116`（跳过 `+0x114`）
  ⇒ 文件偏移是 **264/266/270/272/274/276**（`+268 = wDayOfWeek` 被跳过）+ **280**（i32 游玩秒数）。
- E4 实测（本机 47 个真槽 `SAVE\SAVE??.DAT`）：6 个 u16 与文件 mtime 的年/月/日/时/分/秒逐项一致、`format = 3`、
  `+280 > 0`；守卫 `test/save-slot.test.ts` 第一条就是这份对照。

### 4) 游玩秒数（头 `+280`）怎么算

- 写侧 raw 44812：`v24 = *(Engine+20764 + 1036) - *(…+1032) + timeGetTime() / 0x3E8;` 然后 `*(u32*)(Buffer+280) = v24`。
- 装载侧：载荷读侧 `sub_437980` 把 `+280` 存进容器 `[260]`（raw 45085），`sub_4380F0`（raw 45094-45103）
  再 `[259] = [260]`、`[258] = timeGetTime()/1000`（= 本次会话起点）。
  ⇒ `+280 = 上次存档的 +280 + 本次会话已过秒数` = **累计游玩秒数**（旧的"stamp = 单调时刻"说法不准确）。

### 5) ENC 不变量（两条 ENC 痕迹）

`0x1A1`/`0x19F` 装载完都把 `pool_int`（`Engine[95744]`，`Engine[95738]+1` 个 dword）**整体 ENC** 一遍
（raw 38433-38438 / 38360-38361，`ENC(a) = ROL4(key ^ ROR4(a,7),21)`、key = `Engine[97059]`）。
载荷搬运按 `set:SaveVersion1` 分支不同：a4==1 读时即 ENC（raw 19488-19490）、a4==2/3 直接 `memcpy`（raw 19624/19747）。
"文件里那份到底是明文还是 ENC"属于**未解**的槽载荷细节（`SLOT_GAPS`），本工程只对齐"运行时池是 ENC 态"这条不变量。

### 7) 本工程自己的槽格式（私有扩展，必须写清楚"引擎读不了我们的槽"）

- 同一个容器（`SAVE_MAGIC` + 引擎版本 + 标题 + SYSTEMTIME + `payloadBytes` + format + aux + 20 字节块 + 载荷），
  但 `format = 0`（明文）且载荷尾部多一个**尾块状态**：`AMYS1\n` + JSON
  （`key` / `cur` / 每帧 `scriptId`+`ip`+`retStack` / 全局池 int+float+str / `playSeconds`）。
- 尾块定位依赖 `buildPayload` 写的那个 `u32`（引擎的 `trailerDwords`；本工程写 0 当"空尾部块"）。
  ★**读侧必须吃掉这 4 字节**，否则 `trailing` 前面多 4 个 `00` ⇒ `decodeSlotState` 魔数匹配失败 ⇒ 读档只还原两张表。
  这是本轮实测踩到的真 bug（`decodeSaveData` 已修，见 changes.md）。
- 引擎格式的槽（`format >= 1`）只读头：状态主体布局未分析 ⇒ 如实返回 `engineFormat = true` + 空表 + `state: null`，
  **只把头的 `+280` 接回 `Engine.playSeconds`**（不接的话读真槽再存档，计时从 0 重新开始）。

## 已知边界（`SLOT_GAPS`，与 `src/vm/saveSlot.ts` 的常量保持同文）

1. 真槽（format 1..3）的**状态主体**未解析（只读头 + 游玩秒数 + 空表）；
2. 只还原"当前帧 + 调用栈上的帧"（引擎会按 `0xAE` 版本规则重算 ip，本工程写绝对 ip）；
3. `0x19E` 的覆盖确认框未建模（宿主无对话框 ⇒ 恒等于玩家点了"是"）；
4. `.STH` 只做不透明往返（截图的真实编码未解析）；
5. 按名读档族（`0x190`/`0x0AA`/`0x0AB`/`0x0AC`）未实现（语料 0 次）。
