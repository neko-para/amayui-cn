## 三条候选定因（★先钉住一条再改）

**A. 进入时合成了 hover-enter（光标停在侧边栏条上）**
链路：`i094` → `sub_404020` 首次 `sub_403C50` 命中测试 → 光标若在条内则 `cursor = 条下标` → 下一帧等待泵的 `sub_403E70`：`hover == -1`（被 `0x93` 清过）⇒ 发 `[259+条]` = `label_00000c74` = 展开 ⇒ `1399 = 2` + 16 槽摆到 0。
判据：光标停在条内进场景 ⇒ 应能观察到一次 `hover-enter` 派发到 `label_00000c74`。

**B. `139a` 被粘住（与光标无关）**
`139a` 是 **0/1 开关**（`sub dst 1 dst` = 取反，不是自减）⇒ LOCK 可开可关。LOCK ON 时此后**每个**场景启动都走 `mov 1399 2`。
判据：`139a != 0` 时进场景 ⇒ `1399` 直接是 2 且 16 槽为展开位，且**不依赖**光标位置。
已确认：脚本侧唯一写入端就是那个 LOCK 按钮的取反，不需要引擎写入；`139a` 是**会话级 global**（不落存档）。对照：同型开关 `139d` 才是**配置持久化**的（`SN0000.txt:443-445` `i1cb`(读配置)→取反→`i1ca`(写配置)；`:460-462` 走 `i1b6`/`i1b7`）。

**C. 视觉/状态不同步（场景重建未复位槽平移）**
进入时 16 槽平移是上一场景遗留值，而启动段把 `1399` 改成 1 ⇒ 状态收起、画面展开。
反证：此时移开光标触发的是 e78，而它的守卫要求 `1399 == 2` ⇒ 若纯 C，用户"hover 移开后就正常"应当**不会**发生。⇒ 当前证据更偏 A/B，但仍需断言确认（可能存在 A/B 先把它置成 2、再由移开触发收起的复合路径）。

## 追加：把"平移是否跨删除存活"这条候选也读掉了（结论：不存活 ⇒ 引擎也会画在基准位）

按 `0x220`/`0x1F7` 的 raw 逐字段核对：
- `0x220` → `sub_423DE0` → `sub_4AD3C0`：先把目标元素经 **`sub_4AAA50`(raw 130028，缺失即建项)** 取到，再写该元素的动画窗（`+68` delay / `+88` dur / `+104` / `D3DXMatrixTranslation(元素+0x1AC, …)`）。
- `0x1F7` count>1 → **`sub_4ABB60`**；count≤1 → `sub_4AB950`(raw 130778)：从 `_this+1032`（绘制项容器）erase 掉该 handle，并**销毁它的 record（vtable 删 + `operator delete` 掉 [2]/[3]/[4]）、从 `_this+1064`/`+1080`/`+1096` 三个容器里一并 erase**。
⇒ **元素连同它的动画窗一起被销毁**，`i220` 设的平移不可能跨"`detach-texture` + `draw-texture`"存活。
⇒ 引擎在 `1399 == 1`（收起）时走 `b884` → DRAWCHARM 重画，也只可能画在基准 `x=0x49c`（可见位）——**与我们的模型一致**。

**因此当前最可能的判断：这不是 emulator 的保真缺陷，而是脚本/引擎本来的行为** ——
侧边栏默认画在可见位；"收起"要靠 **一次光标移动** 经全屏热点 `label_00000e78` 触发，而**全屏热点只在展开态（`1399 == 2`）的热点表里**（`SN0000.txt:64-66` 在 `1399==2` 分支内）。场景启动只写 `1399 = 1`，于是：
- 进入时：可见（视觉）但状态是收起（`1399=1`、路由表 7 项、无全屏热点）；
- 第一次悬停条带 → `c74`（守卫 1399==1）把它抬到 `1399=2` 并换成 19 项的表（含全屏热点）；
- 再移开 → `e78` 真正执行收起动画（槽 +0x6e）⇒ "正常了"。

## 订正（用户指正，2026-09）

`SN0000.txt:232` 的 `sub (global-int 139a) 1 (global-int 139a)` **不是自减**：`sub dst a b` = `dst = a - b`，
而这里 dst 与第二个源是**同一个槽** ⇒ 实际是 **`139a = 1 - 139a`（0↔1 取反）**。所以：
- LOCK 是**正常可切换**的开关（我此前"只有自减端、打开就关不掉"的判断错误，已从台账删掉）；
- 同型开关 `139d` 走 `i1cb`(读配置) → 取反 → `i1ca`(写配置)（`SN0000.txt:443-445`）与 `i1b6`/`i1b7`（`:460-462`）⇒ **配置持久化**；
  `139a` 则是会话级 global（不落存档）；
- 本票的根因与修复**不受影响**（`0x256` 区间立即平移未实现；LOCK 逻辑本身正确）。

`binOp` 的读序已核对（`arithmetic.ts`：先 `readIntOperand(op2)`/`(op3)` 再 `writeIntOperand(op1)`）⇒ 我们的模拟器对"dst == src2"的取反算得正确，
