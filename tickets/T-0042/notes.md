## 2026-09-15 · 机制定位（T-0035 第 8 轮延伸）：230 不是「填充色」，是**文字层被按 α≈0.855 合成**

### 决定性测量：按通道解混合系数

对每个文字核心像素，用**同列上方 8px 的天空色**当背景 B，解 `α = (core − B)/(255 − B)`：

| 样本 | α(R) 中位 | α(G) 中位 | α(B) 中位 | 核心最亮 |
|---|---|---|---|---|
| 真机 新汉化 | **0.838** | **0.856** | **0.866** | 232 |
| emulator | **1.000** | **1.000** | **1.000** | 255 |

- 真机三通道解出的 α 一致（0.84-0.87）⇒ 文字是**半透明合成**，不是"填充色 230"。
- 真机核心颜色是 **(233,230,228)** —— **偏暖**（R>G>B），正是"白字以 ~85% 叠在暖色天空上"的结果；emulator 是纯 (255,255,255)。
- 这一条同时解释：核心**永远到不了 255**（α=0.855 ⇒ 上限 ≈ 0.855×255+0.145×bg ≈ 232，与实测最亮 232-235 吻合）、
  固定阈值下笔画"少 1px"（边缘被压到 170 以下）、以及观感"emulator 更粗更亮"。

### 同时排除（本轮新增，都有数据）

| 假设 | 判据 | 结论 |
|---|---|---|
| 整帧色调曲线（对比压缩） | 文字**描边**（引擎纯黑 0）在真机里最暗 = **3-4**（不是 25-30）⇒ 黑没被抬起 | ✗ 排除 |

### 本轮新读到的引擎事实（都写进能力台账了）

- `sub_455DB0`（raw 67944-67964）：**AA 门关时**（真机正是）文字由 **GDI 直接画进"窗表面"的 DC**
  （`sub_43B460` 锁表面 → `SelectObject(HFONT)` → `SetBkMode(TRANSPARENT)`）；**AA 开时这个函数什么都不做**（走另一条路）。
- 窗表面创建：`sub_43C8D0`（raw 48229+）用 `dwFlags = 7`（CAPS|WIDTH|HEIGHT，**不带像素格式** ⇒ 跟显示格式）、
  `dwCaps = 0x840`（OFFSCREENPLAIN|SYSTEMMEMORY）；贴出用**源色键**（`sub_43B070` → 表面 vtable+116，flag 8 = DDCKEY_SRCBLT）。
- 引擎自带的截图路径（raw 47895-47989）显示表面按 dd 掩码/移位转换（16bpp 时 5bit→8bit 是移位，白会变 248）——
  所以**格式转换也产生不了 230**。

### 剩下的唯一候选（也是最可能的一条）：**行淡入被冻在中途**

台账 `msgwin-line-fade-window` 的 note 原话：本工程的 DrawItem 颜色动画**已建模**，但"**缺的是把它接到消息窗行上**"。
引擎侧 `sub_45BE20` 附近（raw 72336-72348）给每行建色窗：`sub_4ACF60(item, rec[66], rec[67/68])` 设**起始色**，
`sub_4AD0C0(item, 0, speed×fade/100, -1)` 设**时长**（`MessageSpeed=50`、`MessageFade=250` ⇒ 125ms），
终点是 `0xFFFFFFFF`（不透明白）—— **若动画没跑完，文字就停在中间 α**。

真机的这三张参考图都是在**游戏窗口非激活**（用外部工具截的、菜单还显示着）的情况下拍的 ——
日式 ADV 常见行为是"窗口失活 ⇒ 暂停帧循环"，那么**色窗就冻在 α≈0.855 上**，而且三行共享起点 ⇒ 三行同为 0.855 ✓✓。

⇒ 判定方法（零成本，一步）：**把游戏窗口点成激活、让这一页显示满（≥1 秒）再截一张**，量同一句的文字核心：
- 若变成 **255/纯白**，且笔画指标回到 emulator 的档（中位 5、归一化 0.134）⇒ 230 是"淡入没跑完"的残留，
  **T-0042 与 T-0035 的观感差异都不是渲染器缺陷**，收口动作 = 在 emulator 里把行淡入真正接到消息窗行上（本就欠的那条）。
- 若仍是 230 ⇒ 是稳定的窗口/文字层 alpha，再去读窗 alpha 的来源（`message:MesWinAlpha=8` 目前**只在 op 0x131 被读、没有任何脚本用它**，
  疑为死键；需另找）。

## 2026-09-16 · **机制定位完成：填充色按「字形覆盖率 α」合成到已画好的描边上**（`Font+1352` 之外的第三条路）

### 二、机制的第二半：**表面 alpha = 覆盖率 α**（`sub_46D9F0` 32bpp 分支逐指令核对）

上轮只读了 `.c` 的 `dst = (C*v31 + dst*(255-v31))/255`，这轮把机器码也读了（`0x46DDC0-0x46DE7E`）：

```text
α = 255·cov/17（AA 关时恒满）        ; esi = α
if (α == 255)        pixel = C | 0xFF000000
else if (A_dst == 0) pixel = C | (α<<24)          ; ← 这一支是关键
else                 RGB = (C·α + D·(255−α))/255  ; 0x80808081 魔数 >>7 = /255
                     A   = max(A_dst, α)          ; ← 取 max，**不是** source-over 的累加
```

两条独立旁证支撑"贴出时按表面 alpha 合成"：

1. **槽里没被字涂到的像素 A=0（RGB 也是 0）**：若贴出不认 alpha，设置界每一行都会出现**黑块**；
   真机与模拟器都没有黑块 ⇒ 贴出确实在用表面 alpha（`sub_48AC40` raw 107006-107070：mode 0 的槽表面
   是 **A8R8G8B8 / D3DPOOL_MANAGED**，本来就有 alpha 通道）；
2. **数值核对**：行标签是**白填充 + 白描边**，落在行底板上（模拟器实测底板 ≈ `(65,47,40)`）
   ⇒ `α·255 + (1−α)·底板` = **(233,231,230) 暖**，与上轮记录的真机区间 **226-234（暖）**一致；
   若按不透明合成则应是纯白 255（= 上轮模拟器的值）。
