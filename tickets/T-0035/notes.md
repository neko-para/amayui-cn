# T-0035 · 过程文档（notes.md）

## 现象（用户实测 2026-09）

与真游戏对照：emulator 里**很多地方**的文字比引擎渲染的**更粗**，且**白色看着更亮**。

## 引擎的字体配置链（逐条核对，raw = `engine/天结_unpacked.exe_utf8.c`）

| 项 | 引擎 | 证据（raw） | emulator | 结论 |
|---|---|---|---|---|
| 面名 | `Font+1260`（主）/`+1320`（注音），来自 `message:Font` 与 `0x1A5`/`0x2FE` | 78859-78875 / 23666 | `msgwin.font.mainFace/rubyFace` + `resolveFace()` 映射到内置族 | ✅ 一致（映射政策另见 `fontSet.ts` 文件头） |
| 字号 | `Font+201684` 初值 24，`0x75` 写；`lfHeight = -size` | 78755-78872 / 24063 | `font.mainSize`（`0x75`） | ✅ 一致 |
| 字重 | `Font+1248` **初值 0**（FW_DONTCARE ⇒ 常规面），`0x2BD` 写 **700/0** | 78854 / 33394-33399 | `mainBold ? 700 : 400`（默认 400） | ✅ 等价（GDI 的 0 取常规面；400 = 常规面） |
| **抗锯齿** | `Font+1352` **初值 0**；**只有** `set:EnableAntiFont` 非 0 才读 `message:UseAntiFont` 并 `sub_4155B0` | 78755 / 23649-23656 / 22409-22422 | ❌（修复前）canvas **永远开 AA** | ★**不一致 → 已修** |
| 描边档 | `Font+1372` 初值 1（0 无 / 1 单向 / 2 同位叠 1/4 / 3 四向） | 78779 / 68091-68121 | `outlineMode` + `raster.ts` 逐档实现（不用 `strokeText`） | ✅ 一致 |
| 描边偏移 | `Font+1384/+1388` **初值 1/1** | 78780-78781 | `outlineDx/outlineDy`（默认走 `defaultWinStyle`） | ★**不一致 → 已修**（默认曾是 2/2） |
| 填充/描边色 | `Font+1360`（默认 `0xFFFFFF`）/`+1364` | 78891-78892 | `0x76`/`0x77` handler → 字段 21664/21665 | ✅ 一致 |

**判定：两处实质偏差** —— 主因是抗锯齿；另一处是**描边偏移的默认值**（引擎初始化 1/1，emulator 的
`defaultWinStyle()` 写的是 2/2 ⇒ 没有脚本显式设过偏移的文本，描边副本会偏出去 2px）。字重/字号/面名/颜色都对得上。

顺带核过、**不是**问题的一项：`Font+1236`（`lfWidth`）初值 **-12** = 高度 24 的一半 —— 对 CJK 字体来说
`tmAveCharWidth` 本来就是半角宽（= 高度/2），GDI 的字体匹配不会因此做横向压缩，与浏览器自然比例等价。

## 为什么本机的引擎是"无 AA"

```
真游戏 base 的 SYS4REG.INI：只有 [display]/[sound]/[message]/[system] 段，**没有 [set] 段**
  ⇒ GetConfig("set:EnableAntiFont") 缺键 ⇒ 引擎的缺键语义是写 0 并返回 0（sub_4957F0 raw 113008）
  ⇒ 23649 的 if 不进 ⇒ 根本不调 sub_4155B0 ⇒ Font+1352 保持初始化值 0 = 无 AA
本工程 overlay 的 SYS4REG.INI：[set] 段里写的是 EnableAntiFont=0（我们首跑生成的全量文件）
  ⇒ 同样无 AA
```

注意 `message:UseAntiFont=1` **确实存在**，但它只是"门后面的值"——门关着就不生效。这条很容易看错：
**只有先看 `set:EnableAntiFont`，才能决定 `message:UseAntiFont` 有没有意义。**

另两个"看起来相关"的键在渲染侧**没有读者**（别照抄成 AA 档位）：

- `message:AntiFontLevel` → raw 23653 写 `Engine+303796`；`grep 303796` 全库只有这一处写入、**零读取**；
- `set:Menu_UseAntiFont` → 只被配置表（`sub_434D00`）读写（raw 111703 / 112525），渲染侧无读者。

## 修复

1. **配置门**（`src/engineConfig.ts`）：`applyConfigToEngine` 里按引擎语义算两键门，写**字段 21662**
   （`Font+1352` = `Engine+85296+1352` ⇒ dword `(85296+1352)/4 = 21662`，与同族的 21664/21665/21667 一致）。
2. **样式携带**（`src/vm/handlers/msgwin.ts`）：`globalTextStyle().main.antiAlias = (字段21662 & 1) !== 0`；
   注音共用同一把开关；`FontSpec.antiAlias`（`text/layout.ts`）与 `DrawStringStyle.antiAlias`（`vm/native.ts`）
   把值带到两条渲染路径。快照语义与其它全局样式一致（入队时钉住）。
3. **锯齿字形化**（`src/renderer/text/raster.ts` 的 `thresholdAlpha`）：`antiAlias === false` 时，
   画完整窗后把画布 alpha 阈值化（`>= 128` 记满 255、否则 0，**颜色不动**）——
   canvas 没有"关文字 AA"的开关（`imageSmoothingEnabled` 只管图像缩放），所以按引擎的**结果**对齐：
   GDI 锯齿字形就是"每像素非 0 即满不透明"。消息窗（`rasterFrame`）与 `0x204/0x205` 直绘
   （`TextureCache.drawString`）两条路径同口径。
4. 阈值取 128（≈ GDI 在 50% 覆盖率处取整）。

## ★第 3 轮调查（2026-09，用户提供 4 张对照截图后）——「粗」的主因不在抗锯齿，而在**字重/字面**

### 用户提供的信息

- 用户提供 4 张截图：模拟器 ADV / 真机 ADV / 模拟器存档列表 / 真机存档列表（会话附件，不入库）。

### 量化测量（方法可复现，结论不依赖 .tmp）

方法：对同一行台词做「文本行分带 → 墨迹（亮度 > 170 的像素）覆盖率 + 横向游程中位/均值」统计。
★.tmp 里的对照图只是**临时产物，不作为证据**（票据证据 = 下面的数字与口径，复现步骤就在这段里）。

截图来源：

真机侧用用户提供的 ADV 截图（1602×958）。三张图都经过相同的 125% 显示缩放。

| 样本 | 末行覆盖率 | 横游程中位 / 均值 | 备注 |
|---|---|---|---|
| 模拟器 · **真 Bold 面**（现状） | **0.330 – 0.398** | 5 / 7.1 – 7.6 | `[font] Amayui CN#700 ← Amayui-CN_cnjp-Bold.ttf` |
| 模拟器 · 强制 **Regular 面** | 0.220 – 0.245 | 3 / 4.6 | 实验：把 `weight` 临时钉成 400 |
| 模拟器 · 强制 **AA**（关掉阈值化） | 0.185 – 0.245 | 3 / 4.6 | 与「Regular+阈值化」**同值** ⇒ 阈值化本身在这条度量上不可见 |
| **真机**（用户截图） | **0.257** | 4 / 5.87 | 落在两者之间、明显偏向 Regular 一侧 |

**结论**：

1. **抗锯齿不是可见主因**：AA 开/关测得的墨迹与笔画统计完全相同（这也解释了用户「没有变化」的观感）。
   ⇒ 第 1 次变更保留（它按引擎语义是对的、且有守卫），但**不能指望它解决观感**。
2. **主因在字面/字重**：模拟器的真 Bold 比真机重 ~1.3×（笔画）/ ~1.5×（墨迹）；真机落在我们
   Regular 与 Bold 之间、偏向 Regular。用户在 OPTOIN/CONFIG 与 ADV 两处都看到同一现象，符合「一支字重主因」。

  那个 vector 里（raw 22172-22237 的构建过程）——补丁会把 **Regular 与 Bold 两个文件**都放进游戏目录
  （`patch/patch.config.json:468-469`），`scripts/register-font.js` 也注册两面（会话级）。
- 未收敛的假说（**下一步要判定的就是这个**）：
  - **(a) 该机 GDI 只看到 Regular 面** ⇒ `lfWeight=700` 退化成 Regular（GDI 不做合成加粗）；
  - **(b) GDI 用的是真 Bold，但网格拟合/锯齿渲染比浏览器细 20-30%**；
  - **(c) ADV 文本用的不是主 LOGFONT**（`sub_459F40` 重建的 HFONT 集合 / 绘制路径用的句柄），

## 2026-09-15 · 第 4 轮：引擎侧核对「加粗到底由谁决定」（本轮只读引擎，未改产品代码）

用户假说：真机上「加粗面」与「常规面」像是**独立枚举**出来的配置项 ⇒ 引擎内部应该不会尝试直接加粗，
只有用户选了粗体字体才会粗。

### 引擎代码核对（结论：假说只有一半成立）

1. **面名只有一个来源**：`GetConfigString("message:Font")` → `sub_465390(Font, …, Source)` → `strcpy_s(Font+1260)`
   （注音面另有硬编码 `"ＭＳ ゴシック"` → `Font+1320`；运行时还能改面名的是 `0x1A5` / `0x2FE`）。
   配置键注册在 raw 111454-111458，缺省值就是 `asc_52686C = "ＭＳ ゴシック"`。
   **全库带 `Font` 的配置键只有 7 个（raw 4236/4334/4335/4387/4388/4389/5006），没有任何一个是"粗体面名"**
   ⇒ 加粗不可能靠换面名实现。
2. **字重只有一个表达**：`0x2BD`（`sub_426200` raw 33385-33402）非 0 ⇒ `Font+1248`（主模板 lfWeight）与
   `Font+218516`（当前字重）都写 **700**，否则都 0；初值 **0 = FW_DONTCARE**（raw 78854，**不是** 400）。
   `0x2BE` 同理写注音的 `Font+1308` / `+218588`。
3. **引擎不做合成加粗**：没有双画、没有 lfWidth 加粗、没有字形膨胀；`sub_459F40`（raw 70941-71191）
   只是把模板 qmemcpy 成 8 个即席 LOGFONT（含竖排 `'@'`、escapement 2700/1800、面 `"AGE Extend"` 的变体）
   再 `CreateFontIndirectA`，`lfWeight` 一路照抄。绘制全文只有两处 `TextOutA`（raw 68095/68587）：
   档位 3 连画 **5 次**是**描边**、不是加粗。
4. **所以决策权在 GDI 的族内选面**：700 只是"请求"；该族有粗体面就选它，没有就静默用常体
   （GDI 不合成、不警告）。这与补丁说明第 6 步「两份族名同为 Amayui CN、系统按 Regular/Bold 配对；
   只装一份时『加粗』那部分不会变粗」是同一件事。

### 顺带查实（可当探针用）

字体选择器的候选表 `Font+201664`（`0x2DC`/`0x2DD`/`0x2DE`）是 `EnumFontFamiliesExA` 的**族**列表：
`Proc`（raw 74146-74171）只收 `lfCharSet == 0x86` 且非光栅的族，`sub_45F6C0`（raw 75028-75100）
再用探针字 `Font+218524` 把缺这些字形的族删掉 ⇒ **一个族一条，粗体不会作为独立条目出现**。
（顺带：`sub_45F6C0` 的调用点是启动配置应用段 raw 23800，喂给它的名单来自配置对象 vtable+48。）

⇒ **真机上的零成本判定（假设 (a) 还是 (b)）**：打开游戏字体选择器，看 `Amayui CN` 出现**一条**还是**两条**。

- **一条** ⇒ 两份 TTF 在 GDI 里配成了一族 ⇒ 真机的 `i2bd 1` 确实选到 Bold ⇒ (a) 不成立，
  偏细只能归因光栅化（(b)：查 DPR / 笔画取整）。
- **两条** ⇒ 该机没配对 ⇒ 700 静默退回常体 ⇒ (a) 成立，且此时 emulator 的「700 → 真 Bold 面」
  就是**过度加粗**，该走 `fonts.bold: 'regular'` 一类策略。

随包资产本身是配得成一族的：两份 TTF 的 `name ID 1` 都是 `Amayui CN`、`OS/2.usWeightClass` = 400 / 700、
`ulCodePageRange1` 一致（含 cp932）；这一前提已被 `test/font-bold-face.test.ts` 钉成棘轮。
⇒ (a) 若要成立，只能是**该机的安装状态与随包资产不符**（缺装 Bold、装了旧版、或字体缓存口径不同）。

### 落库

- 第二层：新增 `bold-is-lfweight-face-mapping`（whySilent 写两种静默错法：(a) 额外合成 ⇒ 过粗、

- 第一层：`Font+1252`（打包 lfItalic/lfUnderline/lfStrikeOut/lfCharSet，初值 0x1000000 ⇒ lfCharSet=1）
  由 tentative 转 confirmed；`Font+218516` 语义收敛为「当前字重」；`0x2BD` 的 purpose 订正（旧措辞「重排文本」是错的）；
- 主题文档：`docs-new/03-engine/adv-text-rendering.md` §1 新增「字重（加粗）落在哪：面名 × lfWeight 的分工」，
  §7 补一段指向（并写明「真机更细」不能归因到「引擎不加粗」）。

## 2026-09-15 · 第 5 轮：量化判定「真机那次 700 有没有落到 Bold 面」——**没落到**（只读 + 复现测量，未改产品代码）

本轮用户答复：① 真机 ADV 对照截图是**两份字体都装好、并完全退出重启游戏之后**拍的；
② 装 700 后 ADV 有没有肉眼变粗「记不清」；③ 5 个字体分类**都设成了 Amayui CN**。

### 独立复现（用第三个光栅器，顺带把「DPR/取整撑胖笔画」这条假说排除）

用 PIL/FreeType 对**同一句台词**「ってきた世界の現神」按票里同一口径（墨迹 = 亮度 > 170；
文本行 bbox 覆盖率）重测：

| 渲染方式 | Regular | Bold | Bold/Regular |
|---|---|---|---|
| 30px 无 AA（hinted mono，最接近 GDI） | 0.241 | 0.379 | **1.57** |
| 30px AA + 阈值 128 | 0.236 | 0.345 | 1.46 |
| 38px AA + 阈值 128（≈DPR 1.25 的设备网格） | 0.221 | 0.350 | 1.59 |
| 38px 阈值化 → 降采样回 30px（≈我们的截图路径） | 0.209 | 0.345 | 1.65 |

- 与票里的实测**互相印证**：emulator 侧量到 Regular 0.220-0.245 / Bold 0.330-0.398，这里 0.209-0.241 / 0.345-0.379
  ⇒ 方法可靠，跨光栅器/DPR/提示网格的噪声 **≤8%**。
- 同一个族的两面覆盖率差 **1.46-1.59×**，比噪声带大一个量级 ⇒ 这个度量**足以判定用的是哪一面**。
- ★**「DPR/取整把笔画撑胖」被排除**：38px 设备网格（0.221 / 0.350）并不比 1× 无 AA（0.241 / 0.379）更胖，反而略轻。
  票里计划第 2 条（"按逻辑像素 1× 光栅化 + 整数对齐"）**不是**这条症状的解。

### 判定

真机 0.257 落在 **Regular 档（0.209-0.245）**，离 Bold 档（0.345-0.398）差 26-35%（≈2 倍噪声带）
⇒ **那张真机截图里，ADV 正文实际是用 Regular 面画的**：真机上那次 `i2bd 1` 的 700 **没有落到 Bold 面**
（GDI 静默退回常体，无错误、无警告）。

方向上与用户最初的怀疑一致（真机的加粗确实"没生效"），但**不是引擎机制的问题、也不是 emulator 面策略的问题**：

- 引擎侧：加粗 = `lfWeight=700` 的**请求**，落哪一面由 GDI 族内选面决定；族里没有可用的 Bold 面就静默退回常体。
  台账 `bold-is-lfweight-face-mapping`（本轮新增）、主题文档 `adv-text-rendering.md` §1「字重（加粗）落在哪」。
- 资产侧：随包两份 TTF 的 `name ID 1` 同为 `Amayui CN`、`OS/2.usWeightClass` 400/700、码页含 932；
  `res/fonts/Amayui-CN_cnjp-Bold.ttf` 与提交里的 LFS oid 一致（sha256 `6f336fad…`）⇒ **分发的那份就是这个**，
  在 Windows 上按定义能配成一族。守卫 `test/font-bold-face.test.ts`。
- ⇒ 真机没粗只剩**安装/缓存状态**这一类原因：仓库自己的 `docs/font-build.md` §8.5.2 / §8.6 就写着这个坑 ——
  「安装后若仍不生效：完全退出游戏 + **重启 FontCache 服务（或重启电脑）** 再测」；
  另外 `%LOCALAPPDATA%\Microsoft\Windows\Fonts\` 里若留着旧版（如缺 932 码页声明的早期构建，
  见 §8.6 的 `.tmp/font-backup/*.sarasa-nocp.bak`），游戏（日文 locale ⇒ `lfCharSet=DEFAULT_CHARSET` ⇒ 932 字符集选面）
  就看不到 Bold 面。

### 真机侧的两个零成本复核（等有环境时）

1. 游戏字体选择器里 `Amayui CN` 出现**一条**还是**两条**（引擎候选表 `Font+201664` 是 EnumFontFamiliesExA 的**族**列表）；
2. 重装两份字体 → **重启 FontCache 服务 / 重启电脑** → 完全退出游戏再进 ⇒ ADV 正文应**明显变粗**
   （按本票方法量同一台词，覆盖率应从 ~0.25 跳到 ~0.35-0.40）。

### 对票的处置

- 「emulator 更粗」这条症状的**基准不成立**：参照图来自「真机加粗没生效」的状态；
  emulator 现在的行为 = 引擎 + 正确安装的资产所应有的行为。
- 可选（由用户决定）：`fonts.bold: 'face' | 'regular'`（默认 `face`）只用于**在模拟器里复现"加粗没生效"的真机**，
  不是修 bug；原版日文游戏 ADV 用的是 メイリオ Bold（真粗体），所以 `regular` 与「对照原版」方向相反。

### 第 5 轮·稳健性补充（排除「真机量的是另一行台词」这个残余风险）

同一族两面各测 8 句不同台词的墨迹覆盖率（30px 无 AA）：

| | 逐行范围 | 行间散布 |
|---|---|---|
| Regular | **0.216 – 0.277** | 0.060 |
| Bold | **0.341 – 0.414** | 0.073 |

两面区间**不重叠**（Regular 最大 0.277 < Bold 最小 0.341），行间散布（≈0.06-0.07）小于两面间距（≈0.13）。
⇒ 真机实测 **0.257 落在 Regular 区间内、离 Bold 区间差 ≥25%** —— 即使真机当时量的是**另一行**台词，结论也不变：
**真机那次 ADV 用的是 Regular 面，700 没落到 Bold 面。**
