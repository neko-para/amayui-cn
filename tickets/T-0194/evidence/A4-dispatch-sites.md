* **不碰 ip、不碰返回栈**：0x400 只写在 `effectFlags`（`Engine+699204`）里，`sub_41A260` 只额外写
  「本帧步长 `95805=1`」。ip 的推进在主循环 `21218: *ip += 4 * stride;` 或
  `sub_411900` 的 `20165: _this[30*f + 95782] += 4 * _this[30*f + 95805];`。
  所以 `src/SN0000.txt:147 wait` 之后，下一轮执行的是 `:148 mov (global-int 1399) 2`，
  `wait` 只是让泵多转一圈（并且在**同一轮**的 21109-21152 里被吃掉，见下）。
* 另有三处把 0x400 当**状态位读**：`20643`（`!*(429752) || (flags & 0x400)` 决定这一轮要不要处理输入）、
  `20690`、`20755`。
* **推论（关于 label_00000c74 的 `:147 wait` 之后流程怎么走）**：`wait` **不会**改变 `label_00000c74`
  的返回语义。EN 派发时引擎压了返回点（20328 的 `sub_405360(_this, -3)` ⇒ 返回 (ip-base)/4-3），
  label 末尾 `:155 ret`（opcode 0x05）弹回该点；`wait` 只贡献 `effectFlags |= 0x400` 这一项
  （也就是真机看到的 `0x…0400` 那个 `0x400`）。

## 4. 为什么「四条约束」不可能同时成立（穷举）

### 4.1 所有清 bit31（`0x80000000`）的写点，以及它们对 bit30 做了什么

| raw | 函数 | 写法 | 同路径对 bit30 的处理 |
|---|---|---|---|
| 13731 | `sub_4090F0` | `a1[174801] &= ~0x80000000;` | 13734-13738 紧接着 `if (v9 & 0x40000000) {...; &= ~0x40000000u;}` ⇒ **清** |
| 14004 | `sub_409700` | `_this[174801] = 0;` | 整字零 ⇒ **清** |
| 17959 | `sub_40DF10`（切场复位） | `= 0` | 整字零 ⇒ **清** |
| 18983 | `sub_40FB60` | `= 0` | 整字零 ⇒ **清** |
| 20197 | `sub_411900` | `&= ~0x80000000` | 20198 `sub_4051A0`（**无门**）⇒ **清** |
| 20250 | `sub_411BC0` | `&= ~0x80000000` | 20247 `sub_4051A0`（门开）⇒ **清** |
| 20276 | `sub_411BC0` | `&= ~0x80000000` | 20278-20282 内联 ⇒ **清** |

| 25810 | opcode **0x7C** = `sub_41AB80` | `= *(489808) & 0xFDFFFFFF` | **整字恢复**（可能把 bit30 写回来） |
| 25723 | opcode **0x05 `ret`** = `sub_41A9B0` | `= 弹出值` | **整字恢复**（可能把 bit30 写回来） |
| 43688 | `sub_436380` | `= 0` | 整字零 ⇒ **清** |
| 90769 / 90974 | 4762F0 / 4764F0 | `= v1 & 0xFFBFFFFF` / `= v2` | 保留 bit30（也不清 bit31） |

（182645/182978 那两处 `v74 &= ~0x80000000` 在一个巨大的数据初始化块里，不是引擎代码。）

⇒ **「清 bit31」与「保住 bit30」在同一时刻、同一路径上互斥**（唯一例外是整字恢复类写点 25723/25810：
它们不「清」任何位，而是把某个**保存过的整字**写回去，因此能造出「bit31=0 且 bit30=1」）。

所以任务书观察到的 `0x40000400`（bit31=0、bit30=1）**只可能**来自：
1. 某个清 bit31 的站点（连带清了 bit30），**随后**被 `ret`(0x05) 从 `Engine+429732` 的 effectFlags 队列
   弹回一个「bit31=0、bit30=1」的旧值；或
2. 被 opcode 0x7C 用 `Engine+489808` 恢复；或
3. 250 ms 采样错过了短暂窗口。

队列的机制（都核过）：
* 压：`sub_409D40`（raw 14245-14265）＝ `Queue<int>::push`，调用点是
  `20022: sub_409D40(_this + 429732, *(_DWORD *)(_this + 699204));` 与
  `20082: sub_409D40(_this + 429732, *(_DWORD *)(_this + 699204));`（都在 `sub_411590` 派发面板 label 前）。
* 弹：`sub_41A520`（raw 25439-25449，对象在 `Engine+107433`＝+429732，[3]=数组、[4]=索引
  ⇔ `Engine[107436]`/`[107437]`），以及 `ret` 的内联弹：
  ```c
  25718:    result = _this[107437];
  25719:    if ( result >= 0 )
  25720:    {
  25721:      v3 = *(_DWORD *)(_this[107436] + 4 * result--);
  25722:      _this[107437] = result;
  25723:      _this[174801] = v3;                 // ← 整字恢复 effectFlags
  25724:    }
  ```
* **这正好也是「ENTER 派发 → 标签体 → `ret`」这一圈里唯一会把标志整字写回去的地方。**

### 4.2 「bit30 被清」到底会不会被任务书的三个观测量看见？

不会——这就是任务书前提 (4) 的漏洞：

* 清 bit30 **不写格节拍计时器**。计时器的 `[2]`/`[5]` 只被 `sub_453A90`（raw 66115-66123）与
  `sub_453A60`（66101-66112）写；调用点只有 `28553`（i072 重新武装）、`29339`（i1D4）、
  `28620`/`33362`（只写 `[6]` 间隔）。
* 清 bit30 只让 **20887 的格跳动闸门**短暂为假：
  ```
  20887:              if ( (v25 & 0x40000000) != 0 )
  20889:                v100 = sub_453AF0((_DWORD *)(_this + 430600));
  20890:                if ( v100 >= 0 ) { sub_45A940(...430816...); 430816 = (430816+1) % 430820; }
  ```
  `sub_453AF0` 用**绝对时间差**判拍（`v6 = timeGetTime() - _this[5]`），所以闸门关一小会儿只是
  让那一拍**晚到**，**不会**改变相位、**不会**改 `[2]/[5]`、**不会**把格号归零。
* 格号 `Engine[107704]` 的归零只发生在 `28552`/`29338`（i072 / i1D4 的武装分支），与清 bit30 无关。

⇒ **「[2]/[5] 从未回落」+「格号相位连续」这两条观测，与「`sub_4051A0` 跑过」完全相容**；
它们只能证明 **i072 从未在 bit30 为 0 的时候执行过**（即从未重新武装），证明不了 bit30 从未为 0。

## 5. 问题 5：`i093` 到底意味着什么（(2) 的推论）

`sub_4191D0`（opcode 0x93，raw 24588-24601）原文：

## 6. 在「纯悬停、掩码=0、真机 INI」下逐条走一遍（唯一可达路径）

真机 INI 相关键：`set:ControlDisibleCursor=0`、`set:ReDrawTextOnKey=1`、`set:WheelKeyUp=3`、
`set:WheelKeyDown=1`、`message:AutoMessageOption=0`、`message:AdvanceMesOnWheel=3`。

在 `sub_411BC0`（只在 bit31 置位的那一帧被调用）里，掩码=0 时：

* 20242 `sub_403D70(panelA, 掩码)`：键位表 `panel+7361` 与掩码比 ⇒ **-1**，跳过。
* 20262 `(*(_BYTE*)v2 & 0x50)` = 0；(1<<WheelKeyDown=1)=2，`2 & 0 == 0` ⇒ 跳过。
* 20315 `(掩码 & 0x20) == 0` ⇒ 进入；
  `((1<<WheelKeyUp=3)|(1<<WheelKeyDown=1)) & 掩码` = `(8|2)&0` = 0 ⇒ 进入 20322；
  `20322: if (Engine[51828])`（面板 A 显示）⇒ 进入；

## 7. 交付口径的最终答复

### ① 站点清单表
见 §2.1（19 行）。

### ② 能同时满足四条约束的站点
**没有。** 硬理由：§4.1 表明，**引擎里没有任何一条路径能在清 bit31 的同时让 bit30 保持为 1**
（每一条清 bit31 的路径都在同路径上清/零 bit30，唯二例外是「整字恢复」类写点
`ret`(0x05)@25723 与 opcode 0x7C@25810，它们不「清」位而是把保存过的整字写回）。
在「掩码=0 纯悬停」下能同时满足 (1)+(2) 的唯一站点是 **`sub_411BC0` 20324-20336**，
但它**会**调 `sub_4051A0`（门实测是开的），所以按字面它不满足 (3)(4)。

**最可疑的前提 = (4)⇒(3)**（「格节拍计时器没回落 ⇒ `sub_4051A0` 没被执行，⇒ bit30 没被清」）：
清 bit30 **不写**计时器（计时器只被 i072 的 28549-28553 / i1D4 的 29337-29339 重臂），只让 20887
的格跳动闸门短暂为假；而 250 ms 采样 + 相位连续 + `[2]` 单调，**都观察不到**这种短窗口。
要在真机上定案，应改测：
(i) effectFlags 以 ≪10 ms 采（或直接看 ▼ 格动画是否出现肉眼可见的停顿）；
(ii) 在悬停窗口内数 `Engine+430600[2]`（节拍计数）有没有「少跳」——「没重新武装」和「没被清」
在这两个量上给出的预测不同；
(iii) 或者直接读 `Engine+107704`（格号）在**一格之内**是否出现过重复/停顿。

**第二可疑 = (2) 的推论**（`i093` ⇒ 悬停 ENTER label）：§5 实测 4954 处里 4286 处不在 ENTER label，
SN0000 自己的 CLICK label（209/230）就含 `i093`。

### ③ getter 对缺失键返回什么
`Engine+697620` 是内嵌 `Reg`（vtable 0x5297DC），**vtable[1] = `sub_4904D0`**（raw 110691-110701）：
先 `sub_428E00(Reg+4, key)` 查 IntReg 哈希（raw 35333-35395）；**命中**返回**值槽地址**，
函数体再 `return *(int*)v2`；**未命中**则 `MessageBoxA(0, key, asc_529460, 0x10)` 然后
**`return 0`**。⇒ **缺失键返回 0**，所以 `!getter(...)` 为**真**（门开，`sub_4051A0` 会被调用）。
而且该键也不缺：构造期 `111543` 注入默认 0，真机
`…\Eushully\天結いキャッスルマイスター.overlay\SYS4REG.INI` 里 `[set] ControlDisibleCursor=0`
（任务书说「没有该键」看的多半是 `backup\SYS4REG.INI` 或乱码目录名那份——那两份确实连 `[set]` 段都没有）。
