# T-0141 · 调查与结论

> 一句话：**坐标口径是对的，`(120,206)` 也没点错 —— 但"切分类 = 载入 CONFIG2"这个前提是错的。**
> `CONFIG2` 只对应左侧第 5 项（角色设定）；`(120,206)` 是第 3 项 ADV设定，本来就该留在 `CONFIG1`。

---

## 1. 实验环境（这次是干净的）

```
cd app/amayui-emulator
node --import tsx src/web/host.ts --instance t141 --port 0 --attach-headless --idle-sec 0
```

* **`--attach-headless`**（`T-0140` 刚做的）：宿主自持一个隐藏渲染页 ⇒ VM 真的在跑，
  而且**不需要人打开面板**、也不会有"第二个页面 = 第二个 VM"来污染观测（`T-0138` 就是被这个坑过一次）。
* 驱动一律走 DSH 插件的每实例路由：`POST /dsh-emulator/t141/api/debug-query {"args":["click …"]}`。
* `viewers` 全程 = 1（只有那个自持的无头页）⇒ 单 VM，观测可判读。

## 2. 第一次尝试：**看起来"复现"了，其实是时序**

第一次我按票面写的一次性脚本跑：

```
click 807 621  → 注册表读到的 bin 还是 TITLE.BIN     ← 误以为"没进 CONFIG1"
click 120 206  → 注册表读到的 bin 变成 CONFIG1.BIN   ← 误以为"点了分类却没进 CONFIG2"
```

**这两条都是注册表心 lag 造成的假象**：`instance.json` 的 `lastStatus` 每 **5s** 才刷一次，
而 `CONFIG1` 的载入与初始化要几秒。截图揭穿了它 —— `01-config1.png` 拍到的**已经是 CONFIG1 的系统设定页**
（左侧 6 个分类全在），也就是说：**第 ② 次点击是在 CONFIG1 还没画出来的时候打进去的**，
自然什么也没发生（最后一张 `02` 图仍是系统设定页）。

⇒ 这正是票据里那句「当时观测被另一件事污染」的**同族错误**，只不过这次污染源换成了**我自己的等待策略**。
修法：不再等固定毫秒，改成"等状态稳定"；而且要读**页面自己的**真值而不是滞后的注册表。

## 3. 决定性证据：直接读页面的活帧栈

`debug-query` 的 `frame` 查询会列出**活帧栈**（带 `←cur` 标记当前帧）⇒ 不需要等注册表：

```
[2] CONFIG.BIN   scriptId=0x34   ip=40/426  caller=1
[3] CONFIG1.BIN  scriptId=0x51cc ip=48/2378 caller=2  ←cur
```

再加 `global 12721e`（**当前分类索引**，`src/CONFIG.txt:44` 初始化、`:51` 用它二选一）：

| # | 分类（截图读出的标签） | 点击坐标 | 实测当前脚本 | 期望（`CONFIG.txt:51`） |
|---|---|---|---|---|
| 1 | 系统设定 | (120,119) | `CONFIG1.BIN` | CONFIG1 ✓ |
| 2 | 游戏设定 | (120,169) | `CONFIG1.BIN` | CONFIG1 ✓ |
| 3 | **ADV设定** | **(120,219)** | **`CONFIG1.BIN`** | **CONFIG1 ✓** |
| 4 | 声音设定 | (120,269) | `CONFIG1.BIN` | CONFIG1 ✓ |
| 5 | **角色设定** | (120,319) | **`CONFIG2.BIN`** | **CONFIG2 ✓** |
| 6 | 操作设定 | (120,369) | `CONFIG1.BIN` | CONFIG1 ✓ |

**6/6 与脚本真源一致。** 脚本真源是 `src/CONFIG.txt:51`：

```text
51  eq (local-int c) (global-int 12721e) 4     ; 当前分类 == 4 ？
52  jcc (local-int c) ffffffff label_000003b8
53  call-script 51cb  // CONFIG2                ; 是 ⇒ 角色设定页
57  call-script 51cc  // CONFIG1                ; 否 ⇒ 其余五页共用
```

⇒ **`CONFIG2` 不是"任何切分类都会载入"，它只是左侧第 5 项（角色设定）那一页**；
第 1–4 与第 6 项**共用 `CONFIG1`**（它 2378 条指令，一个脚本里装了四页）。
页面标题也跟着变（系统设定 → ADV设定 → …）与 bin 不变**并不矛盾**：换页发生在 `CONFIG1` 内部。

角色设定页的截图证据：`evidence/config2-character-page.png`（9 个角色位 + 左侧「角色设定」高亮），
ADV 页：`evidence/config1-adv-page.png`（标题「ADV设定」、左侧高亮同项）。

## 4. 命中矩形**实测**（票面要求逐条对照）

`config1Chain.ts:683` 的口径是「`190×26` 的贴片画在 `(24, 106+50i)`」。x=120 固定、逐 y 扫、
每次先回分类 0 再点目标 y 并读 `12721e`：

```
真实命中带（每项整 50 高、无缝隙）：
  分类 0: y 100..149      分类 3: y 250..299
  分类 1: y 150..199      分类 4: y 300..349
  分类 2: y 200..249      分类 5: y 350..399
（y ≥ 400 落到下方「初始化本页 / 初始化全部」区，会把分类重置回 0）
```

对照表：

| i | 公式贴片 `y = 106+50i .. +26` | 公式中心 `119+50i` | **实测命中带** `100+50i .. 149+50i` |
|---|---|---|---|
| 0 | 106..132 | 119 | 100..149 |
| 1 | 156..182 | 169 | 150..199 |
| 2 | 206..232 | **219** | 200..249 |
| 3 | 256..282 | 269 | 250..299 |
| 4 | 306..332 | 319 | 300..349 |
| 5 | 356..382 | 369 | 350..399 |

**结论：公式是安全可用的，但把 26 高的"绘制矩形"当成了"命中矩形"。**
两者不是一回事：真实命中带是**整 50 高**（贴片只是画上去的样子）。
好在公式给出的中心点（`119+50i`）以及仓库里实际用到的那几个 y（106/156/306/319）**全都落在正确项内**
—— 实测 6/6 命中正确分类，**没有一次点错**。

★但这条差异有实际后果，必须写下来：**`y = 150` 已经不是第 1 项而是第 2 项**。
所以"取贴片矩形求交集/边界"这种推算会错；要判边界只能按 `100+50i` 那套命中带。

## 5. 为什么原票据的两次观测会得出"没切到 CONFIG2"

| 原观测 | 真因 |
|---|---|
| 点 (120,206) 没进 `CONFIG2.BIN` | ① `(120,206)` **本来就不该**进 CONFIG2（它是第 3 项 ADV设定，属于 `CONFIG1`）；② 而且当时它是在 CONFIG1 还没画出来时打进去的（本次复现到同款假象，见 §2） |
| 反而出现一条完整重引导链 | 那是 `T-0138` 的 P0（切形态重建 iframe ⇒ 实例重启），与本票的坐标无关 —— `T-0138` 已修 |

⇒ 票据标题里的「没有切到 CONFIG2」**不是坐标缺陷**，而是**判据用错了脚本**（外加一次时序失误）。
坐标口径本身经实测**成立**。
