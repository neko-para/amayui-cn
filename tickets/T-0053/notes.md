# T-0053 · 过程文档（notes.md）

## 从 ticket.json 的 `notes` 字段迁入（2026-09 文档模型）

为什么值得留一张票而不是只在注释里写一句：① 它是**宿主能力**问题（不是 VM 语义），换宿主（Electron 加原生模块、或换 WebView）就可能变可做 ⇒ 需要一个能被「下次换宿主」时重新评估的归口；② 四条语料用途（1470 处 ADV 侧栏钉光标 + 光标位置记忆 + 拖动回夹 + 对话框居中）里，前两条的**设计意图**就是「玩家看得见光标被挪过去」，观感缺失会让这些界面显得键盘与鼠标不同步；③ T-0051 第 5 条（用键盘走 ADV 侧栏）验证时一定会撞上它 ⇒ 票与票之间要能互相指。★当前状态：引擎侧已建模、守卫已绿（T-0048 done）；本票只跟踪**宿主侧**这条缺口与其决策。
★2026-09 决策与落地（本票的验收第 3/4 条）：**选路线 ①（原生模块调 `SetCursorPos`）** —— 理由：它是唯一能真正复现引擎行为（真实光标真的挪过去、玩家一动鼠标就被新位置接管）且不改变交互模型的做法；② 自绘软件光标要自己处理越出画布/多显示器边界，③ pointer lock 会改变交互模型（Esc 才退出），代价都比"一个 60 行的 N-API 模块 + 一条 IPC"高，而后两者能换来的好处（无原生依赖）在本工程不构成约束（Electron 本来就在本仓构建）。
实现票 = **T-0058**（可复用的原生模块工程 `native/` + `native/win32-input` + 主进程/IPC/渲染侧接线 + 打包方案）。落地要点：`SetCursorPos` 之前有**两跳换算**必须在，① 虚拟→客户区（渲染侧，用与 `inputAttach.toVirtual` 同一套 canvas rect 的逆）；② 客户区→屏幕 DIP→**物理像素**（主进程 `getContentBounds` + `screen.dipToScreenPoint`）。本机 125% 缩放实测：`DIP(447,390) → 物理(559,488)`，少了第二跳就会偏左上。
★仍待人在真界面确认的是**观感**（本票验收第 4 条后半句）：三条语料用途各自的可见变化（ADV 侧栏钉光标 1470 处 / `SBUNKI`·`BUNKI` 的光标位置记忆 / `ALLMAP` 拖动回夹 / `SELSTAGE` 对话框居中）—— 已列进 `T-0051` 的 E4 清单（"0x10A 侧栏钉光标"）。
守卫：`app/amayui-emulator/test/native-win32.test.ts`（7 条：降级契约 / 搜索链顺序 / 真产物只读探测 / 0x10A 宿主缝坐标一致 / headless no-op / 主进程与渲染侧换算源码棘轮）。
