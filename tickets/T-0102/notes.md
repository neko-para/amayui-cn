## 轮 12 续：判据 4（「阿瓦罗的名字变青色，预期橘色」）—— 通道顺序**判死**

### 1. 引擎写入口的位运算，与 emulator 逐位等价

`src/vm/handlers/msgwin.ts:57` 的 `bgrToRgb` 注释逐字引了引擎那一行（`sub_466000` raw 79666）：

```
*(_DWORD *)(_this + 1360) = BYTE2(a5) + ((BYTE1(a5) + ((unsigned __int8)a5 << 8)) << 8);
```

令 `a5` 低三字节 = b0/b1/b2，右边 = `b2 + (b1<<8) + (b0<<16)`，即**把输入当 COLORREF
（`0x00BBGGRR`：b0=R、b1=G、b2=B）读，写成 `0xRRGGBB`**。emulator 的
`((v&0xff)<<16) | (((v>>8)&0xff)<<8) | ((v>>16)&0xff)` 与它**逐位相同**。
⇒ 通道顺序**不是**症状来源：同一次交换作用在整张调色板上。

为什么"正文看着正常、只有角色名偏"恰好符合这个结论：调色板前 4 条是白（`ffffff`），
而正文用的是**暖白/近似中性色**（T-0042 实测真机文字核心 (233,230,228)）——中性色交换前后
几乎无视觉差异；只有**饱和色**（角色名）才会一眼看出橘↔青。**若是通道错，正文也该偏。**

### 2. 调色板的青与橘，是**相邻的下标**

真机 `SAVE.DAT` 的 `adcd`（`LOADCONFIG.txt:34-49`：`for i in 0..0x3e8` 循环里
`lookup-array … adcd … i` + `load-int (local-ptr 0)` ⇒ 1000 条逐个从 overlay 读入）交换后：

| 下标 | 原值（BGR） | 渲染（交换后） |
|---|---|---|
| 0-3 | `ffffff` | `#FFFFFF` |
| **4** | `ffe100` | **`#00E1FF` 青** |
| **5** | `84b1ff` | **`#FFB184` 浅橘** |
| 6 | `dcdcc6` | `#C6DCDC` |
| **7** | `71d8ff` | **`#FFD871` 金橘** |
| 8 | `00d3c3` | `#C3D300` |
| 9 | `4dbf67` | `#67BF4D` 绿 |
| **10** | `2c9bdd` | **`#DD9B2C` 橘** |
| 11 | `d15e4b` | `#4B5ED1` 蓝紫 |
| 12 | `ff90b6` | `#B690FF` 紫（= 判据 3 的残留色） |

⇒ **青（下标 4）与橘（下标 5/7/10）在同一张真机调色板里相邻。** 「青 vs 橘」的候选因此是
**取了下标 4 还是下标 5/7/10**，即 `14acda`（角色号）的派生 —— 不是通道顺序。

```
setDrawColorAlpha   h=0x19640 from=0xa0000000      ← 半透明黑（α=0xa0、RGB=a9db=0）
…
setDrawColor        h=0x19640 d=0 c=800 to=0x-1    ← ★"淡入到**当前色**"（-1 = 操作数）
setDrawColorAlpha   h=0x19640 from=0x0
```

引擎 `sub_4231F0`（0x202，raw 31395-31411）**逐字**：

```c
if (α <= 255) { if (α < 0) α = (unsigned)sub_4ADD60(Scene, handle) >> 24; } else α = 255;
if (color < 0) color = sub_4ADD60(Scene, handle);      // 当前色（整份 ARGB）
```
`sub_4ADD60` = 按 handle 查绘制项、查不到返回 −1、否则读 `DrawItem+0x60`（`Item.from`）。

- **引擎**：`-1/-1` ⇒ TO = `0xA0000000` ⇒ 淡入成**半透明黑** ✓（真机）
- **旧模拟器**：`(-1 & 0xff) << 24 | (-1 & 0xffffff)` = **`0xFFFFFFFF`** ⇒ 淡入成**白** ✗（症状）

`0x203` 的**同一对回退**模拟器早就实现了 —— `0x202` 漏了。
