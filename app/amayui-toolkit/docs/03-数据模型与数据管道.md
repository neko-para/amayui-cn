# 03 — 数据模型与数据管道

> **权威源 = 工程根 `src/`**（ITINIT/PLINIT/ALINIT/EBINIT/STINIT/STINIT2/SKINIT，含 `日文|中文` 名）。提取产物是**衍生物**，直接落到前端可 fetch 的 `public/data/metadata.json`（`public/` gitignored；CI 在 deploy 分支构建生成）。
> 提取脚本与前端的类型契约都放在**本 app 的独立 monorepo** 内（不共享 scripts 环境）。

## 0. 管道一览

```
工程根 src/
 ├─ ITINIT.txt($n$)  物品名 set-string 「日文|中文」
 ├─ PLINIT.txt($n$)  建筑/设施名
 ├─ ALINIT.txt($n$)  配方 mov（标记1物品/2建筑 + 产品 + 元数据 + {材料id,数量}*）
 ├─ EBINIT.txt       单位 名字/副标题 + 掉落 (rate@53eXXX,item@53dXXX)
 ├─ STINIT2.txt($n$) 场景/地图名 + 场景记录（mapNo=addr−0x121e2；loc/seq 槽线性偏移，sub 0 1→loc=-1）——**地图的数据源**
 ├─ STINIT.txt($n$)  地图块 eq … b222 <mapNo> + 单位槽 mov（14dd<0x40+i> 前/后字段）——**单位 join 源**（同场景跨文件按槽合并）
 ├─ SKINIT.txt($n$)  技能名 + 三行描述文案（三段并列数组，stride 0x3e8；见 docs/re/src/05-技能数据.md）
        │
        ▼  app/amayui-toolkit/scripts/extract-metadata.mjs
        │       校验（主键唯一、join 完整、计数核对）+ 归一化（取 src 中文名、派生 craftable、地图/单位槽、场景→地点）
        ▼
app/amayui-toolkit/public/data/metadata.json  ← 前端 fetch('./data/metadata.json') 直接消费（衍生物，gitignored）
        │
        ▼  Vite 将 public/ 原样拷入 dist/ → 上 GitHub Pages（deploy 分支，CI 构建）
```

## 1. 产物：单一 `metadata.json`

旧版是 5 个不同格式的 JSON（两任务产出，风格不一致）。统一为**单一文件**，字段全部带中文名，且结构可复用于「数据查看/检索/联动跳转」。

```jsonc
{
  "schemaVersion": 4,
  "generatedAt": "…",
  "sourceTree": "src",
  "counts": { "items", "buildings", "recipes", "itemRecipes", "buildingRecipes",
              "units", "unitsWithDrops", "dropEntries", "distinctDropItemIds",
              "maps", "mapUnitEntries", "mapUnitDistinctUnits", "mapSpawnableEntries",
              "locations", "mapsWithLocation", "skills", "skillsWithDesc" },
  "items":     [ { "id", "name", "nameZh", "source", "craftable" } ],
  "buildings": [ { "id", "name", "nameZh", "source" } ],
  "recipes":   [ { "type", "productId", "productRef", "product", "productZh",
                   "source", "metadata": [...], "materials": [ { "itemId", "count" } ] } ],
  "units":     [ { "unitId", "name", "nameZh", "title", "titleZh", "nameLine",
                   "hasDrops", "drops": [ { "itemId", "rate", "rateRaw", "itemRaw", "rateMeaning" } ] } ],
  "maps":      [ { "mapNo", "name", "nameZh", "source",
                   "locationId",                       // v3：所属地点 id（null=无标准地点）
                   "units": [ { "unitRef", "spawnFlag", "faction", "row", "col",
                                "levelMin", "levelMax", "extra": [ { "off", "val" } ] } ] } ],
  "locations": [ { "locationId", "name", "nameZh", "source", "maps": [ "mapNo"* ] } ],  // v3：抽象地点
  "skills":    [ { "skillId", "name", "nameZh",              // v4：技能（SKINIT）
                   "title", "titleZh",                       // 描述①题头【分类：名】＋属性
                   "body", "bodyZh",                         // 描述②详述
                   "short", "shortZh",                       // 描述③单行简述
                   "hasDesc", "source", "nameLine" } ]
}
```

> **类型契约（TS-first）**：`app/amayui-toolkit/src/types/metadata.ts` 定义了上述全部类型（`Metadata`/`Item`/`Building`/`Recipe`/`Unit`/`DropEntry`/`MapData`/`Location`/`Skill`/`MetadataCounts`）。前端由此唯一形态消费；`schemaVersion` 变更时 bump，前端按版本兼容。

## 2. 名称中文化（`name/nameZh/titleZh/productZh`）

- 真值来自 `src` 的 `set-string (global-string <addr>) "日文|中文"`，管道分隔：
  - `name` = `|` 前半（日文），`nameZh` = `|` 后半（汉化）。
  - `|` 缺失（未汉化）时 `nameZh = name`；前端按“未汉化”回退展示。
- 物品 id = `addr − 0x18e40`；建筑 id = `addr − 0x1f5ba`（**两套 id 空间**，`recipes[].productRef` 消歧）。
- **全部 id 空间基址收敛在 `src/services/idspace.ts`**（`ID_BASE`：item `0x18e40` / building `0x1f5ba` / unit `0x17ab6` / map `0x121e2` / location `0x1216e` / skill `0x1d4f4`）。
  搜索项的 `addr` 与卡片徽标 `<类型> #<id16> · <addr16>` 都由它生成 —— 两者**同源同形**（有单测锁定），故卡片上的地址可直接粘回搜索框。
- 配方 `product/productZh`（产品名）与单位 `title/titleZh`（副标题）同样取自 `src`。
- 实测未汉化项：物品 40 / 建筑 8 / 单位 6（见 README 一致性说明）。

## 3. 关键字段语义（部分未定）

| 字段 | 说明 |
|---|---|
| `items[].craftable` | 是否出现在某条物品配方（`productRef:'item'`）的产品中（布尔）。 |
| `recipes[].metadata` | 该行未知元数据（保序串，形如 `6bb1d7(3e8)=a21c`），**语义未定**。 |
| `drops[].rate` / `rateMeaning` | 掉落率/权重，值域多为 5..100；`rateMeaning:'unknown'`，**勿当确定百分比**。 |
| `units[].hasDrops` | 是否有掉落表；无者 `drops` 为空（共 40 个剧情/纯敌人单位）。 |
| 物品/建筑 id 重叠 | 如 id 51：物品=城砦拡張図面Ⅰ、建筑=小さな家（黄）。用 `productRef` 区分产品用哪套名表。 |
| `skills[].skillId` | 技能 id = 名串地址 − `0x1d4f4`（**第 4 套 id 空间**，与物品/建筑/单位互不相干）。稀疏，实测 1..803，共 450 个。 |
| `skills[]` 的三行文案 | 取自**三段并列定长数组**（段间 stride `0x3e8`=1000）：`short`=`0x1d8dc+id`、`title`=`0x1dcc4+2id`、`body`=`+1`。**按当前范围只存原始文案**，题头里的分类/属性后缀不预先拆分。 |
| `skills[].hasDesc` | 是否带完整三行描述；`false` 时三行为 `null`（实测仅 #40「進行不可」，纯内部状态技能槽）。 |
| 技能数值字段 | 威力/射程/消耗等 `mov` 项**尚未提取**，语义未定（骨架见 `docs/re/src/05-技能数据.md` §4）。故技能卡片暂无数值区与跨实体跳转。 |
| `maps[].locationId` / `locations` | **抽象地点**（v3）：由 STINIT2 场景记录的 loc 字段归并。地点 id = 地点名 `set-string` 地址 − 0x1216e；场景的 loc 槽 = `0x14e4e1 + sceneIdx`，seq 槽 = loc + `0x3e8`（线性偏移）；`sub ... 0 1` → loc = **-1**（无标准地点，`locationId=null`，如事件/特殊图）。`locations[].maps` 为去重的 mapNo 列表（**按场景自己的 seq 字段排序**，即地点内场景顺序），用于 **地点 ↔ 地图** 互跳。 |

## 4. 前端索引与依赖图（在 `src/dataset/` 中构建）

```ts
// 载入 metadata.json → 内存结构
{
  byItemId: Map<number, Item>,
  byItemName: Map<string, Item[]>,        // 名称规范化（日/中）→ 物品
  recipesByProduct: Map<number, Recipe>,  // 产品 id → 配方
  recipesByMaterial: Map<number, Recipe[]>, // 材料 id → 用到它的配方
  dropsByItem: Map<number, Unit[]>,       // 物品 id → 掉它的单位（含 rate）
  unitsById: Map<number, Unit>,
  byMapNum: Map<number, MapData>,         // mapNo(十进制) → 地图
  byLocation: Map<number, Location>,      // locationId → 抽象地点
  bySkill: Map<number, Skill>,            // skillId → 技能（0x1d4f4 + skillId 为名串地址）
  // 注：各 id ↔ 名串地址的换算统一走 services/idspace.ts，不在各处重复基址常量
  mapsByLocation: Map<number, MapAppearance[]>, // locationId → 该地点内的地图（地点 → 地图）
  mapsWithUnit: Map<number, MapData[]>,   // 单位 unitRef(=unitId) → 出现它的地图（反向）
  craftGraph: Graph,                      // 物品 → 材料（规划器用，防环）
}
```

> 检索：**中/日双索引**（jp 名 + zh 名），任中其一命中即返回。`@mui/x-data-grid` 做大列表，`Fuse.js` 可选模糊。
> 地图：`maps[].units[].unitRef` 与 `units[].unitId` 同键（`0x17ab6 + 单位槽寄存器 id`）；`mapsWithUnit` 由该键做**单位→地图反向查询**。

## 5. 制作规划器（后续 / 独立模块）

`输入(目标物品 + 数量) → 输出(依赖树 + 汇总)` 一次性变换，无背包/持有量。要点：
- 递归展开 `recipesByProduct`；DFS **防环**（标记 `cycle`）。
- 汇总结：同一基础材料多路径出现时聚合总量。
- 每叶子标获取途径：可再合成 / 掉落单位+rate / 未知（无配方无掉落）。
- 目标 `craftable=false` 时提示“不可合成”。
- 纯 TS（`src/services/planner.ts`），可 `vitest` 单测。

## 6. 校验与幂等

`extract-metadata.mjs` 内置断言：
- 各表计数与数组长度一致；`recipe-items`/`recipe-buildings` 计数与主工程旧文档不符时**以文件为准**。
- 所有配方 `materials[].itemId`、所有 `drops[].itemId` 必须映射到某个 `items.id`。
- `recipes[].product` 不得为空。
- 幂等：`pnpm build:data` 可重复，输出固定 schema；`schemaVersion` 变化时前端按版本兼容。

## 7. 运行期数据交付（`public/data/metadata.json`）

- 提取脚本**直接输出**到 `public/data/metadata.json`（前端 `fetch('./data/metadata.json')` 消费）。该文件是**衍生物**（`public/` gitignored）。
- **部署模型**：GitHub Pages 走**独立 deploy 分支**，在 CI 上 `build:data && build:web` 后把 `dist/` 提交到 deploy 分支；**主分支不提交衍生物**（`public/`/`dist/` 均忽略）。本地 gitignore 仅为调试便利（随时可由 `src` 重新生成）。
- **趋势**：数据量小（数 MB），JSON 足够；未来陡增再考虑 `sql.js`/`better-sqlite3`，或在部署前置做索引/瘦身预计算。
