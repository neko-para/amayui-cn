# 04 — 功能与界面设计（SPA）

> 采用**单页 SPA**：局部单视图，无 URL 路由；查阅记录用**页内内存历史**维护。上下两区如下。

## 0. 布局

```
┌────────────────────────── Top AppBar ──────────────────────────┐
│  Amayui Toolkit   [← back]  [→]   …数据版本/计数…     主题       │
├────────────────────────────────────────────────────────────────┤
│ 上半：搜索区（规则式，见 §2）                                     │
│  ［🔍 名称…（自动补全）］                    ← 名称规则槽           │
│   [类型:单位 ✕] [种族:鬼 ✕] [星级≥★3 ✕]  [＋筛选 ▾]  ← 分面 chips │

│  ……（多张卡片纵向 Stack）…                                     │
└────────────────────────────────────────────────────────────────┘
```

## 1. 数据抽象与通用渲染容器（核心）

**下半区是一个通用渲染容器**，只认“当前视图”的内容——一个**有序卡片列表**。后续可通过此抽象实现前后路由/查阅历史。

```ts
// types/nav.ts
export type CardKind = 'item' | 'unit' | 'building' | 'recipe' | 'message';
export type CardSpec =
  | { kind: 'item'; id: number }
  | { kind: 'unit'; id: number }
  | { kind: 'building'; id: number }
  | { kind: 'recipe'; productId: number }
  | { kind: 'message'; text: string };
export type View = CardSpec[];   // 下半区当前内容 = 有序卡片
```

- **渲染**：`<CardList cards={view}/>` 用 `switch(card.kind)` 映射到具体卡片组件（`ItemCard`/`UnitCard`/`BuildingCard`/`RecipeCard`/`MessageCard`）。容器与“数据内容”解耦。
- **跳转**：`navigate(expr, view)` 接受**内部 query 表达式** + 其结果视图；卡片内部可点引用（`RefChip`）用 `queryFromId` 构造单实体 query。一次搜索 = 一个视图 = 全部结果卡片。
- **历史**：内存维护 `HistoryRecord[]`（`{expr, view}`）栈 + 指针，`goBack`/`goForward`（AppBar 的 ←/→）。历史条目 key = 规范化表达式串（去重），点击回放该表达式。

## 2. 搜索区（表达式 query 模型 → 可见「规则」）

**搜索 = 内部 query 表达式**，由若干谓词（AND 交集）组成（见 `src/types/search.ts`：
`category`/`nameSub`/`nameExact`/`idExact`/`unitAttr{race|gender|attribute}`/`unitStar{op,N}`，
结果按「kind 固定序 → 序号」规范化排序，(kind,id) 去重）。

**设计目标**：把该 query 模型以「**可见、可编辑的规则**」呈现给用户，并让**右侧历史侧栏**用**同一套规则渲染**。
为此引入两个共享件（顶部与侧栏复用，文案不各写）。

### 2.1 谓词 → 规则（唯一映射）

| 谓词 | 规则文案 | 作用域 |
|---|---|---|
| `category(k)` | `类型: 单位` | 全部 |
| `nameSub(x)` | `名称含 "x"` | 全部 |
| `nameExact(x)` | `名称=「x」` | 全部 |
| `idExact(n)` | `id <hex>` | 全部 |
| `unitAttr{race}` | `种族: 鬼` | 仅单位 |
| `unitAttr{gender}` | `性别: 女` | 仅单位 |
| `unitAttr{attribute}` | `属性: 火炎` | 仅单位 |
| `unitStar{gte,N}` | `星级≥★N` | 仅单位 |
| `unitStar{eq,N}` | `星级=★N` | 仅单位 |

实现：`rulesFromExpr(expr)`（谓词 → 规则定义）+ **`RuleChips({ expr, interactive, dense })`** ——
顶部搜索区用 `interactive`（可删/可加），历史侧栏用 `readonly + dense`，两者共用同一组件与文案。

### 2.2 顶部搜索区（两行）

```
[ ✏️ 名称…  🔍▾ (清除) ]                    ← 名称规则槽（Autocomplete freeSolo）
规则： [类型:单位 ✕] [种族:鬼 ✕] [星级≥★3 ✕]   [＋筛选 ▾]
```

- **搜索框 = 「名称」规则**：键入 = `nameSub`（实时草稿）；点候选 = `nameExact` **同名成组**（并把该候选类型写成「类型」chip）。
- **分面 chip 行**：`＋筛选` 弹窗（`Popover`）加 类型/种族/性别/属性/星级；`Chip variant="outlined" onDelete` 删除。
- **每轴单选**：种族/性别/属性/星级同轴再取值 = **替换**（实体不可能同时两种，避免空集）。
- **单位分面自动锁定类型=单位**：出现任一分面谓词 → 类型=单位且锁定（移除该 chip 会连坐清掉单位分面）；清空全部分面解锁。对应 `search.ts` 里 `normalizeExpression` 的隐藏规则，此处**显式化**。
- **draft / commit 两态**：chips + 名称框改动 = 草稿（**不写历史**）；回车 / 点候选 / 删 chip / 关弹窗 = 提交 `navigate(expr, view)`（一条历史，避免边敲边污染历史区）。
- **空态**：全空 → 现有 `MessageCard`。
- 组件事例：`Autocomplete(freeSolo)`、`Popover`、`Select`/`ToggleButtonGroup`(≥/= + 星数)、`Chip`。查询内核 `buildResults`/`expressionKey`/`navigate(expr,view)` **不变**。

### 2.3 右侧历史侧栏（与顶部统一）

- 每条历史 = **同一 `RuleChips`（readonly + dense）**：`flexWrap` ≤2 行，超出折成 `…(N)`，`title` = 完整规则。
  **不再用文本 label / kind 图标**（类型由「类型 chip」承担）。
- **点击 = 回填草稿 + 展示结果**：`draft.load(expr)`（顶部呈现同批规则 chips + 名称文本）→ `navigate(expr, 结果)`。
- 历史去重键仍为 `expressionKey(expr)`；`expressionLabel`/`describeCard` 文本仅作 `title` / 无障碍兜底，不作主呈现。

### 2.4 状态：useSearchDraft

`useSearchDraft`（zustand，局部）持有 `{ nameText, facets[] }`：`load(expr)`（从历史/任意表达式回填）、`toExpr()`（序列化回 `SearchExpression`）。
名称规则 = `nameText`，其余分面谓词 = `facets`；这样**历史重放与顶部草稿共用同一数据模型**。

> 注：`category` 作为「类型」chip 显式存在后，搜索框也可**跨类型搜索**（不带类型 chip）—— 这是本次重写顺带解决的原限制（此前必须点某类候选才能定类型）。

## 3. 卡片内容（关系反查，均支持跳转）

> **id / 地址徽标（统一约定）**：每张实体卡片标题行都带一枚徽标 `<类型> #<id> · <名串地址>`，
> **id 与地址一律 16 进制**（无 `0x` 前缀）。地址 = 该 id 空间基址 + id，与搜索框接受的 16 进制查询串**同形**，
> 因此徽标上的地址可直接粘回搜索框定位；反过来也便于把 UI 里看到的实体对回 `src/*.txt` 的 `set-string` 行。
> 各 id 空间基址与格式化函数集中在 `src/services/idspace.ts`（`ID_BASE` / `addrHex` / `idHex` / `entityTagLabel`），
> `dataset.ts` 的搜索项与所有卡片共用同一份，避免基址散落。
> 注意物品与建筑 **id 空间重叠**（如 id `33`：物品=城砦扩建图纸Ⅰ / 设施=小屋（黄）），靠地址或 `productRef` 区分。
> RecipeCard 因配方自身无名串，徽标标的是**产物**的 id 与地址（随 `productRef` 取对应 id 空间）。


| 卡片 | 展示 | 可点引用（→ 跳转目标） |
|---|---|---|
| **ItemCard** | 日/中名、id、`craftable` 徽标、来源 | 材料（→ 其 item 卡）、产品（→ 对应 item/building 卡）、掉落单位（→ unit 卡） |
| **UnitCard** | 日/中名、`title`/`titleZh`、id、掉落清单、**出现在地图** | 掉落物品（→ item 卡）、地图（→ map 卡，反查） |
| **BuildingCard** | 日/中名、id、其建筑配方材料 | 材料（→ item 卡） |
| **RecipeCard** | type、产品、材料| 材料/产品（→ 对应卡） |
| **MapCard** | 日/中名、`mapNo`、**数据表格：地图内单位**（坐标/等级范围/阵营/刷怪） | 单位（→ unit 卡） |
| **MessageCard** | 纯文本（空态/错误/来源未知提示） | — |

- ItemCard 关系块：**配方（作为产物）**、**作为材料（出现在哪些配方）**、**掉落来源（哪些单位掉它 + rate）**、**出现在哪些建筑配方**。
- UnitCard 掉落：`物品(rate)`，`rate` 带“率/权重（未定）”徽标；**出现在地图**用 `mapsWithUnit` 反向查询，列出该单位出现的全部地图（→ map 卡）。
- MapCard：**数据表格**直接列该地图内的单位槽，含 `坐标(列,行)`、`等级范围`、`阵营`、`刷怪`，单位可点（→ unit 卡）；**单位 → 地图 反向查询**由 `mapsWithUnit` 支持。
- 未知信息不误导：`rate`/recipe `metadata` 带“未定”徽标；`craftable=false` 标“不可合成”。

## 4. 状态管理（zustand）

```ts
interface AppStore {
  dataset: Metadata | null; loaded: boolean; error?: string;
  view: View; history: View[]; pos: number;      // 内存历史
  navigate(cards: View): void; goBack(): void; goForward(): void;
  theme: 'light'|'dark'|'system';
  setting: { showUnknown: boolean };
}
```

- `isReady`：`fetch('./data/metadata.json')` → 置 `dataset` + 建索引（`byItemId`/`byUnit`/`byBuilding`/`recipeByProduct`/`materialsIndex`/`dropsByItem`/搜索索引）。
- `navigate(expr, view)`：push 当前 view 至高亮历史，替换 `view`；首屏默认 `[{kind:'message', text:'请在上方搜索…'}]`。历史 record = `{ expr, view }`，去重键 = `expressionKey(expr)`（见 §2.3）。
- 新增 `useSearchDraft`（§2.4）：持有搜索区「草稿规则」，`load(expr)` 供历史回填、`toExpr()` 供提交。
- 加载中骨架屏、失败错误 + “重试”。
